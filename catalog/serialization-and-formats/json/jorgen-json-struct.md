## Verdict

In stephenberry/json_performance (results dated 8 June 2025; MacBook Pro M1, single core, Clang 17, 1,000,000 iterations of one \~0.6 KB object), json_struct from master took 5.87 s for parse-plus-serialize roundtrips against 15.44 s for nlohmann/json v3.11.3 (about 2.6x), with 178 vs 86 MB/s write (2.1x) and 316 vs 81 MB/s read (3.9x) (derived from page data). nlohmann's time includes building its DOM (json::parse then get&lt;obj_t&gt;; j = obj then dump) and a fresh obj_t each read, while json_struct reads into a reused object. An earlier run of the same harness (9 August 2024, Clang 15, preserved in the Loki-Astari fork) gave 5.50 s vs 15.71 s, 182 vs 84 MB/s and 326 vs 80 MB/s, consistent with the 2025 run.

## Use it when

- You already map JSON to plain C++ structs with nlohmann's to_json/from_json and want 2-4x faster struct reads and writes without moving to a C++20/23 reflection library.
- The toolchain is stuck at C++11/14 (old GCC, VS2015-era MSVC, embedded SDKs), which rules out Glaze (requires C++23) and reflect-cpp (C++20).
- Human-edited config files where comments, unquoted keys and trailing commas should parse into typed structs.
- Inputs that arrive in pieces or are very large, using the chunk-fed JS::Tokenizer instead of materializing a document.
- A dependency-free single header with a permissive licence that you can vendor.

## Skip it when

- Top throughput is the goal: on the same harness Glaze (1.01 s roundtrip), yyjson (1.22 s), reflect-cpp (3.15 s), daw_json_link (3.29 s) and RapidJSON (3.76 s) all beat json_struct's 5.87 s, and Boost.JSON (5.38 s) is level with it or slightly faster.
- You need a mutable dynamic JSON value with nlohmann-style operator[] editing; json_struct is built around fixed struct schemas (JS::Map is a read-and-dispatch helper, not a full document model).
- Structs with many members: each incoming key is matched by a linear, compile-time-unrolled scan over member names (primary names first, then aliases), so cost per key grows with member count, unlike Glaze's hashed lookup.
- Number-heavy data with large or very negative exponents: values outside the fast path are converted by multiplying or dividing a 128-bit integer by 10 once per exponent step, so 1e-300 costs hundreds of loop iterations, and the double path has no big-integer correctness fallback (only float gets one).
- Strict schema validation by default: unknown keys are skipped and missing members accepted unless you change ParseContext's flags.

## How it is fast

There is no intermediate tree. A pull tokenizer yields key/value tokens that point into the input buffer, and a compile-time member table generated by the JS_OBJ macros dispatches each key to its member through an unrolled length-plus-memcmp comparison. Values are decoded in place: integers and doubles use a bundled copy of the author's float_tools (Clinger fast path for short significands and exponents, otherwise iterative 128-bit scaling; a Ryu-derived shortest-digit printer for output). Serialization writes into chunked buffers. Since commits of 30 September to 6 October 2025 (after the measured run; the measured header has no SIMD intrinsics), SSE2/SSE4.2/AVX2/NEON scans locate string ends, number ends and whitespace, with a scalar fallback.

## Compared with alternatives

Pick json_struct over Glaze or reflect-cpp only when you cannot use C++23 (Glaze) or C++20 (reflect-cpp), or when you want relaxed config-file parsing into structs; on speed alone they are 1.9-5.8x faster on the same roundtrip harness. Against Boost.JSON (about the same speed) and RapidJSON (faster), json_struct binds straight to structs without hand-written DOM walking or SAX handlers.

## Gotchas

- Lenient by default: ParseContext::allow_missing_members and allow_unasigned_required_members both default to true, so unknown JSON keys are skipped and absent struct members leave old values in place, and parseTo still returns NoError. Set both to false for strict parsing. track_member_assignement_state (default true) also records each unknown key as a std::string; the benchmark harness turned it off in its roundtrip loop but not in its read loop.
- Tokens and DataRef values point into the caller's input buffer, so the buffer must outlive the ParseContext; parsing into an existing object clears and refills vectors and strings and keeps their capacity.
- Version measured versus version shipped: the June 2025 harness fetched master with GIT_SHALLOW. The master tip before 8 June 2025 was commit 6e69e4a (26 March 2025; the next commit is 10 June 2025), and that header (8,656 lines) contains no SSE/AVX/NEON code. The numbers therefore describe the pre-SIMD scalar parser. The SIMD tokenizer and 'More optimizations' landed 30 September to 6 October 2025, and more parse and serialize performance commits landed 4 July 2026 (the current header is 10,315 lines). Current builds are probably faster, but no published number backs that.
- Correctness fixes after the measured run (commit f5bf752, July 2026): \u escapes for U+0800..U+FFFF were decoded with a wrong UTF-8 lead byte (0xd0 instead of 0xe0; the line is still present in 6e69e4a), surrogate pairs were not combined, malformed integers such as '12-3' were silently truncated, and NaN/Inf were written as bare nan/inf (invalid JSON). The benchmark input has no \u escapes, malformed integers or non-finite values, so the measured numbers are not affected, but older vendored copies of the header carry these bugs.

## Known shortcomings

- Glaze author's json_performance harness (June 2025): no optimization flags or build type stated (CMake sets the C++23 standard, no default build type); json_struct pulled from unpinned master; slower than Glaze, yyjson, reflect-cpp, daw_json_link and RapidJSON, and its roundtrip (5.87 s) is slower than Boost.JSON (5.38 s). No first-party performance numbers. Licence is HPND-sell-variant, which SPDX does not flag as OSI-approved (no patent grant), so usability is reference per the BSD-3-Clause-Clear precedent.
- Enricher: the measured json_struct is master 6e69e4a (2025-03-26), a scalar header predating the SIMD tokenizer (2025-09-30 to 2025-10-06) and later perf commits, so no published number covers the current code. Harness asymmetries: json_struct reads into a reused object (keeps capacity) while nlohmann builds a DOM plus a fresh object each read; is_valid_write only prints and does not suppress results; the read loop keeps track_member_assignement_state on. Corroborated by an Aug 2024 run (Clang 15, Loki-Astari fork: 5.50 vs 15.71 s). Lenient defaults (unknown keys skipped, missing members accepted, NoError returned); the double slow path loops once per exponent step with no bigint fallback; the Jul 2026 fix f5bf752 (UTF-8 lead byte, truncated malformed ints, bare nan/inf) is off the benchmark path.

## Caveats and trade-offs

Comparison is struct binding, not DOM parsing (nlohmann goes through its DOM via json::parse plus get&lt;obj_t&gt;, which is how that library binds structs), and the harness author is the Glaze maintainer (a competitor, but not of json_struct or nlohmann); the harness repo itself has about 30 stars. Optimization flags and build type are not stated and the Clang build (Apple or LLVM) is unspecified; hence tier B, not A. Results are dated June 8, 2025 and json_struct was pulled from master at build time, so the version measured is unknown. On the same harness json_struct trails Glaze, yyjson, reflect-cpp, daw_json_link and RapidJSON, and its roundtrip (5.87 s) is slower than Boost.JSON (5.38 s); the win is only against nlohmann. MB/s figures are scaled by the minified document length. json_struct's own repo has a performance/ folder (json_struct vs RapidJSON, simdjson and nlohmann under Catch2) but publishes no results, and the README makes no performance claim, so the list's 'High performance' wording is not backed by the project itself. COPYING is an HPND-sell-variant permissive licence (GitHub shows no SPDX id; the awesome-cpp tag says MIT); it is a variant of the OSI-approved HPND, though SPDX does not flag the sell variant itself as OSI-approved; no patent grant.

Single header (C++11), maps JSON to structs through JS_OBJ macros, relaxed-parsing options. The same table puts json_struct well behind Glaze (1.01 s), yyjson (1.22 s), reflect_cpp (3.15 s), daw_json_link (3.29 s) and RapidJSON (3.76 s), and about level with Boost.JSON (5.38 s roundtrip, 198 MB/s write, 308 MB/s read).

## Maintenance

Actively maintained (630 commits, last commit 29 August 2026, ClusterFuzzLite fuzzing and ASan/MSan CI on PRs). The single header is easy to vendor under an HPND-style permissive licence with no patent grant. The project publishes no benchmark numbers of its own (performance/benchmark.cpp is a Catch2 suite with no results), and the only harness numbers predate its SIMD rewrite and the July 2026 correctness fixes.

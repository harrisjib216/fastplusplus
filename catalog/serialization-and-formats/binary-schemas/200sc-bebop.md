## Verdict

In alecthomas/go_serialization_benchmarks (SmallStruct: two strings, a time.Time, int32, bool, float64), 200sc/bebop v0.5.0 marshals in 94 ns/op and unmarshals in 112 ns/op, against 287/356 ns/op for protobuf-go (google.golang.org/protobuf v1.34.2), about 3.1x/3.2x. With buffer reuse it marshals in 52 ns/op, and against gogo/protobuf (115/166 ns/op) the margin is \~1.2x/1.5x. The Bebop payload is 55 bytes, against 51 for protobuf-go. All rows came from one user-generated run (PR #178, July 2025), and neither the CPU nor the Go version is stated.

## Use it when

- Go services that exchange records with Bebop code in C#, TypeScript, Rust, Dart, Python or C/C++ generated by the upstream bebopc, where Go needs its own codec.
- Hot paths that marshal many small, flat records and where protobuf-go's \~290/360 ns per marshal/unmarshal is visible; reusing an output buffer brings marshal to \~52 ns/op.
- Fixed-layout records that never gain fields (Bebop 'struct', no per-field overhead), with 'message' reserved for records that must evolve.
- Little-endian targets (amd64, arm64) and builds that can run a code-generation step; the module has no third-party dependencies.

## Skip it when

- You need protobuf wire or .proto compatibility, gRPC, or protobuf tooling: this is a different IDL and format. RPC/service definitions are not supported (issue #25 open), and upstream Bebop v3's breaking schema changes are not implemented (issue #40 open since March 2024).
- Decoding untrusted input: generated UnmarshalBebop/DecodeBebop call make() with the uint32 array or map count read from the payload before checking it against the bytes that remain, so a 4-byte input can request a multi-gigabyte allocation.
- Cross-language exchange of date fields: this project writes time.Time as UnixNano()/100 (100 ns ticks since 1970), while the Bebop spec and the upstream TypeScript and Rust runtimes use ticks since 0001-01-01 (offset 621355968000000000), so dates will not round-trip between runtimes. The repo's compatibility tests only compare schema acceptance with upstream bebopc, not bytes.
- Big-endian GOARCHes (s390x, ppc64, mips): iohelp loads and stores integers in native byte order through unsafe.Pointer, so bytes would be wrong there. This is not documented, and CI runs only on ubuntu-latest.
- Go-only data where raw speed is the goal: benc/usafe (121 ns total) and mus/unsafe_reuse (105 ns total) beat 200sc/bebop/reuse (162 ns) in the same table. Schemas also cannot use int8 or recursive structs (testdata/incompatible).

## How it is fast

The Bebop wire format has no per-field tags and no varints: struct fields are concatenated fixed-width little-endian values, strings and arrays are a uint32 length plus payload, and messages add only a uint32 length and a 1-byte index per present field. The generated code is reflection-free, computes the exact encoded size up front with Size(), allocates once, and writes each integer with a direct unsafe.Pointer store into the byte slice (iohelp/bench_test.go compares this against encoding/binary.LittleEndian). MarshalBebopTo into a caller-owned buffer removes the output allocation (the 52 ns/op 'reuse' row). An optional -share-string-memory flag makes unmarshalled strings alias the input buffer instead of copying.

## Compared with alternatives

Pick it over benc, mus-go, colfer or gencode when the schema must be shared with the canonical Bebop toolchain (the 6over3/bebop entry) in other languages. Those four sit in the same 80-125 ns/op marshal band, but their formats are Go-specific. If data never leaves Go, benc or mus-go are as fast or faster and avoid the date-encoding mismatch.

## Gotchas

- MarshalBebopTo does no size check (documented in io.go) and panics on a short buffer; call Size() first. The Must\* methods from -generate-unsafe skip all bounds checks.
- With -share-string-memory, decoded strings alias the input []byte, so reusing or mutating that buffer changes them.
- Dates: the zero time.Time is written as 0 and 0 decodes to the zero time, so 1970-01-01T00:00:00Z comes back as time.Time{}. Decoded times are always UTC at 100 ns precision, and UnixNano is undefined before 1678 or after 2262.
- The streaming EncodeBebop/DecodeBebop path is about 6x slower than the []byte methods (io.go). Nested-message DecodeBebop through a reader returned a false EOF until v0.6.1/v0.6.2 (issue #46, July 2024). The benchmark pins v0.5.0 but uses only the []byte path.

## Known shortcomings

- Dates are encoded as 100 ns ticks since 1970, while the Bebop spec and other runtimes count from 0001-01-01, so dates do not round-trip across languages. Generated decoders allocate the payload's uint32 array/map counts before bounds checks (a 4-byte input can request gigabytes). Native byte order via unsafe.Pointer, so big-endian output is wrong. Last functional release v0.6.2 (2024-07); benc and mus-go unsafe variants are faster in the same table.

## Caveats and trade-offs

This is a Go implementation of the Bebop format, distinct from the canonical https://github.com/6over3/bebop repo already catalogued (not a fork; its README credits 6over3/bebop and documents incompatibilities with the original compiler). The report states no CPU or Go version, and results are user-generated per the report page, so the tier is capped at B. The suite encodes time.Time at 100 ns precision. The independent wellquite.org/bebop Go implementation benchmarks almost identically (95/118 ns/op).

Implements the Bebop IDL/wire format (a schema compiler is required); this is an independent third-party Go codegen backend, not the canonical Bebop repo, so cross-language support depends on this project tracking the Bebop spec.

## Maintenance

Apache-2.0 and dependency-free. The latest release is v0.6.2 (2024-07-05), and the only later commit is a one-line README change (May 2026), so treat it as stable but dormant, not actively developed; the runtime is small enough to vendor.

## Verdict

The author generated translation units with benchmarks/gen.py (200 enums of 16 members, 32 of 200, 200 of 16 at -1024..1024, 100 of 50 at 0..50), each calling to_string once per enum, and averaged 10 compiles with GCC 14.2.0 and Clang 20.1.2 at -O3 and MSVC 19.44 at /Ox on an unnamed Windows 10 machine: with default settings enchantum is 5.7x faster than magic_enum on GCC Small (8.2 vs 47 s), 6.4x on Big, 2.3x on Ideal Range for GCC and Clang, and near parity on MSVC Ideal Range, and with the check disabled 7.8x on GCC Small and Big; Clang object files are 2.7x (Small) to 15.6x (Big) smaller. First-party, compile time and size only.

## Use it when

- Projects with many reflected enums where magic_enum shows up in build profiles; the README's 200-enum GCC case went from 47 s to 8.2 s with default settings.
- Enums with values within a few hundred of zero, or wider ranges that magic_enum cannot handle in reasonable time (Large Range -1024..1024: 34 s on GCC with defaults, magic_enum did not finish in 20 minutes).
- Third-party or C enums you cannot edit, where simple_enum would need first/last markers added to the enum.
- Builds that care about object and executable size: Clang objects 2.7x to 15.6x smaller than magic_enum in the README cases.
- Teams that want a compile error when an enum is only partly reflected (the default out-of-bounds check) instead of silently missing values.

## Skip it when

- Wide-string names: the README lists no wchar_t support, which magic_enum has.
- Enums with tight known bounds where you can annotate first/last: simple_enum compiled faster in the README's Ideal Range case on all three compilers (GCC 2.7 vs 3.0 s, MSVC 4.7 vs 5.8 s).
- MSVC with default settings on small-range enums: Ideal Range is 16 s vs magic_enum 17.9 s, essentially parity.
- Forward-declared enums (static_assert), unnamed enums outside MSVC, unscoped enums nested in class templates on Clang, and scoped or aliased enums in templates on NVC++ (docs/limitations.md).
- If you need a runtime lookup speedup: only compile time and binary size were measured, no to_string or cast throughput.

## How it is fast

Like magic_enum it reads enumerator names out of __PRETTY_FUNCTION__ / __FUNCSIG__, but magic_enum instantiates one is_valid&lt;E, V&gt;() / n&lt;V&gt;() function template per candidate value in the range, while enchantum instantiates a single var_name&lt;V0, V1, ..., Vn&gt;() whose signature string lists the whole range at once; a constexpr linear parser (parse_string) then separates named values ('E::Name') from casts ('(E)42'). Fewer template instantiations is where the compile-time and object-size gap comes from. Names are packed into one char array with a uint8/uint16 offset table, which keeps object files small.

## Compared with alternatives

Pick enchantum over simple_enum (the catalogued sibling that also beats magic_enum on instantiation time) when the enums are not yours to annotate with first/last or when object size matters (simple_enum's Clang objects were 4x to 358x larger in the README cases); pick simple_enum when you can give tight bounds and want the fastest compile. The serialization siblings (Cista++, YAS, bitsery, struct_pack and others) solve a different problem and can use enchantum for enum names.

## Gotchas

- The README's bold compile times are with ENCHANTUM_CHECK_OUT_OF_BOUNDS_BY=0, a define benchmarks/gen.py does not write, and they come from 2025 commits (MSVC column refreshed 2025-06-08, GCC 2025-07-10); the parenthesised default-setting numbers were remeasured on 2026-05-13 after the check was made cheaper (GCC Small 9.3 to 8.2 s, MSVC Large Range 265.1 to 111.4 s), and the check was changed again on 2026-09-07 without a README update. One table therefore mixes library versions and dates, competitor versions are unstated, and Clang Ideal Range moved from 3.5 to 3.8 s across that remeasurement, so differences under about 10% are noise.
- gen.py gives simple_enum two extra enumerators, first and last, set to the whole reflection range (the README admits this misuses simple_enum), and gives magic_enum the same range as enchantum. The Small case (-128..128) is essentially magic_enum's documented default (-128..127), so Small (7.8x with the check off, 5.7x default on GCC) is the fair headline; Big and Large Range push magic_enum to 2x and 8x its default range.
- The default check rescans [2\*min, min-1] and [max+1, 2\*max] and static_asserts if an enumerator sits there; values beyond twice the range are still silently dropped, and the check is skipped for bitflag enums and for enums with a specialized enum_traits. Bitflag enums reflect only 0 and single powers of two, not combinations.
- Issue #18 (closed): with MSVC /GL and /Ot, string-to-enum cast on a uint8_t enum returned 86 instead of 2 in Release builds; the reporter says magic_enum shows the same, and the page shows no linked fix. Range macros must be identical in every translation unit to avoid ODR violations (docs/limitations.md). The GCC parser stores each name length in a uint8_t and scans at most 255 characters for the separator, so very long enumerator names are outside what it handles (code reading, not tested).

## Known shortcomings

- Tier C: compile-time-only comparison. README numbers match gen.py output and gen.py is public, but CPU, library versions and command lines are not stated; the headline numbers use an out-of-bounds check setting of 0 that gen.py does not set. simple_enum wins the Ideal Range column on all three compilers; magic_enum was run at ranges far above its default.
- The README table mixes runs: the bold check-off numbers come from 2025 commits, the parenthesised default numbers were remeasured 2026-05-13, and the check changed again 2026-09-07 with no README refresh; Clang Ideal moved from 3.5 to 3.8 s across the remeasurement (about 10% noise). The Small range -128..128 is about magic_enum's default -128..127, so 'far above default' holds only for the Big and Large ranges; gen.py gives simple_enum extra first/last enumerators. Issue #18 (MSVC /GL /Ot cast gives a wrong value) closed with no linked fix; MSVC Ideal is at parity (16 vs 17.9 s).

## Caveats and trade-offs

First-party benchmark; CPU model, exact command lines and the versions of magic_enum, simple_enum and conjure_enum are not stated, so it falls short of tier A, although the generator (benchmarks/gen.py) is public and its four test cases (Small 200 enums x 16 members, range -128..128; Big 32 x 200, -256..256; Large Range 200 x 16, -1024..1024; Ideal Range 100 x 50, 0..50) match the README table. The bold headline numbers are with the out-of-bounds check disabled (ENCHANTUM_CHECK_OUT_OF_BOUNDS_BY=0), which gen.py does not set, so they need an extra define; the parenthesised values are the default setting (2) and are about 1.2x to 2.1x slower on GCC (MSVC Small 37.4 vs 15.8 s, MSVC Ideal Range 16 vs 5.8 s), so the default-configuration win over magic_enum is smaller (GCC Small 5.7x rather than 7.8x; MSVC Ideal Range 16 vs 17.9 s, near parity). simple_enum is faster on the Ideal Range case on all three compilers (GCC 2.7 vs 3 s, Clang 2.3 vs 2.9 s, MSVC 4.7 vs 5.8 s); the author notes simple_enum was given first/last members spanning the whole reflection range, which the README itself calls a misuse of that library. magic_enum is given the same ranges as enchantum (up to -1024..1024, where it timed out after 20 minutes), far above its default -128..127; the Ideal Range case (0..50), where magic_enum is only 2.7x slower with the check disabled, is the least range-inflated comparison. Each generated file calls to_string once per enum through a volatile; there is no runtime lookup benchmark and no comparison with a hand-written switch or string_view table. Object and executable sizes were measured on Clang only. The README links a post by Vittorio Romeo (a friend of the author) on the compile-time cost of enum-to-string with C++26 reflection versus older methods via reddit; reddit and the aggregator copy (feedbagel.com) were blocked here, so it was not read and no independent reproduction was found. Headline numbers use out-of-bounds check 0, which gen.py does not set. simple_enum wins Ideal Range on all three compilers; MSVC Ideal at parity (16 vs 17.9 s). magic_enum run far above its default range only in the Big and Large rows. The default setting adds an out-of-bounds check (ENCHANTUM_CHECK_OUT_OF_BOUNDS_BY=2) that detects enums not fully reflected, at extra compile time.

## Maintenance

Actively maintained (version 0.5.0 prepared 2026-09-07, last commit 2026-09-16, C++26 reflection backend added 2026-08-29), MIT-licensed and header-only, so it is easy to vendor; two open issues (package-manager integration, C++14 support).

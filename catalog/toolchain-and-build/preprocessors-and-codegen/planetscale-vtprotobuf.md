## Verdict

Per the author's 2021 Vitess blog post (Vicent Marti), a synthetic VReplication stress test replicating a large MySQL table between keyspaces measured 7.17 CPU-seconds of unmarshal overhead with stock protoc-gen-go (APIv2) vs 4.15 CPU-seconds with vtprotobuf's UnmarshalVT (\~1.7x), falling to 0.63 CPU-seconds (\~11x) when vtprotobuf's generated memory pooling is also used; the post gives no hardware, Go version, or compiler flags, and the repo ships no benchmark code to reproduce the numbers.

## Use it when

- Go services already on google.golang.org/protobuf (APIv2) with (de)serialization visible as CPU cost in profiles (RPC hot paths, replication/streaming row processing).
- gRPC, DRPC, or Twirp services that can install vtprotobuf's provided codec so all messages benefit without touching call sites.
- Teams that can explicitly opt into memory pooling per message type and manage single-owner reuse lifetime carefully, where most of the &gt;10x gain reported by the author lives.
- Want reflection-free CloneVT/EqualVT/SizeVT even without wiring the whole RPC path.
- Comfortable checking in generated \*_vtproto.pb.go files as part of the normal protoc build step.

## Skip it when

- Still generating APIv1/gogo code: vtprotobuf targets APIv2 only and is explicitly not compatible with APIv1-generated code per the README.
- Can't tolerate unsafe byte aliasing: UnmarshalVTUnsafe pins the entire input buffer alive via GC for the life of any string/bytes field taken from the message (open issue #167), which can silently balloon retained memory if a field is cached long-term.
- Messages are small or short-lived: the author's own post notes many protobuf messages are too small for pooling to help, and the \~1.7x codegen-only gain (no pooling) is the realistic floor.
- Need pooling correctness for repeated fields, maps, or nested messages: multiple open issues report pooled ResetVT/ReturnToVTPool bugs with repeated fields (#92) and note pooling only reaches the outer message, not nested children (#162, 'Recursive Pool Usage').
- Want a single drop-in replacement for proto.Marshal/Unmarshal with zero call-site changes and no RPC codec registration step.

## How it is fast

All (de)serialization logic is fully unrolled per-field at codegen time (ported from gogo/protobuf's approach to the APIv2 API), so there is no reflection walk over the message descriptor at runtime. SizeVT precomputes the exact encoded size so MarshalVT allocates its output buffer once. UnmarshalVTUnsafe casts wire bytes directly into string/[]byte fields instead of copying them. The optional generated sync.Pool-backed object pools (ResetVT/ReturnToVTPool/FromVTPool) let callers reuse whole message structs across unmarshal calls, avoiding allocation entirely, which is where most of the reported speedup comes from.

## Compared with alternatives

The catalogued siblings (RapidProto, Zserio, FlatBuffers) are all C++ alternatives to protoc's C++ output; pick vtprotobuf instead whenever the stack is Go on google.golang.org/protobuf APIv2, since it optimizes protoc's existing Go codegen and wire format rather than replacing either.

## Gotchas

- UnmarshalVTUnsafe keeps the whole input wire buffer alive via GC for as long as any string/bytes field from the message is reachable (unsafe.String aliasing); documented as an open gap in issue #167, not yet in the README.
- UnmarshalVT on a non-zeroed message behaves like proto.Merge rather than a fresh Unmarshal; call Reset() first or use a freshly allocated message.
- Memory pooling is opt-in per message (`option (vtproto.mempool)` or `--go-vtproto_opt=pool=...`) and, as of issue #162, only pools the outer message — nested/child messages are still freshly allocated on each unmarshal.
- Returning a pooled repeated-field message has open correctness bugs (issue #92, generated ResetVT); verify pool behavior with your own message shapes before relying on it in production.

## Caveats and trade-offs

The numbers come from the author's own 2021 announcement post on the Vitess blog. They are a single workload-specific profile (VReplication row streaming) with no hardware, Go version, or linked benchmark code, and the repo contains no benchmark directory. The \~11x figure depends on memory pooling, where the application reuses Response objects, and is not a pure codegen win. The pure codegen gain is \~1.7x. Upstream google.golang.org/protobuf may have narrowed the gap since 2021.

Generates auxiliary \*_vtproto.pb.go helpers that must be explicitly opted into (SizeVT/MarshalVT/UnmarshalVT etc.) rather than replacing standard methods; the 'unsafe' unmarshal variant aliases input bytes into strings, requiring the caller to keep the wire buffer alive; adds a build-time dependency on the vtproto plugin

## Verdict

The README reports 1777.24 MB/s (about 3.58M messages/s) for llhttp against 694.66 MB/s (1.41M req/s) for http_parser, each single-threaded, re-parsing http_parser's \~518-byte chunked POST fixture until 8 GiB had been consumed: about 2.56x. No CPU, compiler, OS or date is given. The llhttp side ran in llparse-test-fixture with -msse4.2 and the http_parser side in its own bench.c at -O3, so the ratio crosses two harnesses and two runs.

## Use it when

- Event-loop servers, clients or proxies in C or C++ that receive HTTP/1.x in arbitrary TCP fragments and need a resumable parser that keeps its state in a small caller-owned struct and never allocates.
- Migrating off nodejs/http-parser: the callback model is the same, and llhttp is the maintained successor that Node.js ships.
- Code that must parse both requests and responses, chunked bodies, CONNECT and Upgrade, with strict defaults against request smuggling plus per-check lenient switches.
- x86-64 builds compiled with SSE4.2 enabled, aarch64 (NEON), or WebAssembly with simd128, where the vectorized span scan is active.
- Projects in Lua, Python, Ruby or Rust, through the bindings the README lists.

## Skip it when

- When the whole header block is already in one buffer and you only need slices for method, path and headers: callback-free parsers may be faster and simpler. Among the catalogued siblings, iohttpparser's own summary beats llhttp in 16 of 22 scenarios and milo reports about 1.07x.
- HTTP/2 or HTTP/3: llhttp parses HTTP/1.x framing only.
- Interoperating with non-compliant peers: that needs lenient flags, and the README warns that most of them expose you to request smuggling or cache poisoning.
- When you need to change the grammar without a Node.js toolchain: the C is generated (about 10,000 lines of goto-based code in llhttp.c) and edits belong in the TypeScript source, which is regenerated through llparse.
- Generic x86-64 builds without SSE4.2 (the repo Makefile's -Os, or a plain CMake build): the vectorized span scan is compiled out and each byte goes through a lookup table.

## How it is fast

The grammar is written as a TypeScript graph of states (about 1,400 lines) and compiled by llparse into one large C function in which each state is a label and transitions are gotos. Character classes become 256-entry lookup tables, and fixed strings such as method and header names go through a sequence matcher. Long spans such as header values and the URL are scanned 16 bytes at a time with SSE4.2 PCMPESTRI range compares, NEON or wasm simd128. Callbacks fire once per span instead of once per byte, and the parser never allocates. The generated code replaces http_parser's hand-unrolled C and is no harder to maintain when features are added.

## Compared with alternatives

Pick llhttp over iohttpparser, milo or the picohttpparser family when you need an incremental parser that handles both requests and responses and is maintained with Node.js's security process, rather than the fastest parse of a complete header block. Those siblings report wins over llhttp (iohttpparser in 16 of 22 scenarios, milo about 1.07x) on their own first-party benchmarks.

| **Drop-in for the baseline** | partial — same callback-driven design as http_parser, but different types and functions (llhttp_t, llhttp_settings_t, llhttp_execute returning llhttp_errno_t with llhttp_get_error_pos instead of a parsed-byte count), explicit pause/resume and stricter default validation, so call sites need porting |

## Gotchas

- Harness flaw behind the 2.56x: the README table joins two different harnesses. The llhttp rows were printed as 'ops/sec' by llparse-test-fixture's bench mode (visible in the v1.0.1 and v2.0.0 READMEs), which parses the complete \~520-byte message back-to-back on one parser with no-op callbacks called directly, built with -msse4.2 (today's fixture also adds -g3 -Os). The http_parser row is the 'req/sec' line from http_parser's bench.c, built -O3 with HTTP_PARSER_STRICT=0 (loose). bench.c dispatches through function-pointer callbacks, re-initializes the parser every iteration and feeds a 518-byte request missing the final CRLF, so its message never completes. That row has not changed since v1.0.1, while the llhttp row moved from 1497.88 to 1777.24 MB/s at v2.0.0. The comparison is therefore not one same-machine, same-harness run, and flags differ in both directions (O3 favours http_parser, SSE4.2 favours llhttp).
- The x86 SIMD path depends on compile flags: the PCMPESTRI span scan exists only under __SSE4_2__, so builds without -msse4.2 or an -march that implies it (including the repo Makefile's -Os -g3) skip it, although the benchmark binary had it. On aarch64 the NEON path is on by default.
- Errors are sticky: after a non-pause error, llhttp_execute returns the same error until llhttp_init or llhttp_reset. After HPE_PAUSED or HPE_PAUSED_UPGRADE you must resume from llhttp_get_error_pos. Span callbacks can fire several times per field when input arrives in fragments, so accumulate spans yourself.
- Smuggling history: CVE-2021-22959, CVE-2022-32213 and CVE-2022-32214 were fixed through Node.js releases (SECURITY.md says the repo usually issues no CVEs of its own). Reports #876 (trailing HTAB in a response Transfer-Encoding) and #877 (bare LF accepted as a request-line terminator in strict mode) were opened 2026-08-23 with fixes proposed in PRs, but both issues are still open, so track releases. Separately, bench/wasm.ts frees the input buffer twice (llhttp.free(ptr) and then llhttp.llhttp_free(ptr)), never frees the parser and ignores llhttp_execute's return value; this does not affect the README numbers, which come from the native run.

## Known shortcomings

- Tier C: README table (2.56x vs http_parser, derived from page data) with no CPU, compiler or flags; the http_parser row is unchanged since v1.0.1 and never re-run while the llhttp row was re-measured at v2.0.0 (likely mixed runs); the current bench/native.ts times llhttp only; workload is the 518-byte chunked POST from http_parser's bench.c repeated to 8 GiB. llhttp is itself the spec's http-parsers baseline.
- Enricher: the 2.56x joins two harnesses: llhttp rows print 'ops/sec' from llparse-test-fixture (-msse4.2, direct no-op callbacks, complete message) while the http_parser row prints 'req/sec' from bench.c (-O3, loose mode, function-pointer callbacks, request missing the final CRLF, parser reinitialised each iteration), with the baseline row unchanged since v1.0.1. The SSE4.2 span scan compiles only under __SSE4_2__ and the repo Makefile's -Os build skips it. Open smuggling reports #876/#877 (2026-08-23) with fixes proposed but issues open; bench/wasm.ts frees the input buffer twice, never frees the parser and ignores the return value (not behind the README numbers).

## Caveats and trade-offs

First-party README numbers only: no CPU, compiler or flags, and the table is undated. The http_parser row (694.66 mb/s, 1406180.33 req/sec, 11.79 s) is identical to two decimals in the v1.0.1 README and has never been re-measured. The llhttp row was raised from 1497.88 to 1777.24 mb/s at v2.0.0, whose release notes credit an llparse bump with 20-28% more speed. The headline 2.56x therefore probably pairs a newer llhttp run with an older baseline run, and same machine and session are not shown. The current bench/native.ts and bench/wasm.ts time llhttp only (the http_parser side lives in http_parser's own bench.c, which the table's output format matches), so the comparison is not reproducible from llhttp's tree. The Makefile builds the library with clang -Os -g3, so the benchmark flags are unknown. llhttp is itself a named baseline of the http-parsers category, and this record is its win over its predecessor http_parser (also a named baseline). A single hot-cache request, repeated, measures small-message parsing speed, not mixed traffic. No independent comparison was found (one WebSearch; the Node.js blog and author posts are egress-blocked). [retier] README table mixes harnesses and runs: llhttp 'ops/sec' from llparse-test-fixture (-msse4.2, direct no-op callbacks, complete message, re-measured at v2.0.0) vs http_parser 'req/sec' from bench.c (-O3, loose mode, function-pointer callbacks, missing final CRLF, reinit per iteration, unchanged since v1.0.1); no CPU, compiler or flags. SSE4.2 span scan needs __SSE4_2__ (the Makefile -Os build omits it). Open request-smuggling reports #876/#877. llhttp is itself the spec's http-parsers baseline.

Parser is generated from a TypeScript state-machine description by llparse and shipped as C (llhttp.c plus about 450 lines of C helpers); ABI/API differs from http_parser (callbacks and llhttp_t instead of http_parser_settings); strict and lenient flag modes exist.

## Maintenance

Actively maintained under the Node.js org (9.4.3 released 2026-07-30; a header-value scanner performance fix merged 2026-10-01) and MIT-licensed. Use the generated C from the release branch or release tarballs so only a C compiler is needed, and take security fixes from Node.js security releases.

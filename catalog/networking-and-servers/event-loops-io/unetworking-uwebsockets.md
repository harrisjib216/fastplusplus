## Verdict

In a Feb 2021 blog post, the author ran the uWS HelloWorldThreaded example on a fanless 4-core Raspberry Pi 4 (Ubuntu 20.10 ARM64, overclocked to 1.75 GHz), loaded over Ethernet from a laptop by uSockets' http_load_test with 200 non-pipelined connections. It served 106k req/s (93k at stock clock, 77k with TLS 1.3) against 8.8k for Node.js/Fastify run as a cluster (12x); uWebSockets.js reached 75k. This is a single first-party run: Node/Fastify versions and code are not published, and compiler flags are not stated (today's build.c uses -O3 -march=native -flto).

## Use it when

- C++ services that hold many HTTP/1.1 or WebSocket connections with small messages (trading feeds, games, chat, notifications), where server I/O plumbing, not a database, is the bottleneck.
- Replacing a Node.js HTTP/WebSocket tier. In the author's Raspberry Pi test, uWebSockets.js inside Node reached 75k req/s against 8.8k for clustered Fastify, so you can keep JavaScript if you cannot move to C++.
- WebSocket fan-out with built-in topic pub/sub, where per-socket maxBackpressure drops sends to slow subscribers automatically. On the author's 1-core echo chart, v20.42.0 beats Deno's fastwebsockets v0.4.2 by roughly 1.2x from 512 B to 16 kB messages (derived from bar heights).
- In-process TLS 1.3 termination on small hardware. The blog measured 77k req/s with TLS against 106k cleartext. The author's own docs quote TLS retention anywhere from about 60% to about 80%.
- Cross-platform deployment: epoll on Linux, kqueue on macOS/FreeBSD and libuv on Windows, all behind one API.

## Skip it when

- Clients or proxies that speak HTTP/1.0 upstream. The parser accepts only 'HTTP/1.1' request lines, and the maintainer declined 1.0 support (issue #1547, whose reporter hit it behind nginx). There is no HTTP/2, and HTTP/3/QUIC is work in progress.
- General-purpose event-loop work (custom protocols, heavy outbound clients). uWS is server-first, and its C++ WebSocket client (src/ClientApp.h) is a 35-line minimal header. For that work, use uSockets directly or a general event library.
- Designs where many threads share sockets. Sockets must never be touched off their loop's thread, and only Loop::defer is thread-safe.
- Production use of the io_uring backend. The maintainer calls it 'extremely experimental and only for dev', and open issue #1931 reports WebSocket messages above about 2 KB silently dropped on io_uring while epoll works.
- Projects that need clean licensing without legal review. The README reserves all rights except for files with an explicit Apache-2.0 notice, and several headers (ClientApp.h, Http3\*.h, LocalCluster.h) have none.

## How it is fast

Shared-nothing, thread-per-core event loops run on raw epoll or kqueue (uSockets, up to 1024 ready events per wait). Each loop has one 512 KB receive buffer shared by all its sockets instead of per-socket buffers. The HTTP parser is zero-copy (string_views into that buffer) and scans 8 bytes per step with the SWAR 'hasLess(x, n)' bit trick. It writes a '\r' sentinel past the end of the data so the hot loops need no bounds checks, and a 256-bit Bloom filter answers most getHeader misses. Responses are 'corked' into a 16 KB per-loop buffer, so status, headers and body leave in one send() and one TLS record. Idle timeouts use a coarse 4-second sweep instead of per-socket timers.

## Compared with alternatives

Pick uWS when you need a finished HTTP/1.1 + WebSocket server in C++ (routing, pub/sub, TLS, backpressure). The libhv and PhotonLibOS entries are general event-loop/runtime layers measured on ping-pong against libevent/libuv and boost::asio, so pick them for custom protocols. Their 1.05-1.4x gains are not comparable to uWS's 12x, which is measured against a JavaScript HTTP stack, not another native event loop.

## Integration

| | |
|---|---|
| **Form** | header-only (uWS) + static lib (uSockets, a C git submodule you must compile) |
| **Dependencies** | uSockets (bundled submodule); zlib unless UWS_NO_ZLIB; OpenSSL, WolfSSL or BoringSSL for TLS (LIBUS_NO_SSL disables it); optional libuv, ASIO, GCD or liburing event backends; optional libdeflate (UWS_USE_LIBDEFLATE) and simdutf (UWS_USE_SIMDUTF); lsquic + BoringSSL for experimental HTTP/3 |
| **Minimum toolchain** | C++17 for the library headers (per the user manual). Examples build with -std=c++2b -O3 -march=native -flto via build.c. uSockets is C11. No minimum compiler version is documented. |
| **Platforms** | Linux (epoll by default, io_uring experimental), macOS and FreeBSD (kqueue), Windows (libuv). Portable C/C++ with no ISA requirement; the benchmark ran on ARM64. |
| **Thread safety** | Not thread-safe. Use one App and event loop per thread; a socket created on one thread cannot be used from another. The only thread-safe call is Loop::defer, which queues a callback onto another loop through a mutex-protected queue. |
| **Drop-in for the baseline** | no |

## Gotchas

- If a handler returns without calling res-&gt;end() and without registering res-&gt;onAborted(), uWS calls std::terminate. HttpRequest is stack-allocated and valid only during the handler, so copy what you need before going async.
- Automatic corking applies only inside uWS callbacks. Sends from third-party library callbacks or later async code are uncorked, so wrap them in res-&gt;cork(...) or pay for several syscalls and TLS records. Only one socket per thread can be corked at a time.
- Hard request limits: 4096 bytes of headers (the UWS_HTTP_MAX_HEADERS_SIZE environment variable) and 100 headers (the UWS_HTTP_MAX_HEADERS_COUNT macro); larger requests get 400. Timeouts are only accurate to about 4 seconds.
- The benchmarked multi-core example uses LocalCluster.h, which calls itself 'highly experimental' and defines non-inline globals in a header. Open issue #1863 reports an ASAN double-free of WebSocket UserData when ending sockets from the server side during shutdown.

## Known shortcomings

- The 12x figure is the author's 2021 blog (uWS 106k vs Fastify cluster 8.8k req/s on an overclocked Raspberry Pi 4) with no compiler, flags or Fastify versions; the repo's own older chart shows about 6x. Apache-2.0 notices are missing from some source files and one file is third-party MIT.
- No HTTP/1.0 (declined, #1547) or HTTP/2; HTTP/3 is WIP. The io_uring backend is dev-only and drops WebSocket messages over \~2 KB (#1931, open); an ASan double-free on shutdown is open (#1863). The benchmarked threaded example uses the 'highly experimental' LocalCluster.h. Returning from a handler without end() or onAborted() calls std::terminate. 4 KB header limit by default.

## Caveats and trade-offs

The 12x figure is 106k vs 8.8k req/s from a single first-party run in the uWS author's own blog post (Alex Hultman, Level Up Coding, 2021-02-03), on an overclocked Raspberry Pi 4. Node.js and Fastify versions and the Fastify server code are not published, and compiler/flags are not stated. The workload is a hello-world HTTP server comparison, not an event-loop microbenchmark. The original levelup.gitconnected.com URL returns HTTP 403 to bots; the Wayback snapshot 20220510081241 is readable. The repo's older benchmarks/README.md chart (uWS v0.15 vs Node.js 10.13, CPU-time normalized) shows a smaller gap: about 6x (derived from page data, bar heights read approximately as \~180k vs \~28k req/s). Licensing: the README says 'Intellectual property, all rights reserved' and that Apache-2.0 applies only where an explicit notice is given. src/ClientApp.h, src/Http3\*.h and src/LocalCluster.h carry no license header, and src/MoveOnlyFunction.h is third-party MIT.

uSockets (the underlying eventing layer) supports five event-loop backends including libuv, ASIO, GCD and raw epoll/kqueue, so libuv is also an optional backend, not just a competitor; header-only C++17 built on a C core

## Maintenance

Actively maintained (v20.80.0 released 2026-09-03, last commit 2026-09-18) and fuzzed in OSS-Fuzz (18 OSV records from 2020-08 to 2021-12, all marked fixed), but usability is 'mixed' because the README reserves all rights except for files that carry an explicit Apache-2.0 notice.

## Verdict

In the-benchmarker/web-frameworks develop-branch run of 2026-09-24 (zrk closed-loop keep-alive, empty-body GET /, 15 s at 64/256/512 connections, server pinned to 4 cores of a 16-CPU x86-64 Linux 7.2 host of unknown CPU model), Drogon 1.9.13 (CMake Release, C++17, Debian trixie GCC 14) served 126K-135K req/s. Go net/http from the golang:1.27 image (labelled 1.22 in the data) served 67K-71K req/s, so Drogon was 1.77-2.00x faster; the master-branch run with the older zrk ramp method shows only about 1.2x.

## Use it when

- High-request-rate HTTP/1.1 REST/JSON APIs written in C++ where per-request framework overhead matters: 126K-135K req/s for an empty GET on 4 pinned cores, about 1.8-2x Go net/http in the same run.
- Many concurrent keep-alive or pipelined clients on Linux, where every IO thread has its own SO_REUSEPORT listener and epoll loop.
- Services that want async PostgreSQL/MySQL/SQLite/Redis access, an ORM, sessions and WebSocket in one framework; FastDbClient runs DB IO on the HTTP threads to avoid thread hops.
- C++20 codebases that want coroutine handlers (co_await on DB and HTTP-client calls) instead of nested callbacks.
- Cross-platform builds (Linux, macOS, BSD, Windows, ARM); CI covers GCC 9-13, Clang 11-17, MSVC on Windows 2022 and macOS 14/15.

## Skip it when

- You need an HTTP/2 or HTTP/3 server: master speaks HTTP/1.0/1.1 only, and HTTP/2 exists only as a beta client (v1.10.0-beta.3).
- Tail latency at modest concurrency matters more than peak req/s: in the same run Drogon's p99 at 64 connections was 9.8 ms, against 3.05 ms for net/http and 1.13 ms for Oat++, even though its median was 0.12 ms.
- Handlers must call blocking libraries (sync DB drivers, sync HTTP clients, long CPU work): each loop is single-threaded, so you have to offload that work or rewrite it with async callbacks or coroutines.
- Static-file serving or generated ORM RESTful controllers exposed to untrusted input without review: as of 2026-09-26 there are open reports of a %00 path-truncation bypass of the static-file extension allowlist (#2591; fix PR #2600 not merged) and of SQL injection via Mapper::orderBy() and the Criteria JSON constructor (#2575, #2576).
- HTTP framing is not your bottleneck: the 2x is for an empty-body hello-world, the older-method master-branch run showed only about 1.2x, and header access copies into std::string maps (issue #2535).

## How it is fast

It runs on trantor, a muduo-style one-event-loop-per-thread reactor: each IO thread owns an epoll (kqueue on macOS/BSD) loop, and on Linux each thread gets its own SO_REUSEPORT listening socket, so the kernel spreads accepts with no shared acceptor; cross-thread work is handed over through a lock-free task queue. Requests are parsed by a hand-written incremental HTTP/1.x state machine (CRLF scanning over a MsgBuffer) that drains every pipelined request from one read, and HttpRequestImpl objects are recycled per connection through a shared_ptr custom deleter. Exact-path routes are a hash-map lookup, and responses marked setExpiredTime(0) are rendered once and reused, with only the Date bytes patched once per second.

## Compared with alternatives

Pick Drogon over Oat++ when you want built-in async DB/Redis clients, an ORM and more hello-world throughput (1.09-1.34x Oat++ in the same run), but note that Oat++ had much tighter p99 there. CWIST (C) was 15-18% faster than Drogon in that run, and the Crow and Lwan figures come from TechEmpower rather than this suite, so choose Drogon for its feature set plus competitive speed, not as the fastest server listed.

## Gotchas

- The benchmarked GET / never reaches the router: a registerSyncAdvice hook returns it before routing, filters and middleware run, and the config disables the Date and Server headers. A normal HttpController route does more work per request.
- setThreadNum defaults to 1 IO thread, and 0 means std::thread::hardware_concurrency(). Set it explicitly, especially in CPU-limited containers (the benchmark used 0).
- Paths are lowercased and matched case-insensitively. When the exact-path hash lookup misses, routes with {param} placeholders are found by a linear scan with std::regex_match over all regex routes, so cost grows with the number of parameterized routes.
- Never block in a handler or DB callback: sleep or sync IO stalls every connection on that loop, and sync queries on a FastDbClient, which shares the HTTP IO threads, deadlock (threading FAQ, issue #1068).

## Known shortcomings

- The 1.8-2.0x over Go net/http is from the-benchmarker's develop-branch data (2026-09-24); the master data with the older method shows only about 1.2x. The suite's CPU label is garbled, and the server is pinned to 4 cores.
- The benchmark's GET / is answered by a registerSyncAdvice hook before routing, filters and middleware, with Date and Server headers disabled: a best case, not a normal route. p99 at 64 connections 9.8 ms vs 3.05 ms for net/http. Open security reports: %00 in the path bypasses the static-file extension allowlist (#2591, fix PR #2600 unmerged); SQL injection via Mapper::orderBy() and the Criteria JSON constructor (#2575, #2576). No HTTP/2 server. Install docs say gcc 5.4 but C++17 with std::filesystem is required. Default is 1 IO thread; {param} routes are matched by a linear std::regex scan.
- Enricher on the an-tao/drogon nginx claim: the nginx hello_world module and config were never published and the Chinese wiki admits nginx may have been misconfigured; Drogon's numbers measure a cached response (setExpiredTime(0) caches forever, the controller runs once, only Date bytes are patched); the -t 12 row and nginx 31/49 (max below min) are inconsistent; 2018 run on gcc 7.3, which cannot build current Drogon. Two third-party runs put nginx ahead: cinatra's doc (nginx 239,629 vs Drogon 216,982 req/s, config published) and gonwan/webframework-benchmark (nginx 1.28.2 336k/s vs Drogon 1.8.7 320k/s).

## Caveats and trade-offs

Numbers come from the develop-branch data.json of 2026-09-24 (the zrk --closed keep-alive method adopted in September 2026). data.json is overwritten on every run, and the suite says runs from different benchmark revisions are not comparable. The master-branch data.json (2026-09-20, earlier zrk ramp method) shows a smaller gap: Drogon 120,197 / 101,786 / 101,282 vs nethttp 96,149 / 85,406 / 83,964 req/s (about 1.2x). Hello-world endpoint only, server pinned to 4 cores; the CPU label in data.json is garbled. A separate single-author benchmark (gonwan/webframework-benchmark, 0 stars, AMD 7840HS host, wrk with keep-alive) shows Drogon 1.8.7 at 320k/s vs Boost.Beast 1.83 at 220k/s, with nginx at 336k/s.

Full-featured framework (ORM, views, sessions, plugins) adds binary size/complexity vs a bare net/http server; still well behind actix-web (163K-179K req/s) in the same suite.

## Maintenance

Actively maintained (v1.9.13 released 2026-05-06, commits through 2026-09-16, 14.3k stars, 441 open issues and PRs) and MIT-licensed. It installs via CMake add_subdirectory or Conan, but it is a sizable library with trantor/jsoncpp/uuid/zlib dependencies, not something to vendor as a few files.

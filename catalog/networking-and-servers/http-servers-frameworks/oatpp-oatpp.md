## Verdict

In the-benchmarker/web-frameworks develop-branch run of 2026-09-24 (commit f673364), oatpp 1.3.1's Simple API served an empty GET / at 115.7K / 101.0K / 98.2K req/s over 64 / 256 / 512 keep-alive connections, against Go net/http ServeMux (labelled 1.22, built in the golang:1.27 image) at 71.5K / 67.4K / 67.2K, i.e. 1.62x / 1.50x / 1.46x. Both servers were CPU-bound on 4 pinned cores of a 16-CPU x86_64 host whose CPU model is garbled in the metadata; oatpp was built C++11, CMake Release, with Debian trixie's GCC (14.2 implied). The earlier master-branch run showed only 1.16-1.21x.

## Use it when

- C++ REST/JSON services that want declarative endpoints, DTO mapping and Swagger docs without third-party libraries: the core links only the thread library (plus libatomic on Linux, ws2_32 on Windows).
- Embedded, IoT and robotics targets, which the README names as its main use: a minimal app is about 1 MB, and known builds include OpenWRT boards with 64-128 MB RAM, Nvidia Jetson, Android and iOS.
- Tens to a few hundred keep-alive connections on a few cores. In that range the Simple API measured 1.46-1.62x Go net/http req/s with lower p50 and p99 latency (p99 1.1 ms vs 3.1 ms at 64 connections, 9.4 ms vs 15.5 ms at 512).
- Thousands of long-lived connections (WebSocket fan-out, streaming, 1K+ concurrent downloads) through the Async API, the case the README reserves it for. The project demoed 5 million WebSockets on one 16-vCPU server with 0.19.4 in 2019, with no baseline.
- Codebases stuck on C++11/14: the 1.3.x line builds as C++11 with CMake 3.1.

## Skip it when

- Very high connection counts on the Simple API. It is thread-per-connection: throughput fell 15% from 64 to 512 connections, and p99.999 latency (the suite's percentile99999 field) hit about 643 ms at 512, where Go had about 35 ms, in the same run.
- Maximum raw HTTP throughput: in the same 4-core run Drogon (126-135K req/s) and CWIST (149-155K) beat oatpp (98-116K).
- Anything that needs HTTP/2 or HTTP/3. HTTP/2 has been requested since 2019 (issue #116, still open) and is not supported.
- Parsing untrusted, deeply nested JSON on the 1.4.0-dev master branch. Fuzzing found a recursion stack overflow in the new json::Deserializer (#1037, open; a commenter says 1.3.1 is not affected), and several out-of-bounds reports against DTO mapping filed in August 2026 (#1094-#1104) have no maintainer reply.
- Teams that need a fast-moving upstream: the last release is 1.3.1 (December 2024), 1.4.0 has been 'in development' since then, and the last commit was 2025-11-12.

## How it is fast

The benchmarked app uses the Simple API: HttpConnectionHandler spawns one detached std::thread per accepted connection with blocking sockets, and that thread loops read-parse-route-respond for as long as keep-alive holds, with no event loop or cross-thread handoff per request. The header reader peeks into a reused per-connection buffer, finds the end of headers with a rolling 32-bit CRLFCRLF accumulator, and parses the start line and headers into zero-copy StringKeyLabel slices; routing is a per-method hash map followed by a linear pattern scan, and response headers go through a reused 2 KB-initial buffer. The Async API instead runs stackless coroutines (each act() returns an Action) on processor workers and parks I/O waits in edge-triggered, one-shot epoll or kqueue workers. The benchmark does not isolate why it beats Go (for example GC or scheduler cost); that is not documented.

## Compared with alternatives

Drogon and CWIST posted 10-50% more req/s than oatpp in the same run, and Drogon stayed flatter as connections rose. Pick oatpp when a zero-dependency, C++11-capable build, a small footprint for embedded targets, or its built-in DTO/Swagger/ORM codegen matters more than peak throughput; at 64 connections it also had the lowest p99 of the three (1.1 ms vs Drogon 9.8 ms and CWIST 8.6 ms).

| **Thread safety** | Not documented for user code. The Simple API runs each connection on its own detached std::thread, so endpoints run concurrently and shared controller/service state must be synchronized by you. | **Drop-in for the baseline** | no |

## Gotchas

- Request headers are capped at 4096 bytes in total by default (HttpProcessor::Config::headersReaderMaxSize). In 1.3.1, exceeding the cap makes the reader return -1 and the connection is dropped silently, with no 431 response.
- An unmatched route (404) or any exception thrown from an endpoint or interceptor sets the connection to CLOSING, so every error response costs the client its keep-alive connection.
- The Simple API pins every connection thread to CPUs 0..N-2 (N = std::thread::hardware_concurrency()), deliberately leaving one CPU free. To change this, set OATPP_THREAD_HARDWARE_CONCURRENCY or OATPP_COMPAT_BUILD_NO_SET_AFFINITY at build time. Thread stack size cannot be configured (issue #589, open).
- Master (1.4.0-dev) breaks the 1.3 API: it requires C++17, moves headers (oatpp/core/\* to oatpp/\*, parser/json to json) and renames OATPP_LOGD to OATPP_LOGd with {} formatting; the README says to use the 1.3.0-latest tag for now. Per-object counters also stay on in Release builds unless you pass -DOATPP_DISABLE_ENV_OBJECT_COUNTERS=ON, which the benchmark build did not.

## Known shortcomings

- The 1.46-1.62x over Go net/http is from the-benchmarker's develop-branch data; the '5 Million WebSockets' page names no baseline.
- The benchmark uses the Simple API HttpConnectionHandler (one detached thread per connection, blocking I/O), not the async server. p99.999 at c=512 is \~643 ms vs \~35 ms for net/http. Request headers over 4096 bytes close the connection with no response (1.3.1). A 404 or endpoint exception closes keep-alive. Workers pinned to CPUs 0..N-2; object counters stay on in Release. No HTTP/2 (#116). Unanswered out-of-bounds reports on DTO mapping (#1094-#1104); heap overflow #1007 fixed only on master. No release since 1.3.1 (2024-12); last commit 2025-11. oatpp.io/benchmark returns HTTP 500.

## Caveats and trade-offs

Numbers come from the develop-branch data.json of 2026-09-24 (the zrk --closed keep-alive method adopted in September 2026). data.json is overwritten on every run, and the suite says runs from different benchmark revisions are not comparable. The master-branch data.json (2026-09-20, earlier zrk ramp method) shows a smaller gap: oatpp 116,452 / 100,950 / 97,773 vs nethttp 96,149 / 85,406 / 83,964 req/s (about 1.16x-1.21x). Hello-world endpoint only, server pinned to 4 cores; the CPU label in data.json is garbled. oatpp's own '5 Million WebSockets' benchmark (oatpp 0.19.4, May 2019) names no baseline, so it does not qualify on its own.

Throughput degrades somewhat as concurrency rises (115.7K at c=64 down to 98.2K at c=512), unlike Go/Drogon which stay flatter; zero-dependency design trades some convenience features for portability.

## Maintenance

Active but slow-moving: Apache-2.0, 8.7k stars, last release 1.3.1 (Dec 2024), master (1.4.0-dev) last committed 2025-11-12, which makes it stale after 2026-11-12. Pin the 1.3.1 tag as the benchmark did.

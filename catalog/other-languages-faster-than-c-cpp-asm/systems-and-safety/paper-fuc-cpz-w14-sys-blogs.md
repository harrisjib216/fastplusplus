## Verdict

These are first-party hyperfine runs from March 2023 (--warmup 3, warm page cache) on an Intel i7-7700 with 15 GiB RAM, a RHEL 9 5.14 kernel and /tmp on XFS over SATA. Copying ftzz-generated trees, cpz took 5.076 s against 18.436 s for the distro GNU cp -r with 1M empty files (3.63x), 7.593 s against 28.173 s with 1M files totalling 1 GiB (3.71x) and 0.379 s against 1.632 s with 100,000 empty files (4.30x). The single-threaded Rust cp_stdlib matched cp -r, and in a flat directory cpz led cp -r by only 1.19x and trailed xcp.

## Use it when

- Duplicating nested trees of many small files on a local Linux filesystem (10,000 to 1M files): 3.4-4.8x faster than cp -r in the author's tables (for example 0.379 s vs 1.632 s for 100,000 empty files).
- Scratch, build-output, test-fixture or dataset copies where mode bits are enough and timestamps, ownership and xattrs need not be preserved.
- Machines with idle cores: the wall-clock win comes from running up to available_parallelism threads, at the cost of more total CPU.
- Building hard-link farms of a tree with -l (supported since May 2025, issue #46).

## Skip it when

- One huge flat directory: work is split per directory, so a single directory is copied by one thread (flat 100,000-file row: user+system 1.338 s for 1.365 s wall, derived from page data); there cpz is only 1.19x faster than cp -r and loses to the Rust xcp (1.133 s vs 1.365 s at 0 B; 1.209 s vs 2.080 s at 1 GiB).
- Backups or migrations that need cp -a/-p semantics: no timestamps, ownership, xattrs or ACLs, and sparse files are not handled (issue #37 open since 2024; the maintainer will not implement it himself but would accept a PR).
- Trees with read-only directories copied as a non-root user: the destination directory is created with the source mode before its contents, so writing into it fails; the author's own commit message (11d5469) says a final chmod would be needed 'but whatever'.
- Docker containers with the default seccomp profile, which blocks unshare: cpz fails with 'failed to unshare' unless the undocumented NO_UNSHARE environment variable is set (issue #34).
- Shared or busy machines and network mounts: at 1M files cpz used 26.48 s user+system against 18.10 s for cp -r (derived from page data), and a copy to an sshfs mount never finished (issue #26, closed for inactivity without a fix).

## How it is fast

On Linux each directory is a task on an unbounded crossbeam channel; a root worker plus lazily spawned workers (up to available_parallelism) read entries with raw getdents64 (rustix RawDir, 32 KiB stack buffer), use d_type to skip stat calls, create entries with fd-relative openat/mkdirat, and move file data with copy_file_range. Each worker thread unshares its file-descriptor table (unshare CLONE_FILES), which the author says speeds up directory processing (issue #34). The gain is parallelism, not Rust codegen: the single-threaded Rust cp_stdlib in the same tables is as slow as GNU cp (19.496 s vs 18.436 s at 1M files), and its scheduler puts cpz 15-30% ahead of a plain rayon version on most nested trees (cp_rayon wins at 5 files per directory with 1 GiB: 0.733 s vs 0.775 s).

## Compared with alternatives

Pick cpz when the job is duplicating a nested small-file tree on Linux; rmz is the deletion counterpart built on the same engine, and dumac and cligen/dents only walk trees (du, find, ls) rather than copy them.

## Gotchas

- Harness: the '1 GiB' rows do not measure data copying. In the 10-file 1 GiB row cpz takes 1.3 ms and cp -r 1.9 ms while the tar pipe needs 304.3 ms and rsync 1042.4 ms, so on this XFS cp, cpz and the Rust tools cloned extents rather than copying bytes (derived from page data). Every table is therefore a warm-cache metadata benchmark on one SATA partition with no sync, and says nothing about byte-copy throughput on ext4, across devices or over the network.
- Mode bits: prep_regular_file passes the full source st_mode, including set-user-ID and set-group-ID bits, to openat(O_CREAT), and directories get their source mode via mkdirat. The GNU cp manual says new files are created with the source mode minus the set-user-ID, set-group-ID and sticky bits unless attributes are preserved. Issue #52, a private report about 'preserving privileged mode bits', was closed on 2026-06-21 with links only to two directory-mode commits (from code reading; avoid running cpz as root on untrusted trees).
- Only EXDEV from copy_file_range triggers the read/write fallback. Any other error aborts the copy; an earlier EINVAL on a 4.14 kernel needed a length fix (issue #31). Holes in sparse files are not preserved.
- Destination semantics differ from cp: without a trailing slash DST is the copy itself, so an existing DST is an error unless -f, and -f merges the source's contents into it.

## Known shortcomings

- rustc version, GNU cp version and build flags unstated; the gain is multithreading (the single-thread cp_stdlib matches cp) and Rust xcp beats cpz in flat directories; about 1.46x total CPU; numbers from March 2023; wcp is in the run script without a results row.
- The '1 GiB' rows never copy bytes: in the 10-file 1 GiB row cpz takes 1.3 ms and cp -r 1.9 ms while the tar pipe needs 304.3 ms and rsync 1042.4 ms, so on this XFS the copies cloned extents (derived from page data) and every table is a warm-cache metadata benchmark. Work is split per directory, so one flat directory means one thread and xcp wins there. Mode bits: the full source st_mode including setuid and setgid is passed to openat(O_CREAT) where GNU cp strips those bits (issue #52, private report closed 2026-06-21); read-only directories break the copy (admitted in commit 11d5469); sparse files are not handled (#37 open); `cpz src existing_dir` errors instead of copying into it. git master needs nightly (#51) while the crates.io releases declare rust_version 1.88, and Docker's default seccomp blocks unshare (undocumented NO_UNSHARE workaround, #34).

## Caveats and trade-offs

The win is parallel copying, not Rust code generation: the single-threaded Rust cp_stdlib in the same table (std::fs::copy per file) matches GNU cp (19.496 s vs 18.436 s at 1M files, 0 B). The tables were last regenerated in March 2023 (commits 4cb8736 and ebf11a7, 2023-03-23/24) and the code has changed since. cpz is not the fastest tool in every row: in a flat directory of 100,000 files the Rust xcp wins (0 B: xcp 1.133 s, cpz 1.365 s, cp -r 1.618 s; 1 GiB: xcp 1.209 s, cpz 2.080 s, cp -r 2.464 s), and cp_rayon and fcp edge it at 5 files per directory with 1 GiB. Total CPU time rises: at 1M files, 0 B, cpz uses 26.48 s user+system against 18.10 s for cp -r (derived from page data). The run script also builds and runs wcp (C++) but no wcp row appears in any results table. cpz copies with copy_file_range, which can clone extents on a reflink-enabled xfs, while an older GNU cp may do a byte copy; cp_stdlib uses the same syscall and still matches cp, so this is not the main factor. Source and destination on the same xfs SATA partition, one machine, warm page cache with no sync between runs; the variance on the cpz rows is large (+- 0.976 s at 1M files). The author's blog overview (alexsaveau.dev/blog/fuc) does not resolve from this environment. [retier] Enricher: the '1 GiB' rows do not measure data copying; in the 10-file 1 GiB row cpz takes 1.3 ms and cp -r 1.9 ms while the tar pipe needs 304.3 ms and rsync 1042.4 ms, so on this XFS the copies cloned extents (derived from page data). Work is split per directory, so one flat directory means one thread and xcp wins there. The full source st_mode including setuid and setgid is passed to openat(O_CREAT) where GNU cp strips those bits (issue #52 closed 2026-06-21); read-only directories break the copy; sparse files are not handled (#37); git master needs nightly (#51) while crates.io releases declare rust_version 1.88; Docker's default seccomp blocks unshare (#34).

Linux is the primary target (other platforms use the rayon-style implementation). Non-goal: compatibility with coreutils cp options. Much higher total CPU time than cp (System 23.7 s vs 15.3 s at 1M files, 0 B).

## Maintenance

The project is actively maintained (cpz 3.2.1 on crates.io 2026-10-04, Apache-2.0, about 28.6k downloads) and usable from releases or crates.io, but the benchmark tables date from March 2023 and their 1 GiB rows measure extent cloning on reflink XFS rather than byte copying (derived from page data), so read the 3.4-4.8x as a warm-cache small-file metadata result.

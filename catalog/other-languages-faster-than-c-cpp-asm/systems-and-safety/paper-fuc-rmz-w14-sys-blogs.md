## Verdict

These are first-party hyperfine runs from March 2023 (--warmup 3, tree regenerated by ftzz before every run) on an Intel i7-7700 with 15 GiB RAM, a RHEL 9 5.14 kernel and /tmp on XFS over SATA. rmz deleted 1M empty files in 4.711 s against 9.491 s for the distro GNU rm -r (2.01x) and 1M files totalling 1 GiB in 6.559 s against 23.354 s (3.56x). Single-threaded Rust std::fs::remove_dir_all matched rm -r, and a flat 100,000-file directory showed parity (830.7 vs 847.1 ms).

## Use it when

- Deleting deep, nested trees of many files on a local Linux filesystem (node_modules, build directories, CI workspaces, test fixtures): 1.8-4x faster than rm -r in the author's tables (4.711 s vs 9.491 s for 1M empty files).
- Trees whose files carry data: the gap widens when extents must be freed (1M files totalling 1 GiB: 6.559 s vs 23.354 s, 3.56x).
- Machines with idle cores where wall-clock time matters more than total CPU.
- Scripts that delete trees you own and control, where rm's prompts and safety options are not needed.

## Skip it when

- One huge flat directory: work is split per directory, so a single directory is emptied by one thread (flat 100,000-file row: user+system 801.1 ms for 830.7 ms wall, derived from page data), giving parity with rm -r (830.7 vs 847.1 ms at 0 B; 1.115 vs 1.129 s at 1 GiB).
- As root on trees that untrusted users can write to, or anywhere rm's guard rails matter: there is no interactive mode, no write-protected-file prompt, no --one-file-system, and the preserve-root check can be bypassed (see gotchas).
- Directories that other processes keep writing into: the ENOTEMPTY retry loop is now unbounded (commit 2d4687f removed the 4,096-attempt cap that 5722542 had added to stop a file-creating process from causing an endless loop).
- Busy or shared machines: at 1M files rmz used 19.19 s user+system against 9.23 s for rm -r (derived from page data).
- Docker containers with the default seccomp profile, which blocks unshare: rmz fails with 'failed to unshare' unless the undocumented NO_UNSHARE environment variable is set (issue #34).

## How it is fast

On Linux each directory is a task on an unbounded crossbeam channel; a root worker plus lazily spawned workers (up to available_parallelism) read entries with raw getdents64 into a 16 MiB mmap'd NORESERVE buffer per thread, unlink non-directories at once with unlinkat relative to the directory fd using d_type (no stat; EISDIR redirects unknown types), and send subdirectories on as new tasks that hold an Arc to their parent. Whoever finishes a parent's last child rmdirs the empty chain bottom-up, so no second pass is needed. Each thread unshares its file-descriptor table and filesystem context (unshare CLONE_FILES|CLONE_FS), which the author says speeds up directory processing (issue #34). The gain is parallelism, not Rust codegen: single-threaded std::fs::remove_dir_all (rm_stdlib) matches GNU rm (9.345 s vs 9.491 s at 1M files), and the scheduler puts rmz 12-41% ahead of a plain rayon version on nested trees (rm_rayon still wins the 10-file 1 GiB row, 15.9 vs 17.3 ms, and the flat 1 GiB row).

## Compared with alternatives

Pick rmz for deleting nested trees on Linux; cpz is the copy counterpart on the same engine, and dumac and cligen/dents only walk trees (du, find, ls). Prefer plain rm -r for flat directories, where rmz gains nothing.

## Gotchas

- Preserve-root is only a path-equality test (`file == Path::new("/")` in schedule_deletions), so an operand such as '/..' or '/usr/..' passes the check and is deleted recursively. GNU rm refuses any operand whose last component is '.' or '..' and compares the operand's device and inode with those of / (coreutils src/remove.c). Found by code reading; not reported in the issue tracker.
- Symlink race: Linux workers reopen every queued directory by its full path (openat(CWD, path, O_NOFOLLOW|O_DIRECTORY)) and rmdir it by path, and O_NOFOLLOW guards only the last component. A user who can write inside the tree could swap an intermediate directory for a symlink mid-run and redirect deletion outside it, the TOCTOU class of CVE-2022-21658 that Rust 1.58.1 fixed in the std::fs::remove_dir_all used by the rm_stdlib comparison. GNU rm walks with fts FTS_CWDFD. Found by code reading.
- Benchmark staleness and setup: the tables are from March 2023 and predate the 2026 changes (the getdents buffer grew from 8 KiB to 16 MiB in 1095d9d, and an ENOTEMPTY retry loop was added). Each timed run deletes a tree that ftzz regenerated just before it with no sync, on one SATA XFS partition with a warm cache.
- With NO_UNSHARE set (the Docker workaround) the threads share one working directory, and the fallback for paths of 4,096 bytes or more calls set_current_dir while other threads still resolve CWD-relative paths. A relative operand could then resolve against the wrong directory (code reading; no report).

## Known shortcomings

- rustc version, GNU rm version and build flags unstated; parity on flat directories and rm_rayon beats it in 2 rows; about 2x total CPU; numbers from 2023 with the code changed since.
- Safety bugs found by code reading, not in the issue tracker: preserve-root is a path-equality test only, so `rmz /..` passes; workers reopen directories by full path, so a symlink swap mid-run can redirect deletion (CVE-2022-21658 class); the ENOTEMPTY retry loop has been unbounded since 2d4687f. The numbers are from March 2023, older than the 2026 rewrite (getdents buffer 8 KiB to 16 MiB, 1095d9d). A flat directory is parity on one thread. git master needs nightly (#51) while the crates.io releases declare rust_version 1.88; Docker's default seccomp blocks unshare (#34).

## Caveats and trade-offs

The win is parallel tree deletion, not Rust code generation: the single-threaded Rust rm_stdlib (std::fs::remove_dir_all) in the same table matches GNU rm (9.345 s vs 9.491 s at 1M files, 0 B). Flat directories show parity (100,000 files at depth 0: 830.7 ms vs 847.1 ms at 0 B, 1.115 s vs 1.129 s at 1 GiB), and the plain rm_rayon variant beats rmz in two rows (10 files 1 GiB; 100,000 files 1 GiB flat). Total CPU time roughly doubles: at 1M files, 0 B, rmz uses 19.19 s user+system against 9.23 s for rm -r (derived from page data). The tables were last regenerated in March 2023 (commits 4cb8736 and ebf11a7) and the deletion code has changed since (2026-07 NFS deletion fixes). One machine, one xfs SATA partition, trees regenerated by ftzz in --prepare so the page cache is warm. GNU coreutils and rustc versions are not stated. The author's technical overview (alexsaveau.dev/blog/fuc) does not resolve from this environment. [retier] Enricher (code reading, not in the issue tracker): preserve-root is a path-equality test only, so `rmz /..` passes; workers reopen directories by full path, so a symlink swap mid-run can redirect deletion (CVE-2022-21658 class); the ENOTEMPTY retry loop has been unbounded since 2d4687f. The numbers are from March 2023, older than the 2026 rewrite (getdents buffer 8 KiB to 16 MiB, 1095d9d); a flat directory is parity on one thread.

Linux is the primary target (macOS and Windows fall back to the rayon-style implementation). Fewer options than coreutils rm. Uses far more total CPU time (System 18.65 s vs 8.77 s at 1M files, 0 B) because it deletes with many threads, so on a busy machine the wall-clock gain shrinks.

## Maintenance

The project is actively maintained (rmz 3.2.1 on crates.io 2026-10-04, Apache-2.0, about 214k downloads) and fine for deleting build or scratch trees you own, but the 2023 numbers predate the 2026 deletion rewrite, and the code has unhardened safety edges found by code reading (preserve-root bypass via '/..', path-based reopen open to symlink swaps, unbounded ENOTEMPTY retries), so do not alias it to rm or run it as root on untrusted trees.

## Verdict

These are first-party hyperfine tables regenerated by benches/update_readme.sh on a GitHub Actions ubuntu-24.04 runner (CPU not stated), with rasusa built in release mode with LTO on stable Rust and filtlong and seqtk from unpinned bioconda packages. A 2.9 GB long-read FASTQ subsampled to 50x of a 4.41 Mbp genome took 0.740 s against filtlong's 25.84 s (34.9x, but a different algorithm). Paired 179 MB files cut to 140,000 reads took 0.950 s against 1.132 s for seqtk one-pass (1.19x) and 0.963 s for seqtk -2 (1.01x, parity).

## Use it when

- Downsampling FASTQ/FASTA to a target coverage or base count when you know the genome size and do not want to work out a read count first.
- Paired-end downsampling in one command, so both outputs hold the same read IDs.
- Long-read datasets that need an unbiased random subset (for example assembly-at-depth experiments), rather than filtlong's subset biased toward length and quality.
- Capping per-position depth in a sorted BAM/CRAM with `rasusa aln` (stream strategy, a single pass for unpaired data).
- Keeping a few reads out of a huge run with --num/--frac (selection memory scales with reads kept since v5.0.0), or a streaming --one-pass/-p subsample when an approximate fraction is acceptable.

## Skip it when

- Raw speed over seqtk for a fixed read count: rasusa 0.950 s against `seqtk sample -2` 0.963 s is parity, and only seqtk's one-pass reservoir mode is slower (1.19x).
- Filtering by read quality or length: filtlong is the right tool, and the 34.9x figure compares random sampling with filtlong's scoring, not the same task.
- Input from a pipe or process substitution in the default modes: they open the input path twice. Only --one-pass reads it once.
- --coverage/--bases on more than 4,294,967,296 reads: the shuffle uses a u32 index vector, documented as undefined behaviour. Memory in that mode grows by about 9 bytes per input read (u32 length, u32 shuffled index, bool flag; derived from the code).
- Multi-threaded FASTQ throughput: the FASTX path is single-threaded, --threads only drives BAM BGZF (de)compression, and the multi-threading request (#55) has been open since 2022.

## How it is fast

It makes two streaming passes with the needletail FASTX parser (decompression through niffler). The first pass collects per-read lengths, or only counts reads in --num/--frac mode. A PCG64-seeded selection then marks the reads to keep in a Vec&lt;bool&gt;: a full shuffle of u32 indices for --coverage/--bases, and O(k) `rand::seq::index::sample` for --num/--frac since v5.0.0. The second pass writes only the marked records through a BufWriter. Its large lead over filtlong comes from doing less work (no per-read length and windowed-quality scoring). Against seqtk's equivalent two-pass mode, the run time is the same.

## Compared with alternatives

No catalogued sibling subsamples reads. mosdepth, sambamba and mako replace htslib-based C tools for depth calculation, BAM processing and sorting, so pick rasusa for random downsampling to a coverage, base or read target and use mosdepth to check the resulting depth.

## Gotchas

- Seeded output changes across major versions. v3.0.0 (rand 0.8 to 0.10) changed every seeded subset, and v5.0.0 changed which reads --num/--frac select for a given --seed (--coverage/--bases are unchanged since v3). Pin the version when reproducibility matters.
- --coverage/--bases keep adding shuffled reads until the target is reached, so the result can overshoot by one (possibly very long) read. Without --strict, an unreachable target only warns and returns everything possible.
- Benchmark harness: the filtlong row measures a different algorithm (filtlong scores every read on length and windowed quality), and the like-for-like seqtk -2 row is parity. The seqtk rows also run two processes inside one hyperfine shell command against one rasusa process, a small fixed cost in rasusa's favour. Tool versions and the Rust toolchain are unpinned, and the runner CPU is not stated.
- `rasusa aln` in paired mode subsamples read 1 at half the requested coverage and then recovers mates, so depth fluctuates around the target rather than being capped exactly.

## Known shortcomings

- 34.9x over filtlong compares a different algorithm (quality scoring); the like-for-like seqtk -2 row is parity (1.01x); runner pinned to ubuntu-24.04 with the CPU unstated and tool versions unpinned (bioconda -O3).
- No new harness bug: parity with seqtk -2 (0.950 vs 0.963 s) and the different-algorithm filtlong row confirmed; two seqtk processes per hyperfine command against one rasusa process gives rasusa a small fixed edge. Coverage mode uses a u32 index vector (undefined over 2^32 reads, about 9 bytes per read); the default modes open the input path twice, so no pipe input; the FASTX path is single-threaded.

## Caveats and trade-offs

First-party, on a shared GitHub Actions runner (CPU model not stated); the tool versions and Rust toolchain are not pinned. The 34.9x over filtlong is not like-for-like: filtlong scores every read by length and windowed quality and keeps the best subset, while rasusa draws a random subset. The rasusa JOSS paper itself says filtlong is a filtering tool, not a subsampler. For the same job, seqtk sample -2 (two-pass random sampling, the mode the README calls analogous), the result is parity: 0.950 s vs 0.963 s, 1.01x. Against seqtk's one-pass reservoir mode it is 1.19 +/- 0.14x. The README's internal v4.1.0 to v5.0.0 table (about 7-8% wall time, 25-74% peak RSS) compares rasusa with itself, not with a C/C++ tool. ## Maintenance

Actively maintained (v5.1.0 on 2026-07-31, last commit 2026-10-01, only two open enhancement issues), MIT-licensed, described in JOSS (2022) and Gigabyte (2026) papers and packaged everywhere. Choose it for its coverage-targeted interface and paired handling, not for a speed edge over seqtk, which is parity in the like-for-like mode.

## Verdict

Usubac-generated C for DES, AES-CTR, ChaCha20, Serpent-CTR and Rectangle was timed against hand-tuned SUPERCOP references (Kwan DES, Kasper-Schwabe SSSE3 and Kivilinna AVX AES, moon and Dolbeau ChaCha20, Linux C and avx2-16way Serpent) with clang or icc -O3, using SUPERCOP xor_cycles on 4096-byte messages (mean of the faster half of the samples) on an unnamed amd64 host. Across the 15 rows Usuba ranges from 23% faster (Rectangle SSE) to 4.6% slower (Serpent AVX2), with a median of +1.66% and 5 rows within 2%, consistent with the paper's 'on par' claim (abstract seen in a search snippet only); DES GP is 11.47 against 12.01 cycles per byte for Kwan with identical S-box circuits.

## Use it when

- You need a constant-time implementation of an S-box-based or ARX cipher that has no hand-tuned SIMD code (lightweight or NIST LWC candidates such as Ascon, Gift, Pyjamask, Rectangle) and want one source for x86 GP, SSE, AVX2 and AVX-512.
- Bulk, parallel workloads: CTR or ECB over many blocks, where 64 to 512 independent blocks per call keep every bitslice lane busy.
- Research or prototyping where you want to compare slicing strategies (bitslice, vslice, hslice) or check masking (arch/MASKED.h) without hand-writing intrinsics.
- Vendoring a single generated C file is acceptable and you can write the transposition and mode wrapper yourself.

## Skip it when

- AES or ChaCha20 where a maintained library already exists: the authors' own table has Usuba 1.9-2.2% slower than the Kasper-Schwabe and Kivilinna bitsliced AES and level with Dolbeau and moon on ChaCha20 AVX/AVX2, so there is nothing to gain.
- Serpent on AVX or AVX2, where Usuba is 3.6-4.6% slower than the avx-8way and avx2-16way references.
- Sequential modes (CBC encryption) or short messages: bitslicing needs many independent blocks in flight.
- Production use that needs a maintained toolchain: the compiler is a research prototype, substantive development stopped in September 2022 (last commits 2024-09-04 only touch Docker and build instructions), init_scheduler is disabled as buggy (issue #78), and some passes overflow the stack (results.org log; issue #65 recommends ulimit -s unlimited).
- You want a library API: there is no packaged runtime, release or ABI; you get one C function per cipher.

## How it is fast

Bitslicing (and its m-slicing generalisation) processes 64 to 512 blocks per call as boolean circuits on SIMD registers, which is also constant-time by construction. Usubac replaces S-box tables with known circuits from data/sboxes (data/sboxes/des_1.ua is Matthew Kwan's 1998 gate list, the same one the baseline uses), then applies bitslice-aware inlining, instruction scheduling and interleaving of independent cipher instances before the C compiler sees the code. The repo's ablation log (results.org, from bench/inlining and bench/scheduling-bs) lists DES at x0.46 to x0.76 relative to the -no-inline build once inlining is on; the log does not label the unit.

## Compared with alternatives

No sibling is a cipher compiler: tachyon-rs is the pick for production AES-GCM and ChaCha20-Poly1305 against OpenSSL, and SPARKNaCl for verified NaCl primitives; choose Usuba only when you need constant-time bitsliced code for a cipher those libraries do not implement, or want one source for several SIMD widths.

## Gotchas

- Harness flaw: the largest wins (Rectangle SSE +22.95%, AVX +14.43%, AVX2 +14.29%, GP +9.54%) come from bench/ua-vs-human/rectangle/rectangle_ua and rectangle_ref, which run.pl calls but which are not in the master tree (404), so the Rectangle reference and its timing loop cannot be inspected. The SUPERCOP rows read supercop-data/dadaubuntu/..., which is not committed either, and name compiler settings (icc -xSSSE3, icc -xSSE2, icc -msse4.2) that the committed supercop/okcompilers/c does not list.
- Harness flaw in ciphers/des/main.c: verif() compares the output with a Perl DES but only prints 'Encryption error.' to stderr and carries on, and compile.pl reads only stdout, so a wrong binary would still be timed. Timing uses _rdtsc (TSC reference cycles, not core cycles) and includes byte swaps and the 64x64 to 256x256 transposition on both sides. The Usuba side also copies the key with memcpy on every call, which makes the comparison slightly conservative.
- Several rows pair different compilers or ISA flags: Serpent GP (+15.11%) is Usuba clang -march=native against Linux C icc -msse4.2, and Serpent AVX is Usuba clang against icc. The DES baseline is Kwan's code with S-box circuits dated March 1998, and Usuba's data/sboxes/des_1.ua matches Kwan's s1 gate for gate (the other seven were not checked), so the DES row mostly isolates scheduling and inlining, not circuit quality. The Serpent SLOC figures are computed from chacha20_shadow.ua plus 190, a copy-paste error that affects code-size claims only.
- The default branch is main, which was restructured and no longer carries bench/, ciphers/ or experimentations/; the hand-tuned comparison exists only on the old master branch.

## Known shortcomings

- Mixed against the SUPERCOP hand-tuned references (bench/ua-vs-human/human.tex): Rectangle +9.5-23%, Serpent GP +15%, ChaCha20 SSE +15%, DES GP +4.5%, but slower on AES (about 2%), Serpent AVX/AVX2 and DES SSE/AVX; the 'bsc' comparison is Pornin's non-optimising prototype compiler, not hand-tuned C; CPU unstated, some rows use a different compiler per side, paper unreachable. Stale since 2024-09-04.
- The Rectangle rows (the biggest wins, +9.5 to +23%) come from bench/ua-vs-human/rectangle/rectangle_{ua,ref}, called by run.pl but 404 on master; the supercop-data raw files are not committed and the icc -xSSSE3/-xSSE2/-msse4.2 configurations are missing from the committed supercop/okcompilers/c. ciphers/des/main.c's verif() only prints 'Encryption error.' to stderr while compile.pl reads stdout, so a wrong binary is still timed. The Serpent SLOC is computed from chacha20_shadow.ua plus 190; data/sboxes/des_1.ua matches Kwan's s1 gate for gate (the other 7 not checked), so the DES row tests scheduling, not the circuit. The median over the 15 rows is +1.66%. Paper blocked (dariusmercadier.com 403).

## Caveats and trade-offs

Win is mixed and small: faster on Rectangle (9.5-23%), Serpent GP (15%), ChaCha20 SSE (15%) and DES GP (4.5%); slower on AES (about 2%), Serpent AVX/AVX2 (3.6-4.6%) and DES SSE/AVX; the paper itself claims 'on par'. The results.org DES comparison is against BSC 0.1, which the experiment's own Readme calls a prototype 'not meant to be an optimizing compiler', so it is not a hand-tuned baseline. The hand-tuned comparison lives only on the old master branch (bench/ua-vs-human/human.tex, ciphers/des/results.txt); the default main branch was restructured and no longer carries bench/, ciphers/ or experimentations/. Numbers are undated author runs on an unstated CPU, and some rows use different compilers or ISA flags for each side. Usuba output is C compiled by the same C compiler, so the gain comes from the Usubac compiler's transformations (scheduling, interleaving, inlining), not from a different backend. results.org also logs broken runs ('No supercop', 'C compilation goes wrong', a stack overflow, 0.00 AVX-512 results). Papers not opened (snippet only). [retier] The Rectangle rows (+9.5 to +23%) come from bench/ua-vs-human/rectangle/rectangle_{ua,ref}, which run.pl calls but which 404 on master; the supercop-data raw files are not committed and the icc configurations are missing from the committed supercop/okcompilers/c. ciphers/des/main.c's verif() prints only to stderr while compile.pl reads stdout, so a wrong binary is still timed. data/sboxes/des_1.ua matches Kwan's s1 gate for gate, so the DES row tests scheduling, not the circuit. The median over the 15 rows is +1.66%.

Domain-specific language for bitsliced and vector-sliced ciphers; targets x86 SIMD and the generated code is only as good as the C compiler used.

## Maintenance

Stale research prototype (substantive work ended September 2022, last commit 2024-09-04, no releases, 62 stars); MIT-licensed, and a generated C file plus one arch header can be vendored without the OCaml toolchain, but the benchmark evidence is partly missing from the repo (Rectangle harness, SUPERCOP raw data) and the DES harness does not enforce its correctness check.

## Verdict

The author ran hey -n 100000 -c 250 (one run of about 1 s per proxy) through prebuilt Docker images on an i5-13600K PC, with each proxy and the echo backend capped at 4 CPUs. Spire got 114,512 req/s vs HAProxy 2.7.3 85,406 and Envoy 1.22.8 48,040, but the load generator had 12 CPUs only in the Spire and nginx runs; tuned nginx 1.23.3 reached 148,677 (Spire 0.77x), and with equal load-generator CPUs in 2023 Spire was 0.81x HAProxy. A third-party run (holmofy/proxy-benchmark, Sept 2024, i7-13700H laptop, wrk -t4 -c1000 -d120s from the host) put Silverwind 0.0.20 at 19,352 req/s vs HAProxy 17,826 (1.09x) and Envoy 13,517 (1.43x), but Silverwind's backend was lsk569937453/echo-server:0.0.3 (about 80 bytes per response) while the others used jmalloc/echo-server (169-335 bytes), and that run's nginx row returned 29,520 non-2xx responses.

## Use it when

- You want one Rust binary that bundles gateway features (rate limiting, circuit breaker, API-key/Basic auth, IP lists, CORS, health checks, ACME, hot reload, Prometheus) behind a single YAML file.
- Moderate HTTP/1.1 reverse-proxy load: around 100k req/s on 4 cores of a desktop CPU in the author's Docker run is enough headroom for your service.
- You prefer a memory-safe stack with rustls instead of OpenSSL for TLS termination.
- You want an HTTP-to-gRPC route that calls a gRPC backend and returns JSON (prost-reflect path in proxy/http1/http_proxy.rs).

## Skip it when

- Raw proxy throughput or tail latency is the goal: tuned nginx 1.23.3 beats it in its own table (148,677 vs 114,512 req/s; p99 4.9 vs 11.8 ms), and in the 2023 run where every proxy had the same load generator it reached 0.81x HAProxy.
- Memory-constrained hosts: issue #59 reports it used the most memory of the proxies tested, and that third-party run lists 280 MB for Silverwind vs 85 MB HAProxy, 70 MB Envoy and 40 MB nginx.
- High-cardinality URL spaces: request metrics are labelled with the raw path and query string, so every distinct URL creates new Prometheus series.
- You need a mature, widely deployed proxy: pre-1.0 (0.0.28), one maintainer, 74 crates.io downloads, and the config schema changed between releases (the benchmark's app_config.yaml uses the old services/listen_port schema).
- You need response compression (issue #56 'Add encoding for the response' is open), HTTP/3 or caching (none documented).

## How it is fast

Nothing beyond a standard async Rust stack: a Tokio multi-threaded work-stealing runtime with one task per accepted connection, a Hyper 1.x HTTP/1.1 server, and the hyper-util legacy pooled client for upstream keep-alive (default pool settings, not overridden in http_client.rs). mimalloc is the global allocator and rustls with ring does TLS. There is no io_uring, per-core SO_REUSEPORT sharding or zero-copy splice, and the release profile is not tuned (lto = false, codegen-units = 16, panic = unwind).

## Compared with alternatives

Pick Spire over routez or rproxy (whose catalogued wins over nginx and HAProxy come from tighter harnesses, rproxy's median of 3 runs on pinned cores) only when you want the bundled gateway features more than raw proxy speed. To replace Envoy specifically, Orion Proxy and linkerd2-proxy carry Envoy comparisons.

## Gotchas

- Harness flaw beyond the verifier's 12-vs-4-CPU finding: docker 'cpus: 4.0' sets a CFS quota, not a CPU mask. HAProxy 2.7 defaults nbthread to the CPUs in its affinity mask, and Envoy 1.22.8 defaults --concurrency to the number of hardware threads, so both probably ran about 20 threads (i5-13600K) inside a 4-CPU quota. nginx was pinned to 4 workers, and Tokio sizes its pool from std::thread::available_parallelism, which honours cgroup quotas. CFS throttling would fit the 40-51 ms tail clusters in the HAProxy and Envoy histograms (inferred, not measured).
- The benchmark compose sets JEMALLOC_SYS_WITH_MALLOC_CONF at run time, but that is a build-time jemalloc-sys option, and Spire's global allocator is mimalloc (Cargo.toml at benchmark commit 0cac057 and now), so the variable does nothing; the record's 'jemalloc' note is wrong.
- Every proxied request writes an info-level access-log line and updates two Prometheus metrics labelled by raw path; each HTTPS accept clones the rustls ServerConfig under a std RwLock and logs the whole config at info level.
- Upstream connection errors and timeouts come back as HTTP 500 with a JSON body ('Request time out, the uri is ...'), not 502/504, and failures in the outer adapter return 404 with JSON. The Host header is rewritten to the upstream host.

## Known shortcomings

- Crippled baseline: the committed compose files (0cac057) give hey 12 CPUs for the Spire and nginx runs but 4 CPUs for HAProxy, Envoy, Traefik and Caddy; in the 2023 run with hey at 4 CPUs everywhere (benchmarks.md at 42659e7) Spire, then Silverwind, scored 66,370 vs HAProxy 81,674 (0.81x). Also 0.77x nginx in its own table; the Traefik row is copied from the 2023 run against a different backend; nginx tuned while HAProxy and Envoy configs are not; one run of about 1 s per proxy; build flags unstated; config path mismatch (/temp vs /tmp) in the Spire compose file.
- Beyond the 12-vs-4 hey CPUs: docker cpus: 4.0 is a CFS quota, so the defaults give HAProxy 2.7 nbthread and Envoy 1.22.8 --concurrency about 20 host threads inside a 4-CPU quota while nginx is pinned to 4 workers and Tokio honours the cgroup quota (inferred, fits the 40-51 ms tail clusters). The compose JEMALLOC_SYS_WITH_MALLOC_CONF is a no-op (a build-time jemalloc-sys variable; the global allocator is mimalloc, also at 0cac057), so the record's jemalloc note is wrong. Per-path Prometheus labels mean unbounded series; per-request info log; upstream errors return 500/404. Third-party run holmofy/proxy-benchmark (2024-09): Silverwind 19,352 vs HAProxy 17,826 req/s (1.09x) with a different echo backend image (80 vs 169 bytes per response) and 280 MB vs HAProxy's 85 MB.

## Caveats and trade-offs

Crippled baseline harness. The compose files committed with the 2025 numbers give the hey load generator 12 CPUs for the Spire and nginx runs but 4 CPUs for the HAProxy, Envoy, Traefik and Caddy runs, while benchmarks.md says every service was limited to 4 cores. Only the two 12-CPU rows jumped between runs (Spire 66,370 to 114,512 req/s, nginx 42,388 to 148,677); HAProxy stayed at 81,674 to 85,406. In the 2023 equal-CPU run Spire (then Silverwind) was 0.81x HAProxy. The Traefik row is copied byte-for-byte from the 2023 run and used a different backend (jmalloc/echo-server). Configs differ: nginx is tuned (4 workers, upstream keepalive 100), HAProxy has a minimal config with no timeouts, and Envoy's concurrency is not set. Envoy also adds headers that the echo backend returns, so its response is 294 bytes vs Spire's 155. Even so, Spire is slower than nginx in its own table (114,512 vs 148,677 req/s; p99 11.8 ms vs 4.9 ms). Each proxy had one hey run of about 1 s on the same PC as the load generator, with old HAProxy and Envoy releases and unstated build flags. The checked-in Spire compose sets CONFIG_FILE_PATH to /temp/app_config.yaml but mounts the file at /tmp/app_config.yaml, and app_config.yaml uses an older schema than the README, so the published harness may not run as checked in. The README headline 'Exceptional Performance' is not backed by a like-for-like win over any C or C++ proxy. [retier] docker cpus: 4.0 is a CFS quota, so the defaults give HAProxy 2.7 nbthread and Envoy 1.22.8 --concurrency about 20 host threads inside a 4-CPU quota while nginx is pinned to 4 workers and Tokio honours the cgroup quota (inferred, fits the 40-51 ms tail clusters). The compose JEMALLOC_SYS_WITH_MALLOC_CONF is a no-op; the global allocator is mimalloc (also at 0cac057). Third-party holmofy/proxy-benchmark (2024-09): Silverwind 19,352 vs HAProxy 17,826 req/s (1.09x) with a different echo backend image (80 vs 169 bytes per response) and 280 MB vs HAProxy's 85 MB.

Rust reverse proxy and gateway on Tokio and Hyper (HTTP/1.1, HTTP/2, gRPC, TCP/TLS) with rate limiting, circuit breaking, ACME and hot reload; about 7 MB binary and 4 MB start-up memory per README.

## Maintenance

Active but quiet (last commit and crates.io release 0.0.28 on 2026-01-28), Apache-2.0 (license file named 'licence'), single-maintainer pre-1.0 gateway that is usable as a binary; its speed claim over C and C++ proxies rests on a harness that gave the load generator 12 CPUs only for Spire and nginx and probably left HAProxy and Envoy oversubscribed inside a 4-CPU quota, so treat it as a feature-rich gateway, not a faster one.

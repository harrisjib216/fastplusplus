## Verdict

In kostya/jit-benchmarks round 1 (README update 2023-02-28; raw data in results/amd64/round_1.yml), OpenResty luajit2 2.1-20230119 ran k-nucleotide on a 7,000,000-base input in 0.767 s of self-reported CPU time against 2.09 s for test.cpp built with g++ 12.2.0 -O3 -march=native -fomit-frame-pointer -funroll-loops -std=c++11 (std::unordered_map&lt;std::string,int&gt;, substr keys), one run each in Docker on Ubuntu 22.10 on an AMD Ryzen 7 3800X: about 2.7x (derived from page data). The C++ row is the only C or C++ row in the knucleotide table.

## Use it when

- Lua code under LuaJIT that counts or deduplicates many short substrings drawn from a small key set (log tokens, k-mers, n-grams), where interning makes repeated keys cheap.
- Scripts where you would otherwise write the naive C++ version (std::string keys, default std::hash, no reserve) and do not plan to tune it.
- Embedding LuaJIT (or OpenResty, which ships this fork) for text-processing hot paths in a C or C++ host.

## Skip it when

- As evidence that LuaJIT beats tuned C++: the Benchmarks Game's own C++ k-nucleotide programs pack bases into 2-bit integer keys and use custom hash tables; none of them was run here, and C++11 also rules out std::string_view keys.
- As a general LuaJIT-beats-C claim: this is LuaJIT's only win in the suite; it is slower than C or C++ on all ten other benchmarks where it has a row (for example binarytrees 6.73 s vs C++ 0.44 s, revcomp 3.33 s vs C 0.54 s, regexdna 9.99 s vs 5.6 s, nbody 1.44 s vs 0.56 s, fasta 1.71 s vs 0.57 s).
- Workloads with millions of distinct keys: the periodic input keeps every table at about 140,000 entries or fewer and peak RSS near 30 MB, so table growth, GC pressure from millions of new strings, and cache misses on large tables are not exercised.
- Multi-threaded counting: the benchmark is single-threaded and a LuaJIT state cannot be shared across threads.

## How it is fast

LuaJIT interns every string: string.sub hashes the window and returns the existing string object if it is already in the string table, and the Lua table then looks the key up by object identity. The input generator (knucleotide/helper.c) uses the Benchmarks Game LCG with modulus 139,968, so the THREE section is periodic and has at most about 140,000 distinct k-mers; after the first period no new strings are allocated. The C++ program instead builds a std::string per window (a heap allocation and free for the 18-mer pass, beyond libstdc++'s 15-character small-string buffer), hashes all k bytes with std::hash, reduces modulo a prime bucket count, walks a node chain and compares bytes. The suite does not explain the gap; this mechanism is inferred from the two programs and the runtime sources.

## Compared with alternatives

Among the LuaJIT siblings this is the best-documented row (public code, flags, CPU and raw results), stronger than the spion word-count gist (single 2012 timing) and the JuliaLang print_to_file row (cross-runner, directional); against the HotSpot, .NET and Julia string-hashing siblings it is the case to cite when the runtime is LuaJIT or OpenResty and the C++ rival is naive std::string-keyed code.

## Gotchas

- The 'Lua JIT' row is not upstream LuaJIT: docker-compose.yml builds the luajit container from OpenResty's luajit2 fork (docker/luajit downloads openresty/luajit2 tag v2.1-20230119). The README Versions table's '2.1.0-beta3' is only the LUAJIT_VERSION string that every 2.1 build printed before 2023. On x64 that fork replaces the string-interning hash with an SSE4.2 CRC32 hash (src/lj_str_hash.c), which sits on this benchmark's hot path, so upstream LuaJIT was not measured.
- The 'Best T' column is the time each program reports about itself, not an external measurement: tools/cli.rb takes min_run_time from the time(...) line each program writes to stderr. Both sides use process CPU time (C++ clock(), Lua os.clock()), and the C++ value is printed with only two decimals. The harness's wall-clock full_time minus start_time agrees (about 2.07 s vs 0.75 s in results/amd64/round_1.yml).
- Each row is a single run (args [1], Runs 1) from round 1 (2023-02-28), so there is no variance estimate and LuaJIT's trace compilation falls inside its one timed run. Input reading happens before the 'started' marker and is excluded for both sides.
- Only the 18-mer pass makes the C++ program allocate per window; the 1-, 2-, 3-, 4-, 6- and 12-mer passes fit libstdc++'s small-string buffer, so the C++ cost there is the std::string copy, full-length std::hash, modulo-prime bucketing and chain walk rather than malloc.

## Known shortcomings

- The C++ side is untuned (a std::string per window, an unreserved unordered_map, C++11 with no string_view); single run, 2023 numbers (gcc 12.2.0, Ryzen 7 3800X); the LuaJIT win comes from string interning.
- The 'Lua JIT' row is OpenResty's luajit2 fork at tag v2.1-20230119 (docker-compose.yml and docker/luajit), not upstream LuaJIT; the README's '2.1.0-beta3' is only the LUAJIT_VERSION string every 2.1 build printed before 2023, and on x64 the fork's SSE4.2 CRC32 string-interning hash (src/lj_str_hash.c) sits on this benchmark's hot path, so upstream LuaJIT was not measured (name corrected). Best T is each program's self-reported CPU time (clock, os.clock; tools/cli.rb min_run_time), not external timing, raw data in results/amd64/round_1.yml (0.767395 s vs 2.09 s). helper.c's LCG mod 139968 makes the input periodic, so at most about 140k distinct k-mers exist and the tables stay small; the C++ side heap-allocates per window only in the 18-mer pass.

## Caveats and trade-offs

Idiomatic code against idiomatic code, not tuned C++: the C++ program builds a std::string per window with substr (heap allocation for k=18, beyond libstdc++'s 15-character small-string buffer), hashes it with the default std::hash and inserts into a node-based std::unordered_map that is never reserved; -std=c++11 rules out std::string_view keys, and the Benchmarks Game's own C++ k-nucleotide programs use packed integer keys and custom hash tables that would be far faster. The LuaJIT program is Mike Pall's Benchmarks Game program (string.sub keys in a Lua table, frame-strided loop). Each row is a single measured run (Runs 1) with no variance reported. Numbers are from round 1 (README update 2023-02-28) with LuaJIT 2.1.0-beta3 and gcc 12.2.0 and were not rerun; the only 2026 commit (2026-01-27) adds a README link, so the code and results are effectively from 2023 although the last commit counts as active. In the same suite LuaJIT is slower than C on regexdna (9.99s vs 5.6s) and revcomp (3.33s vs 0.54s). The README states no reason for the difference.

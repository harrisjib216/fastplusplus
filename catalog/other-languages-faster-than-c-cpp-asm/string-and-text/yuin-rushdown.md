## Verdict

The README's 'make bench' output converts the 198 KB CommonMark spec text to HTML (raw HTML allowed) in 3.34 ms with rushdown building its converter per call and 3.18 ms with a cached converter, against 3.64 ms for cmark master built Release (-O3, shared library, no LTO) and timed by a 500-iteration gettimeofday loop: 1.09x and 1.14x (derived from page data). Rust side is criterion with fat LTO, codegen-units 1 and panic=abort; CPU, OS and compiler versions are not stated.

## Use it when

- Rust services rendering CommonMark or GFM to HTML that build one converter and call it many times (the cached row: about 3.18 ms for a 198 KB document, roughly 64 MB/s, derived from page data).
- Pipelines that need to inspect or rewrite the AST (custom @mention syntax, heading IDs, link rewriting) before rendering, with goldmark-style extension points.
- no_std targets with alloc: the no-std feature swaps std collections for hashbrown.
- Replacing comrak or pulldown-cmark in a Rust project when CommonMark compliance and extensibility both matter (comrak 4.25 ms vs rushdown 3.34 ms on the same fixture).

## Skip it when

- C or C++ codebases: there is no C API, and the published lead over cmark is 9% like-for-like on one document, not worth an FFI layer.
- Many small documents with a converter built per call: building the converter costs about 0.16 ms (3.3427 minus 3.1845 ms, derived from page data), which dwarfs parsing a 1-2 KB comment. Build it once and reuse it (it is not Send, so one per thread).
- Untrusted input that relies on GFM's disallowed-raw-HTML tag filter: not supported; with allows_unsafe enabled you need a sanitizer such as ammonia (README).
- Projects that need a stable API: 0.x crate with frequent breaking refactors (refactor! commits through April 2026, e.g. Emphasis split into Emphasis and Strong).
- Code that builds Segment or Index values by hand from untrusted ranges: open soundness issue #2 (see gotchas).

## How it is fast

The README names no mechanism; the source shows the usual zero-copy parser design. AST nodes live in a Vec-backed arena addressed by index (NodeRef, initial capacity 1024), text is kept as Segment/Index offsets into the source string rather than copied, and memchr drives newline, backslash and entity scanning. Autolink and table scanners are DFAs generated by re2rust (src/scanner/\*.re), HTML entities use a compile-time phf map, and built-in node kinds are rendered through an enum match with optional override slots rather than dynamic dispatch. cmark itself also uses re2c scanners and a C arena, so the measured gap is small and unexplained.

## Compared with alternatives

Against zigmark (Zig CommonMark renderer, also measured against cmark) pick rushdown when you are in Rust and want an extensible AST with GFM extensions and a crates.io ecosystem (footnote, meta, emoji, highlighting, diagram, definition-list crates); pick zigmark for Zig. No other Markdown parser is catalogued in this category.

## Gotchas

- Harness flaws behind the numbers, beyond the verifier's (uninitialised 'double sum' in benches/cmark_benchmark.c, unpinned cmark master, no hardware): the single fixture benches/fixtures/data.md is the CommonMark spec text itself, about 38% of its bytes inside 708 fenced example blocks, so it is code-block heavy; the cmark C loop has no warm-up call while the goldmark driver warms up and reuses its buffer; the ftell check compares a size_t with &lt; 0 and can never fail. None of these looks large enough to flip a 9% gap, but nothing is reproducible without a hardware and compiler record.
- Rust sibling rows are not like-for-like either: rushdown runs with allows_unsafe and xhtml, comrak and markdown-rs run with their safe defaults (raw HTML omitted or escaped), and the pulldown-cmark closure also calls comrak::markdown_to_html, so its 6.0 ms row times two parsers.
- Soundness: Index::str and Segment::str are safe functions that call get_unchecked on user-supplied ranges (src/text.rs; the doc comment has a '# Safety' note but the function is not marked unsafe). Issue #2 (opened 2026-08-12, with Miri output) shows UB from safe code; no maintainer reply or fix as of 2026-10-12. Normal parsing creates in-range segments, so this mostly bites extension authors.
- Rendering walks the AST with a recursive ast::walk, and no nesting-depth limit was found in the parser, so pathologically deep blockquote or list nesting may exhaust the stack (cmark renders with an iterative iterator); the crate is fuzzed with cargo fuzz but this was not tested here. Defaults also differ from the benchmark: allows_unsafe and xhtml are both false unless set.

## Known shortcomings

- 1.09x like-for-like (1.14x cached) over cmark on one fixture; the cmark driver reads an uninitialised double sum (undefined behaviour); cmark master unpinned with the Release build inferred from CMakeLists; harnesses asymmetric; a different implementation, not a language win.
- The fixture benches/fixtures/data.md is the CommonMark spec text (198 KB, about 38% of bytes in 708 fenced blocks); the cmark C loop has no warm-up while the goldmark driver warms up; the size_t ftell &lt; 0 check is dead. Rust rows are mismatched: comrak and markdown-rs run on safe defaults, and the pulldown-cmark row also runs comrak; none flips the 9% gap. The per-call converter build is about 0.16 ms (derived), bad for small documents. Soundness: Index::str and Segment::str are safe functions calling get_unchecked; issue #2 (2026-08-12, Miri UB) is unanswered; ast::walk is recursive with no nesting limit found.

## Caveats and trade-offs

Margin is 9% (per-call converter, the like-for-like row) to 14% (cached converter) on a single fixture with no hardware or compiler versions stated, and cmark is downloaded from master at bench time, so its version is unpinned. In benches/cmark_benchmark.c the accumulator 'double sum' is never initialised, so the cmark figure depends on whatever was on the stack (the reported value looks sane, but the harness is undefined behaviour). Different harnesses: Criterion with warm-up for Rust, a 500-iteration gettimeofday loop with no warm-up for cmark. rushdown renders XHTML (xhtml: true) while cmark renders HTML. The Rust harness also runs comrak inside the pulldown-cmark case, inflating that row. Rust side has fat LTO and codegen-units 1, cmark is a non-LTO shared library. No mechanism for the win is given. [retier] The fixture is the CommonMark spec text (198 KB, about 38% in 708 fenced blocks); the cmark C loop has no warm-up while the goldmark driver warms up. comrak and markdown-rs run on safe defaults and the pulldown-cmark row also runs comrak; none flips the 9% gap. The per-call converter build is about 0.16 ms. Index::str and Segment::str are safe functions calling get_unchecked (issue #2, Miri UB, unanswered); ast::walk is recursive with no nesting limit.

AST-based and extensible, no_std option; does not support GFM disallowed raw HTML; cmark has a different (non-AST streaming) output path.

## Maintenance

MIT-licensed single-author 0.x crate (rushdown 0.18.0, 47 commits, 35 stars, last commit 2026-04-30) with CI on stable, beta and nightly and fuzzing; usable today, but pin the version given the breaking-change cadence and the unanswered soundness issue #2.

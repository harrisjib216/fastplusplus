## Verdict

BENCHMARK_H20.md and BENCHMARK_GB200.md (first-party, generated by benchmarks/generate_benchmark_md.py using CUDA-event timing, warmup 30, 200 iters x 5 repeats) report KDA forward latency at T=8192, D=128, H=96 and 64. With FlashKDA run in fp32-state mode against fla's Triton chunk_kda, the speedup is 1.85-2.31x on H20 and 1.70-3.27x on GB200, largest for varlen batches. No fla, PyTorch or CUDA versions, driver or host CPU are recorded, and the numbers predate later correctness fixes.

## Use it when

- Serving or prefill for KDA-based models (Kimi Linear style) on Hopper or Blackwell, where fla's chunk_kda is on the critical path: about 1.85-2.3x on H20 and 1.7-3.3x on GB200 at T=8192, H=64/96.
- Varlen batches of mixed sequence lengths, where the gain over the Triton kernel is largest (2.3x on H20 and 3.2-3.3x on GB200 for 8x1024 packed sequences).
- Stacks already built on flash-linear-attention: install FlashKDA and chunk_kda picks it up with no code changes, as long as the call runs under torch.inference_mode().
- Inference where a bf16 recurrent state is acceptable (it halves the state's memory); fp32 state in and out is also supported and is what the published tables measure.

## Skip it when

- Training: there is no backward pass, and FLA only dispatches to FlashKDA in inference mode.
- Head dims other than K=V=128 (enforced by TORCH_CHECK; issue #4 asks about other sizes), non-bf16 activations, or pre-Hopper GPUs (setup.py builds only sm_90a, 100a, 103a and 120a).
- Scalar-gate gated delta rule (GDN) models: that is a different algorithm, and against fla's GDN kernel FlashKDA is only 0.96x (slower, GB200 H=64 fixed) to 1.80x.
- Anywhere you need a stable, released dependency: version 0.0.1, 10 commits, no PyPI wheel documented, 14 of 16 issues open, and an exact-match correctness test failing on B200 with CUDA 13.0 (#12, open).

## How it is fast

It uses chunk size 16 instead of FLA's 64. With the gate lower_bound at -5 this keeps exp(cumsum(g)) within bf16 range without intra-chunk rescaling, and the 16x16 inverse becomes cheap: fp32 forward substitution on two 8x8 diagonal blocks, merged with bf16 HMMA GEMMs. The work is split into a token-parallel kernel (gate activation, L2 norm, decay, L/Mqk build, inversion) and a head-parallel kernel (chunked delta-rule recurrence, output, state), which the authors say is at least 15% faster than one fused kernel. Other tricks: the on-chip state is held in bf16 but updated with fp32 FMAs; base-2 ex2.approx and tanh.approx-based sigmoid; __launch_bounds__(256,8) with shared-memory unions for occupancy; register-file transposes (MOVM) instead of shared-memory round trips; and TMA loads.

## Compared with alternatives

Pick FlashKDA when the model uses KDA's per-channel gate and you only need inference. FlashQLA targets the scalar-gate gated delta rule (Qwen-style GDN) and also covers backward, so it is the better fit for GDN models or training. FlashInfer's GDN prefill kernel is the option if you are already inside FlashInfer.

## Gotchas

- The published H20 (2026-04-22) and GB200 (2026-05-26) tables predate the fix for missing TMA proxy and mbarrier-init fences (#24/#25, 2026-07-29), which issue #24 says could cause hangs, stale data or silent corruption. They also predate the 2026-09-01 switch from an fp16 Neumann inverse to fp32 forward substitution. No re-run has been published, and issue #34 asking about the performance effect is unanswered.
- lower_bound is documented as -5 to 0, but csrc/flash_kda.cpp does not check it. The chunk-16 bf16-range argument in the design doc assumes -5, so do not pass values below that without testing accuracy yourself.
- In varlen mode B must be 1 and cu_seqlens int64; initial_state and final_state must share a dtype.
- The default build compiles only for the GPU visible at install time and fails if none is visible; set FLASH_KDA_CUDA_ARCHS=all (or e.g. 90a,100a) for wheel or CI builds.

## Known shortcomings

- Numbers predate the TMA proxy-fence race fix (#25) and the fp32 solver precision change; GB200 H=64 is 0.96x vs GDN (slower).
- test_fwd exact-match fails on B200 with CUDA 13.0 (#12, open); TMA fence UB (#24: hangs, stale data, silent corruption) fixed after the bench tables; lower_bound not validated; forward and inference_mode only.

## Caveats and trade-offs

First-party benchmark with no fla/PyTorch/CUDA versions, build flags or CPU model on the benchmark pages. The H20 page names benchmarks/generate_benchmark_hopper_h20_md.py, which no longer exists (raw fetch 404; the current generator is benchmarks/generate_benchmark_md.py). Both result pages (generated 2026-04-22 and 2026-05-26) predate correctness-related commits: 'fix missing proxy fences around TMA accesses (#25)' (2026-07-29) and 'replace fp16 Neumann inverse with 8x8 fp32 forward substitution' (2026-09-01), so the numbers were measured on code later changed for correctness/precision. H20 is a low-compute, high-bandwidth SKU, so H20 numbers may not transfer to H100. Baseline is the FLA Triton KDA kernel, not oneDNN/cuDNN/XNNPACK/Eigen; the GDN reference is a different (scalar-gate) algorithm, and in one GB200 case (H=64 fixed) FlashKDA is slower than it (0.96x). Only the forward pass is benchmarked; K=V=128 only.

KDA forward only (the benchmark pages cover forward); requires SM90 or newer GPUs and CUDA 12.9+; uses bf16 inputs and a custom forward-substitution inverse, so results are checked against fla_chunk_kda for accuracy.

## Maintenance

Active but early (v0.0.1, last commit 2026-09-01, 10 commits). MIT-licensed and small enough to vendor, though it builds against a CUTLASS submodule and needs CUDA 12.9+ on Hopper or Blackwell.

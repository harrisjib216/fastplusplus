## Verdict

The author benchmarked on an Apple M2 Max (macOS 26.5.1, rustc 1.98.0, opt-level 3, mimalloc) with one Instant-timed pass over 100k random 8-128 byte keys in a filter sized for 200k (about 38% full). Positive lookups ran at 81.0 M/s vs 14.6 M/s for sile's scalable_cuckoo_filter 0.5.1 (SipHash-1-3) and 20.4 M/s for cuckoofilter 0.5 (FarmHasher, given 10x capacity). Adds ran at 21.8 vs 9.1/14.9 M/s and removes at 53.5 vs 13.6/13.5 M/s. The contenders use different hash functions, so part of the gap comes from the hasher rather than the filter. The README's '4.5x/3x' headline comes from an older table that gives no environment.

## Use it when

- A Rust service needs a 'definitely absent' pre-check with deletions for a key set that grows without a known final size, for example in front of an index or WAL write path, as the README's example shows.
- String or byte-slice keys (the bench used random 8-128 byte keys) on hardware with AES instructions, where hashing dominates the cost of a lookup.
- Lookups that are mostly for keys that are present. The deferred second hash pays off most there, because most positive lookups hit the first bucket.
- You already use sile's scalable_cuckoo_filter and want the same layout and memory footprint (both 353 KB in the bench) with faster operations, and you can rename a few calls.
- Servers or Apple Silicon builds where you control RUSTFLAGS (e.g. -C target-cpu=native).

## Skip it when

- Portable x86-64 binaries built without extra RUSTFLAGS. The default gxhash feature does not compile there, and turning it off falls back to std's SipHash, which voids the published numbers.
- Static or rarely changing sets. In the bench it used about 29 bits per key (353 KB for 100k keys at 0.17% measured FPP, because bucket counts round up to a power of two and the filter was 38% full), and immutable xor/binary-fuse filters are far smaller.
- Workloads dominated by keys that are absent. These were never benchmarked; every miss hashes twice and probes both buckets in every layer, so the cost grows with the number of growth layers.
- Concurrent writers. There is no concurrent API: mutation takes &mut self, so you need an external lock or sharding.
- Projects that are strict about maturity or licensing: 3 stars, about 1.1k downloads, MulanPSL-2.0 declared only in Cargo.toml and the README with no LICENSE file, and the upstream's MIT notice is not reproduced.

## How it is fast

It keeps the upstream's partial-key cuckoo hashing (Fan et al., CoNEXT'14) with bit-packed fingerprints and 4-entry buckets. When a bucket fits in 64 bits it is read with a single unaligned 128-bit load and all slots are compared branchlessly with `|`, where the upstream reads each slot in a bounds-checked byte loop; inserts find the matching and empty slots in the same pass. The alternate bucket index, which costs a second hash of the fingerprint, is computed only when the first bucket misses, while the upstream always computes it. The default hasher is gxhash (AES-NI/NEON) instead of the upstream's SipHash-1-3.

## Compared with alternatives

Pick it over xorf (static xor/binary fuse, smaller and faster but immutable) or fastbloom (no deletion) when a Rust set must take inserts and deletes and grow without a known size. The C++ efficient/cuckoofilter reference and CGCL's Dynamic Cuckoo Filter cover the same ground outside Rust, and no head-to-head numbers against them exist.

## Gotchas

- `cargo add autoscale_cuckoo_filter` does not build on default x86-64 targets. gxhash 3.5 raises compile_error! unless aes+sse2 are enabled, and docs.rs builds of 0.5.26 and 0.5.27 failed for this reason, so recent versions have no hosted docs. Set RUSTFLAGS="-C target-cpu=native" (or +aes,+sse2) or use default-features = false.
- The README is wrong about the hasher and serialization. It says the default hasher is RapidHash and advertises optional serde, but the code uses gxhash::GxHasher (std SipHash with no hash feature) and supports bitcode only. The hasher field is skipped when encoding, so a filter built with a custom or seeded hasher decodes with H::default() and returns wrong answers. The gxhash docs also say hashes may change across its major versions and warn that the unseeded default hasher is open to DoS.
- The branchless one-load bucket path only applies while fingerprint bits x entries &lt;= 64 (16-bit fingerprints at 4 entries). Each growth layer adds one fingerprint bit, so an FPP below about 2.4e-4, or a fourth layer at the default 0.001, falls back to a per-entry loop.
- The usual cuckoo deletion hazards apply, and the README documents them at length. `add` stores duplicates. Removing a key that was never inserted can delete a colliding fingerprint and cause a false negative. `len()` is approximate.

## Known shortcomings

- Contenders use different hashers (default gxhash; the README says RapidHash); no LICENSE file; the gain is \~5.6x/\~4.0x on contains in its own README table (Apple M2 Max).
- The default gxhash feature makes a stock x86-64 build fail (compile_error!), and docs.rs builds for recent versions failed. The README is wrong (claims RapidHash and serde; code uses gxhash and bitcode only); the hasher is skipped on encode, so a custom/seeded hasher decodes as H::default() and gives wrong answers. The bench is positive lookups only on a \~38%-full filter in one pass (\~29 bits/key); the branchless single-load path is lost at FPP below \~2.4e-4 or at the 4th layer. 3 stars; the upstream MIT notice is missing; the crate's CI never runs.

## Caveats and trade-offs

The hasher differs per contender. autoscale defaults to gxhash (Cargo default feature, an AES-based hash; the README wrongly says RapidHash), scalable_cuckoo_filter uses its own default hasher, and cuckoofilter uses FarmHasher, so part of the gap is the hash function. contains measures only positive lookups. The table numbers come from single Instant-timed passes on one Apple M2 Max, not Criterion statistics. Measured FPP differs (0.17% vs 0.15% vs 0.27%), and cuckoofilter is given 10x capacity (1024 KB vs 353 KB). The upper README Performance table has no environment and disagrees with the generated Bench section and bench.json. The README says it was 'Forked from sile/cuckoo_filter', and that URL 301-redirects to sile/scalable_cuckoo_filter (MIT, 27 stars). It is a code copy, not a GitHub fork, relicensed as MulanPSL-2.0 (OSI-approved). No LICENSE file sits in the crate directory or the monorepo root; the license is declared only in Cargo.toml and the README. It lives in a monorepo with 3 stars and has 1,082 crates.io downloads.

cuckoo filter caveats apply (deletion can cause false negatives on double-delete/never-inserted keys, documented at length in README); part of a monorepo, not a standalone repo; comparison crates chosen by the author, not the canonical CMU cuckoo filter C++ reference

## Maintenance

Actively released (19 crates.io versions from 2025-12-29 to 0.5.27 on 2026-09-06), but it is a 3-star monorepo crate whose per-crate CI file sits in a subdirectory that GitHub Actions does not run. It is about 2,000 lines of Rust including tests, so it is easy to vendor under MulanPSL-2.0 once the gxhash build flags are handled.

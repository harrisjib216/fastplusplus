## Verdict

This is a size-only comparison on Mozilla's production CRLite data. The 2024-08-29 snapshot (816M certificates, 795 issuers, 11.7M revoked) encodes to an 8.5 MB clubcard, versus 19.3 MB for Mozilla's own multi-level Bloom filter cascade, 56% smaller. The IEEE S&P 2025 paper reports issuer-partitioned clubcards averaging 54% smaller than the cascades for 2024-10-29 to 2024-11-11. There is no compiler or query-speed comparison. The crate docs also cite a preliminary build of 8.5 MB in 200 s versus 19.8 MB in 293 s for the cascade (Ryzen 3975WX, 64 GB).

## Use it when

- Static set membership over a universe you can list in full at build time, such as revoked certificates among all CT-logged certificates, when in-universe keys must never be false positives.
- Filters shipped to many clients where bytes matter more than build time or per-query nanoseconds. CRLite ships a roughly 4 MB snapshot every 45 days plus 12-hour deltas.
- Data with a natural partition whose member density varies a lot across blocks, such as issuer or expiry hour. In the README's example, partitioning by issuer lowers the information-theoretic bound from 11 MB to 7.6 MB.
- Replacing a CRLite-style multi-level Bloom filter cascade that you already rebuild in batches.
- Snapshot-plus-delta distribution. A clubcard for R2\R1 inside U2 zstd-compresses to about 26 kB per 6-hour WebPKI delta when the previous snapshot is used as the dictionary.

## Skip it when

- Online inserts or deletes. Construction is batch-only, and the exact stage must see every element of U, not just the members. For streaming use, pick a Bloom, cuckoo or quotient filter.
- An open or unknown key universe, such as arbitrary strings. Answers are only defined for items in U: unchecked_contains is undefined outside it, and contains is only as good as the in_universe predicate you write.
- Hot paths that need nanosecond lookups. The paper puts a CRLite query at about 10 microseconds per clubcard (one SHA-256 plus some memory accesses), and query cost grows linearly with the number of delta clubcards. The crate has no published query microbenchmarks.
- Unpartitioned sets of uniform density. In the paper's simulation (n=1M, r=10k), clubcards were 10% above the optimum while Westerbaan's ncrlite was 1.4% above. Without partitioning, the win over Bloom shrinks to the Ribbon part alone: the README estimates an issuer-sharded Bloom cascade at about 13 MB versus 8.5 MB.
- Projects that need a stable API or wire format, or need to avoid serde. The README says neither the API nor the serialization format is stable. The crate is 0.x, has one main author, and requires serde (issue #6 asking to make it optional was closed). Blocks near 50% density also blow up in size: the paper's hypothetical 180M-certificate issuer grows from 0.29 MB to 25.4 MB if half its certificates are revoked.

## How it is fast

It uses Mike Hamburg's two-level cascade (RWC 2022). A Ribbon approximate filter, a homogeneous GF(2) system with k = floor(log2(|U\R|/|R|)) columns, cuts U down to R plus about |R| false positives. A one-bit Ribbon retrieval function over those survivors then corrects them, for roughly (k+2)|R| bits in total, where a Bloom cascade needs many levels. Both systems are solved by Dillinger-Walzer Ribbon banded elimination with back-substitution (band 64\*W bits, 256 in CRLite; epsilon 0.02). Each partition block (the issuer, in CRLite) gets its own ribbons, stitched into one matrix sorted by descending rank. Total size therefore tracks sum n_i\*H(r_i/n_i), which falls below the unpartitioned bound when member density varies across blocks. Blocks denser than one half are encoded by their complement using an inverted flag.

## Compared with alternatives

BuRR, RocksDB Ribbon, ribbonGo, xorf and xor_singleheader are approximate filters: they have a false-positive rate but need only the member keys. Pick Clubcard when you can enumerate the whole universe and need exact answers for every in-universe key, especially if a partition with uneven densities exists. For a general-purpose static approximate filter in Rust, xorf or a Ribbon implementation is simpler and has published speed numbers, which Clubcard does not.

## Gotchas

- Builds are not deterministic. Back-substitution fills free variables and the solution tail from thread_rng, so the same input gives different bytes each time. This matters for reproducible builds and binary diffing.
- You write the hash. AsQuery::as_query must return an Equation with s uniform in [0,m) and a[0]&1 == 1 (asserted). A weak hash causes insertion failures, which go into a per-block exceptions list that every query scans linearly.
- Answers are only exact for items inside U. When you combine a snapshot with deltas, merge the results in precedence order: member &gt; non-member &gt; no data &gt; not in universe.
- Epsilon is hard-coded at 0.02. Bumped ribbon retrieval (#2), false-positive herding (#3) and a compact index encoding (#5, about 50 kB saved) are open TODOs. The README says 8.5 MB is 12% above the bound and that about 8% is reachable.

## Known shortcomings

- The win is size (clubcards \~54-56% smaller than Bloom cascades for revocation sets), not lookup speed; designed for static certificate-revocation sets.
- Batch build only and it must enumerate the whole universe U (exact only inside U); unstable API and format, serde required, non-deterministic builds (thread_rng). Weak on uniform unpartitioned sets (+10% over optimum vs ncrlite's +1.4%); part of the win comes from issuer partitioning (a sharded Bloom is \~13 MB vs 8.5 MB); size blows up near 50% block density. No query-speed benchmark (\~10 us per clubcard query in the paper); epsilon hard-coded at 0.02.

## Caveats and trade-offs

This is a memory/size comparison from production snapshots, not a timing benchmark, so no CPU or compiler details apply. The baseline is Mozilla's own prior multi-level Bloom-cascade encoding of the same dataset, not a generic third-party Bloom filter. Part of the gain comes from partitioning revocations by issuer rather than from Ribbon versus Bloom: the README estimates an issuer-sharded Bloom cascade would be about 13 MB. The README warns that the API and serialization format are not stable. Peer-reviewed paper: Schanck, 'Clubcards for the WebPKI', IEEE S&P 2025.

Exact (no false positives for encoded set) membership filter built on Ribbon filters plus a two-level cascade; construction is offline/batch (not designed for online inserts like a classic Bloom filter). API and serialization format explicitly marked unstable ("work in progress").

## Maintenance

Active but slow-moving: a single-author Mozilla crate at v0.3.4 (2026-07-31), MPL-2.0, about 1,300 lines including tests, vendored in Firefox and the default desktop CRLite backend since Firefox 137. Fine to depend on, but pin the exact version because the API and format are declared unstable.

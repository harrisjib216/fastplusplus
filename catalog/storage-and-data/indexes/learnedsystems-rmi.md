## Verdict

The claim comes from the SOSD paper (PVLDB 14(1), Table 2): 200M 32-bit amzn keys, 10M random lookups, Xeon Gold 6230. There, the fastest CDFShop-tuned RMI took 180.90 ns per lookup at 48 MB, against 482.11 ns at 166 MB for the STX B+Tree, about 2.7x lower latency at about 3.5x less space. The SOSD harness is a CMake Release build with -ffast-math -march=native, but the paper names no compiler, and both hash tables beat RMI on point lookups.

## Use it when

- Immutable or bulk-rebuilt sorted arrays of 32/64-bit unsigned integers or doubles, such as read-only segments, lookup tables or analytics columns, where you look up the same data many times.
- Point or lower-bound lookups where you want lower latency than a B+Tree at a fraction of the memory: in SOSD, 181 ns at 48 MB vs 482 ns at 166 MB for STX B+Tree on 200M 32-bit amzn keys.
- Key sets with a learnable CDF (SOSD amzn, face, wiki), where the SOSD paper found learned indexes Pareto-optimal up to about 100 MB of index size.
- Read-heavy multithreaded lookup: in SOSD's 40-thread test with 50 MB models, RMI was the only learned index to out-throughput the radix lookup table (RBS).
- Build pipelines that can absorb an offline train, codegen and recompile step, and can ship the rmi_data/ parameter files with the binary.

## Skip it when

- Any inserts, deletes or updates. Each change means retrain, regenerate and recompile. Use ALEX or LIPP instead.
- Pure point lookups with memory to spare: in the same Table 2, CuckooMap (114.5 ns, 1.5 GB) and RobinHash (93.7 ns, 6.1 GB) are faster.
- Hard-to-learn key distributions such as OSM Hilbert-curve cell IDs. On osm, no learned index beat a plain radix table, and small RMIs were slower than binary search over the whole array.
- String or variable-length keys. Only u32, u64 and f64 inputs are supported, and 32-bit keys gain nothing because model math runs in 64-bit doubles.
- Frequent rebuilds or when you need a maintained, tested library. Build was the slowest of the learned indexes (80 s vs 38 s for PGM and 20 s for RS on the largest amzn size), and substantive development stopped in Aug 2020.

## How it is fast

It uses a two-stage Recursive Model Index (Kraska et al. 2018). A root model (linear, cubic spline, radix, normal-CDF, etc.) picks one of B leaf models, and that leaf's linear model predicts the key's position in the array. Each leaf's stored maximum error bounds a short binary search. Inference is a few `std::fma` evaluations with at most two cache misses, while a B-tree takes roughly one cache miss per level. The generator packs each leaf's error next to its parameters to save a cache miss, and hard-codes small layers as constants. The CDFShop optimizer (`--optimize`) searches model types and branching factors along the size/error Pareto front.

## Compared with alternatives

Pick RMI over RadixSpline (266.58 ns at 4 MB) or PGM-index (326.48 ns at 14 MB) when the lowest static lookup latency matters more than memory, build time and tuning effort; those two are tuned with two knobs and build faster. If you need inserts, use ALEX or LIPP. CARMI reports beating RMI on the SOSD platform, so benchmark it too.

| **Thread safety** | Not documented. Inferred from the generated code: lookup() only reads namespace-level globals set by load(), so concurrent lookups after load() look safe, and SOSD ran it at up to 40 threads. load() and cleanup() must not race with lookups. |

## Gotchas

- Only two-layer RMIs are implemented. A three-layer spec such as `linear,linear,linear` hits a bare panic!() (issue #5, not in the README). A radix root with branching factor 1-3 panics (issue #3, open), and very small inputs (\~100 keys) can trip an assertion in train_two_layer (issue #8, open).
- Correctness of the error bound on duplicate keys is in question. Open PR #14 (Jun 2026) says longest_run never records the final run of duplicates, so the per-leaf error bound can come out too small. Open PR #15 says the cargo unit tests no longer compile and that FixDupsIter feeds every model one phantom duplicate row. Neither is merged.
- Each generated index is a C++ namespace with global state and is tied to one dataset. Changing the data means regenerating code and recompiling. load() returns false if rmi_data/ is missing, and lookup() before load() reads unset parameters.
- Tuning decides performance. The README calls it critical, and poorly sized RMIs can lose to plain binary search. Inference is std::fma-based, and the repo builds with -march=native -ffast-math.

## Known shortcomings

- Read-only and not a container: it returns a position guess and error bound and the user does the last-mile search; any data change needs retrain, regenerate and recompile. Only the 2-layer implementation works (3-layer panics #5; radix root with branch 1-3 panics #3; \~100-key inputs assert #8). Open PR #14: duplicate runs can make the error bound too small; PR #15: cargo tests do not compile.
- 'Active' is misleading: no code changes from 2020-08 to 2026-05. Loses to hash tables on point lookups, poor on the osm dataset, slowest learned-index build (80 s vs PGM 38 s, RadixSpline 20 s). Little-endian, tested on x86 only.

## Caveats and trade-offs

The SOSD/VLDB'21 'Benchmarking Learned Indexes' paper states the CPU model and methodology, and the SOSD harness is public, but no compiler is named, so it is capped at Tier B. Table 2 numbers are for a 32-bit version of amzn and are the fastest (48 MB) RMI variant. Both hash tables (CuckooMap 114.50 ns / 1541 MB, RobinHash 93.69 ns / 6144 MB) are faster for point lookups. RMIs are read-only, need offline training, and take much longer to build than PGM/RS or B-Trees (Section 4.6). The RMI 'library' is a Rust compiler that emits C/C++ source files, and those generated files are what gets linked and benchmarked. The SOSD harness is GPL-3.0, while the RMI repo is MIT.

Read-only: RMI requires offline training and does not support inserts without a full retrain; must be tuned (branching factor, layer types) per dataset via the CDFShop optimizer; RMI build times are slower than PGM/RadixSpline per the same paper.

## Maintenance

Listed as active, but the commit log shows no code changes from Aug 2020 until May 2026, when a 2020 cleanup PR (#7, header guards) was merged. Fix PRs #14 and #15 are open. It is MIT-licensed, and the generated C++ is small and dependency-free to vendor, but regenerating needs the Rust toolchain.

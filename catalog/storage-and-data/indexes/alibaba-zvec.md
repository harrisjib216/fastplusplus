## Verdict

Alibaba's own VectorDBBench run of the zvec 0.1.1 PyPI wheel, in-process on a 16 vCPU / 64 GiB Alibaba g9i.4xlarge, using HNSW with int8 quantization (m=50, ef 118, fp32 refiner on Cohere 10M; m=15, ef 180 on Cohere 1M), reached 8,475 QPS (recall 0.933) on 10M and 16,490 QPS (recall 0.916) on 1M at concurrency 12-20. The rival rows are VectorDBBench's stored client-server results measured by Zilliz on Xeon Platinum 8375C hosts: Milvus 2.5.11 sq8 437 / 3,465 QPS, Milvus 2.2.12 HNSW 179 / 1,259 and Zilliz Cloud 8cu 3,957 / 9,704, so only the Zilliz Cloud comparison (about 2.1x and 1.7x, derived from page data) is at matched recall.

## Use it when

- An application (Python, Node.js, Go, Rust, Dart or C++) that needs local approximate nearest-neighbour search over up to roughly 10M 768-dimensional embeddings on one machine, without operating a Milvus or Qdrant server.
- Local-first RAG, agent memory or code search where vectors, scalar filters and keyword full-text search must be combined in one query against one on-disk collection.
- Read-heavy serving in which several worker processes query the same collection read-only (mmap) while one process does the writes.
- You can accept recall@100 around 0.92-0.93 from int8 HNSW in exchange for throughput, or can afford fp32/refiner settings and tune ef upward for higher recall.
- Edge or mobile deployments: since v0.7.0 releases ship prebuilt SDK binaries for Linux (glibc and musl), macOS, Windows, Android and iOS.

## Skip it when

- You need a distributed, replicated or multi-writer service; Zvec is single-node, and writes to a collection are exclusive to one process.
- You need the recall levels of the Milvus HNSW rows (about 0.98): the published configuration reached 0.933 (10M) and 0.916 (1M), and no iso-recall curve against Milvus was published.
- You only want a small ANN index library to vendor: Zvec pulls in Arrow, RocksDB, ANTLR, glog and a dozen other submodules; FAISS or hnswlib are leaner, and no Zvec-versus-FAISS/hnswlib numbers exist (issue #159 is open and deferred).
- ARM64 with INT8 flat search, where INT8 was reported 2.3-4x slower than FP32 on Apple Silicon (issue #719, open), or AVX2-only x86 CPUs on early wheels (v0.1.1 crashed with SIGILL on Broadwell, issue #92).
- You need a long-stable API and storage format: the project is v0.x (0.1.1 in January 2026 to 0.7.0 in August 2026) with recent concurrency crash fixes.

## How it is fast

Search is HNSW (the parameter keys are still named proxima.hnsw.\*, consistent with Alibaba's Proxima engine as its origin): a greedy descent through the upper layers, then a beam search on level 0. On current main the level-0 loop has a specialised fast path for mmap-backed contiguous storage that collects all unvisited neighbours, software-prefetches their vectors (by default every cache line of each vector), scores them with one batched SIMD distance call and keeps candidates in an AVX2 BlockHeap or a linear pool instead of the classic two-heap scheme. The benchmarked setup adds int8 scalar quantization (only the quantized vectors are held in memory, fp32 originals stay on disk) and an optional refiner that re-scores the ef candidates against the fp32 vectors; SIMD distance and quantizer kernels live in src/turbo with AVX2/AVX-512 paths. Running in-process removes the RPC, serialization and network hop that the client-server rivals pay per query. Note that the benchmark ran v0.1.1, so not every one of these main-branch paths was in the measured build.

## Compared with alternatives

No vector-search siblings are catalogued in this category: the siblings are ordered and learned key indexes (ALEX, PGM-index, LIPP, HOT) and embedded key-value stores (TidesDB, redb, libmdbx), none of which do nearest-neighbour search. Against FAISS (catalogued under autodiff-and-ml-kernels), pick Zvec when you want a persistent embedded database with WAL, filters, full-text search and multi-language SDKs rather than an in-memory index library; there are no head-to-head numbers.

## Gotchas

- Harness asymmetry: VectorDBBench ran Zvec in-process, with 12-20 spawned Python processes each opening the collection read-only through mmap on the same 16 vCPU g9i.4xlarge (Intel Granite Rapids according to a search snippet; the docs name no CPU), while the Milvus and Zilliz Cloud rows are Zilliz's stored client-server results from Xeon Platinum 8375C (Ice Lake) hosts. Hardware generation, deployment model and network hop all differ, so the ratios are not engine-versus-engine.
- The 19x and 47x Milvus ratios are not iso-recall (Zvec 0.933 vs Milvus sq8 0.951 and Milvus HNSW 0.984 on 10M); only Zilliz Cloud 8cu matches recall, at about 2.1x (10M) and 1.7x (1M) QPS, derived from page data. The 10M run also used the fp32 refiner while the 1M run did not.
- The benchmarked v0.1.1 int8 quantizer had a correctness bug: SQ8 sum/squared-sum metadata was computed from pre-rounded floats (issue #328, fixed by PR #329 on 2026-04-16). It cut recall on skewed data (OpenAI 1536D50K: 0.7377 before, 0.9588 after); maintainers reported no regression on Cohere 768D, and the bug lowers recall rather than inflating QPS, but the published numbers were measured on code later fixed in the quantizer hot path.
- Quantization keeps both the fp32 and the quantized copy on disk, so storage grows; the refiner re-reads fp32 vectors, which needs them in page cache (about 31 GB for Cohere 10M, derived) to keep latency low.

## Known shortcomings

- First-party v0.1.1 run read from chart images: the Milvus rows are stored VectorDBBench results from other hardware (Xeon Platinum 8375C, client-server), not iso-recall; only the Zilliz Cloud row matches recall (2.1x/1.7x derived). The Proxima claim was not found in the README or docs. CPU model not stated; no FAISS row.
- Enricher: rival rows are Zilliz's stored client-server VectorDBBench results on a Xeon 8375C (Ice Lake) while Zvec ran in-process on g9i (Granite Rapids per a snippet); not iso-recall vs Milvus; the benchmarked v0.1.1 int8 quantizer had an SQ8 metadata bug (#328, fixed by PR #329 on 2026-04-16; lowers recall, does not inflate QPS); the v0.1.1 wheel needed AVX-512 (#92 SIGILL); no FAISS or hnswlib comparison (#159 deferred).

## Caveats and trade-offs

First-party numbers. The docs site zvec.org was not opened; the figures were read from the PNG charts embedded in the SVGs of the zvec-ai/zvec-web docs repo (qps-10M.svg, recall-10M.svg, load-duration-10M.svg, qps-1M.svg, recall-1M.svg) and the reproduction steps from content/docs/en/db/benchmarks.mdx in the same repo. The rival rows are VectorDBBench's stored standard results (vectordb_bench/results has Milvus, ZillizCloud and other directories but no Zvec results), measured by Zilliz with a client-server path on Xeon Platinum 8375C hosts, while Zvec ran in-process on an Alibaba g9i.4xlarge, so hardware and deployment differ. Not iso-recall: Zvec recall is 0.9328 (10M) and 0.9164 (1M) versus 0.951 and 0.9528 for Milvus sq8 and 0.9843 and 0.9799 for Milvus HNSW, so the 19x to 47x Milvus ratios partly buy lower recall. At matched recall the fairer comparisons are Zilliz Cloud 8cu (recall 0.932 vs 0.9328 on 10M, 0.9169 vs 0.9164 on 1M), about 2.1x and 1.7x QPS (derived from page data), and on 10M QdrantCloud-16c64g-1.14.1 (recall 0.9357, 446.9 QPS), about 19x (derived from page data). Milvus versions are mixed (2.2.12 and 2.5.11). Zvec version is v0.1.1 (PyPI upload 2026-01-28); the current release is v0.7.0. The README embeds only a QPS chart. FAISS is not in this comparison. CPU model not stated, so not tier A.

In-process embedded library: no server, but writes are single-process exclusive (multiple processes may read the same collection). Benchmarked configuration trades recall for speed with int8 quantization plus a refiner. SDKs for Python, Node.js, Go, Rust and Dart.

## Maintenance

Actively developed (v0.7.0 on 2026-08-24, last commit 2026-09-29, 443 commits, 16.1k stars) and Apache-2.0, usable from C++ through shared libraries, but it is a young v0.x database with a heavy vendored dependency tree and recently fixed concurrency crashes (#714, #580), so pin a release and re-run VectorDBBench on your own hardware before relying on the published ratios.

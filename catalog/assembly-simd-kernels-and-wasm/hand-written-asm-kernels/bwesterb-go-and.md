## Verdict

With the repo's benchmark.sh (go test -count=10, benchstat) on an Intel Core i9-13900 under Linux, Go gc with default flags and an unrecorded Go version, And/Or/Xor/AndNot on 32,000-byte buffers took about 361 ns per call versus 6,943 ns for a naive byte loop (19x) and 2,826 ns for the uint64 purego build (7.8x); Popcnt on 1 MB took 22.5 us versus 177.5 us naive and 66.5 us purego (2.95x), for geomeans of 15.4x over naive and 5.1x over purego (derived from page data). An older Apple M2 Pro table (NEON) gives a geomean of 21x over naive and 4.6x over purego (derived from page data).

## Use it when

- Go code doing bitmap/bitset algebra on byte slices of a few hundred bytes or more: bloom filters, roaring-style dense containers, posting-list bitmaps, image masks.
- Hot loops that intersect two bitmaps and only need to know whether the intersection is non-empty (AnyMasked) or its cardinality (PopcntMasked), without materialising the result.
- amd64 servers with AVX2 (Haswell and later) or Apple Silicon / other arm64 where the NEON And/Or/Xor/AndNot/Popcnt paths exist.
- Cache-resident working sets (the measured 80+ GiB/s rows use 32,000-byte buffers); this is where SIMD beats a scalar Go loop by the largest margin.

## Skip it when

- Slices under 256 bytes: the SIMD loops only run on whole 256-byte blocks for and/or/xor/andnot/not/any (128-byte with AVX1), so short slices fall through to the uint64 Go loop plus a non-inlinable call.
- XOR only: Go's own crypto/subtle.XORBytes is already assembly (16-byte SSE2 loop on amd64, 64-byte NEON loop on arm64) and was not part of go-and's benchmark, so the gap there is unmeasured and likely much smaller than the README's naive-loop ratio.
- Fastest possible popcount on x86: amd64 Popcnt is scalar POPCNTQ summed into one register (no AVX2 Harley-Seal or VPSHUFB method); issue #17 asking for the Mula-Kurz-Lemire AVX2 popcount has been open since July 2024.
- arm64 users who need Not, Any, AnyMasked or PopcntMasked fast: on arm64 these are pure-Go fallbacks (TODO comments in and_arm64.go).
- C/C++ projects: this is a Go package with Go-ABI assembly, not callable from C++ (and maturity is low: 2 stars, no tagged releases).

## How it is fast

The Go gc compiler does not auto-vectorize, so a byte or uint64 loop runs scalar; go-and replaces the bulk of each slice with unrolled SIMD loops (eight 32-byte VMOVDQU/VPAND-style ops per 256-byte block on AVX2, a 128-bit AVX1 variant, sixteen 16-byte NEON registers per 256-byte block on arm64) and finishes the tail with a uint64 Go loop. Any/AnyMasked use VPTEST with an early exit; amd64 Popcnt is an 8-way unrolled scalar POPCNTQ loop and arm64 Popcnt uses NEON CNT with byte-lane adds and UADDLV. CPU features are picked at run time via golang.org/x/sys/cpu, or at compile time with GOAMD64=v2/v3; the amd64 assembly is generated by avo (internal/asm/src.go), the arm64 assembly is hand-written.

## Compared with alternatives

Pick go-and in Go code that needs whole-slice AND/OR/XOR/ANDNOT, any-bit tests or total popcounts; cespare/xxhash is the same asm-versus-purego Go pattern for hashing, and pospop (clausecker) is the better choice when you need positional (per-bit-index) popcounts or AVX-512/AVX2 counting, since go-and's amd64 popcount is scalar POPCNT.

## Gotchas

- Two-input functions panic unless all slices have equal length; Popcnt, Any and Memset do no length checks. Exact in-place use (dst == a) works and is what the benchmarks do; partially overlapping slices are not documented and the 256-byte block load-then-store order would differ from a byte loop.
- Benchmark harness caveats: the headline 15x geomean is against a one-byte-at-a-time loop; against the uint64 purego build it is about 5.1x (i9-13900) and 4.6x (M2 Pro), derived from page data. And/Or/Xor/AndNot/Any rows use 32,000-byte buffers (L1/L2 resident), Popcnt rows 1,000,000 bytes, Any/AnyMasked scan all-zero buffers (worst case), the purego build runs at default GOAMD64 (v2/v3 not measured), the Go version is not printed, and the hybrid i9-13900 run is not pinned to a P-core. No correctness bug found in the measured code: tests compare every SIMD function with the naive loop for sizes 1 to 2^19 plus random tails.
- amd64 Popcnt (41.4 GiB/s on the i9-13900) runs at about half the arm64 NEON Popcnt rate (82.4 GiB/s on the M2 Pro); its single-accumulator add chain caps it near 8 bytes per cycle (estimate), so the 2.95x win over purego is from unrolling, not SIMD.
- CI (GitHub Actions, ubuntu-latest) runs the tests only on amd64; the arm64 NEON path is only compiled in CI, never executed, and the Apple M2 Pro table dates from August 2024 (it has a Memset row and no Any, AnyMasked or PopcntMasked rows).

## Known shortcomings

- Naive-loop baseline inflates the headline (the purego column is about 5x geomean, derived); 32 KB cache-resident buffers; the M2 Pro table is from an older run; Go version unrecorded (go.mod 1.24.0); only the arm64 NEON kernels are hand-written, amd64 is avo-generated. Go-only library.
- Enricher: headline is against a byte loop (the purego gap is only about 5.1x geomean on an i9-13900, 4.6x on an M2); the amd64 Popcnt is scalar POPCNTQ with one accumulator (41.4 GiB/s vs 82.4 on M2 NEON; issue #17 on AVX2 popcount open since 2024-07); arm64 Not/Any/AnyMasked/PopcntMasked are pure-Go fallbacks and CI never runs tests on arm64; Go's crypto/subtle.XORBytes (SSE2/NEON asm) was never benchmarked; 32,000 B cache-resident buffers, Any on all-zero buffers, Go version unrecorded; tests check every SIMD function against the naive loop.

## Caveats and trade-offs

Baseline is a deliberately naive byte loop; the stronger comparison is the uint64-wise purego column (derived from page data: asm about 7.8x faster than purego on And-32 2825.5ns vs 360.8ns, about 2.95x on Popcnt-32 66.45us vs 22.49us, geomean about 5.1x on the i9-13900 and about 4.6x on the M2 Pro). The amd64 AVX2 assembly is generated by avo programs in internal/asm (and_amd64.s carries a 'Code generated ... DO NOT EDIT' header); the arm64 NEON code in and_arm64.s is hand-written Go assembly. The and/or/xor/andnot/any benchmarks run on 32,000-byte buffers (a commit of 2024-08-04 moved to 32K buffers 'so we're less memory constrained'), so the 80+ GiB/s rows are cache-resident; popcount rows use 1,000,000-byte buffers; Any benchmarks use an all-zero buffer (full scan, worst case). The Apple M2 Pro table comes from an older run: it has a Memset row that the current benchmark.sh no longer runs and lacks the Any, AnyMasked and PopcntMasked rows. The baseline is Go gc output, not a C/C++ -O3 compiler, and the library is a Go package (not directly callable from C++). Very small repo (2 stars, 2 forks).

AVX2 required on amd64 (runtime dispatch, AVX variants also generated) and NEON on arm64; pure-Go fallback via purego tag; amd64 and arm64 only; function-call overhead dominates tiny slices (Go never inlines asm).

## Maintenance

Active (last commit 2026-07-26, PRs from three contributors, CI on Go 1.25) and MIT-licensed, small enough to vendor, but it has 2 stars, no tagged releases and an untested arm64 path in CI.

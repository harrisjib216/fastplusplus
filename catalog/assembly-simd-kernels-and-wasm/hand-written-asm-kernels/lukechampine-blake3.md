## Verdict

Author's go test -bench output from August 2020, with no Go version or flags, on a CPU labelled '2020 MacBook Air (i5-7600K @ 3.80GHz)', a label the AVX-512 listing contradicts. Sum256 of 64 KiB took 16.2 us with AVX-512 (4.0 GB/s), 31.1 us with AVX2 (2.1 GB/s) and 133.5 us in pure Go (0.49 GB/s), about 8.2x and 4.3x; streaming Write and XOF throughput gained 4-8x, and 64 B and 1 KiB inputs gained nothing. The code was single-threaded then, and the baseline is the same package's pure-Go compressor built by gc.

## Use it when

- Hashing large buffers or streams (tens of KiB and up) in Go on x86-64 with AVX2 or AVX-512: in the author's 2020 run, Sum256 of 64 KiB reached 4.0 GB/s (AVX-512) and 2.1 GB/s (AVX2) against 0.49 GB/s in pure Go.
- Long XOF output (key streams, deterministic random bytes) on x86-64, where one SIMD call produces 16 output blocks (1 KiB): 4.2 GB/s vs 0.53 GB/s in pure Go.
- Content addressing or verified streaming that needs Bao encode/decode, slices or chunk groups in pure Go without cgo.
- Batch jobs that hash a few very large inputs and are glad to use every core per hash (v1.4.0 and later parallelize Write and XOF).

## Skip it when

- Inputs up to about 1 KiB (keys, short messages): there is no single-block assembly, so 64 B and 1 KiB inputs run the same pure-Go code on every CPU (README 'Shortcomings'; issue #21 still open).
- arm64 (Apple Silicon, Graviton) or x86 without AVX2: pure Go only, with no NEON or SSE4.1 kernels.
- Servers already saturating their cores with many concurrent hashes: since v1.4.0 every Write longer than 1 KiB allocates a slice and starts goroutines, and there is no single-threaded option.
- Decisions that need current numbers: the README figures come from August 2020 code, before the 2021 avo regeneration, the April 2024 VZEROUPPER fix for the AVX2 routines and the 2025 goroutine path.
- Builds pinned to v1.4.0: that release is retracted because it returned wrong hashes for some split writes.

## How it is fast

BLAKE3 cuts the input into 1 KiB chunks that are leaves of a binary Merkle tree, so independent chunks can be compressed side by side in SIMD lanes. compressChunksAVX512 hashes 16 chunks per call (MaxSIMD = 16, 'AVX-512 vectors can store 16 words') and compressChunksAVX2 hashes 8, both with all 7 rounds inlined; an AVX2 kernel merges parent nodes 8 at a time, and XOF output compresses 16 successive counter values of the root node at once. The assembly is generated by Go programs using mmcloughlin/avo, not written by hand. Since v1.4.0 (February 2025) Write also compresses each power-of-two subtree (eigentree), and each 16 KiB group inside it, in its own goroutine, and large XOF reads are split across up to runtime.NumCPU goroutines.

## Compared with alternatives

Against zeebo/blake3 (AVX-512, AVX2, SSE4.1 and NEON kernels, with an assembly gain even at 64 B in its own tables), pick this package for Bao verified streaming, a seekable XOF, or built-in multi-core hashing of large inputs on amd64, and zeebo/blake3 for arm64, SSE4.1-only CPUs or small inputs. Use cespare/xxhash when a non-cryptographic hash is enough.

## Gotchas

- Benchmark labelling: BenchmarkWrite streams b.N KiB through io.CopyN, so each Write call receives io.Copy's 32 KiB buffer, and the 2020 BenchmarkXOF read through ioutil.Discard's 8 KiB buffer. The ns/op figures are per KiB streamed, not the cost of 1 KiB writes or reads. The 64 B and 1 KiB rows are identical in all three listings (120 ns and 2229 ns, MB/s to the hundredth), so they were pasted rather than re-run. Neither the 2020 nor the current code has a flag or build tag that selects AVX2 or pure Go on an AVX-512 machine, so producing those listings meant editing the source. The labelled CPU (i5-7600K, no AVX-512) cannot have run the AVX-512 listing.
- The current code is not the measured code. Write and Sum on inputs over 1 KiB have used goroutines since v1.4.0 (the 2020 blake3.go has none). CompressEigentree starts one goroutine per 16 KiB group with no cap; only XOF output is capped at runtime.NumCPU. A single Write with a 512 MiB subtree starts 32,768 goroutines (derived from the code). Re-running the benchmarks today on a multi-core machine measures parallel throughput, which cannot be compared with single-threaded BLAKE3 figures.
- v1.4.0 (2025-02-24) is retracted in go.mod. Its parallel Write consumed a partly filled buffer greedily, so Sum depended on how the input was split across Write calls; 83c0fac (v1.4.1, 2025-05-08) fixed it, and TestSplitWrite now checks every split point of a 2 KiB input.
- New(size, key) returns no error: a key shorter than 32 bytes panics, and a longer key is silently truncated to its first 32 bytes. OutputReader.Seek panics on an invalid whence, which the maintainer kept on purpose (issue #16).

## Known shortcomings

- README numbers date from 2020 with no Go version and a contradictory CPU label; the SIMD path starts at 2 KiB (identical 64 B and 1 KiB rows); the Split-Write fix landed 2025-05-08; the assembly is avo-generated, not hand-written. Go-only.
- Record correction: the Write and XOF rows are not 1 KiB writes; BenchmarkWrite streams through io.CopyN in 32 KiB calls and the 2020 XOF read through ioutil.Discard's 8 KiB buffer, so ns/op is per KiB streamed; no flag or build tag selects AVX2 or pure Go, so those listings needed source edits, and the identical 64 B and 1 KiB rows were pasted. The current code is not the measured code: since v1.4.0 Write and Sum spawn goroutines with no cap (32,768 for a 512 MiB subtree), so re-runs measure multi-core throughput; v1.4.0 was retracted for wrong hashes on split writes (fixed in 83c0fac); the AVX2 numbers predate the April 2024 VZEROUPPER fix. A short key panics and a long key is silently truncated.

## Caveats and trade-offs

Author's own run from August 2020 (README benchmark sections were added in commits of 2020-08-01 to 2020-08-10 and not updated since): no Go version or flags, and the CPU line ('2020 MacBook Air (i5-7600K @ 3.80GHz)') is contradictory, since the i5-7600K is a desktop part without AVX-512. The identical 64 B and 1 KiB rows are explained by the code: guts/compress_amd64.go uses the AVX-512/AVX2 paths only for buffers of at least two chunks (2 KiB), and the README says there is no assembly routine for single-block compressions, so small inputs run pure Go in all three builds; identical ns values suggest one run was pasted. Later code differs from the measured version: a goroutine-parallel path (PR #25, 2025) and a split-Write correctness fix (83c0fac, 2025-05-08, with the buggy version retracted). Baseline is the package's own pure-Go path, not a third-party library. The assembly is generated by avo, not hand-written.

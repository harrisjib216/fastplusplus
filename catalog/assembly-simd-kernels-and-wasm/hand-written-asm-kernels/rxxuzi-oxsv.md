## Verdict

The author's own run used WSL2, an unnamed Intel Core CPU, DDR4-3200, and an xsv of unstated version and build. It covered a generated 1 GB CSV (6.27M rows, 18 columns, no quoted fields), best of 3 after a warmup, with outputs discarded to /dev/null: count 0.17 s vs 13.14 s (76x), select 0.82 vs 19.27 s, search 1.31 vs 25.63 s, stats 12.97 vs 74.25 s (5.7x). xsv's 13.14 s count is about 82 MB/s, far below xsv's own published 414 MB/s, and oxsv count only popcounts newline bytes. The shipped test/bench.sh cannot reproduce the table: it times a 500 MB file, has no fmt row, and also times `wc -l`, which the published table omits. In the 'SIMD microbenchmark', the baseline is naive gcc -O2 byte loops (not memchr). Its count buffer holds 1/256 newlines rather than the commented \~6%, and parse_get_field is itself a scalar byte loop, so its \~2.5x gain is not a SIMD effect.

## Use it when

- Counting rows, peeking at headers or the first rows, or pulling columns from multi-GB machine-generated CSV known to contain no quoted fields, on a local file under Linux x86-64 with AVX2.
- Exact-match or integer-threshold row filtering (search -s COL PAT, --gt/--lt) over such files, where xsv's regex engine and full CSV parse are unnecessary.
- Reading NASM AVX2 byte-scan kernels (src/core/scan.asm) as a compact example of vpcmpeqb + vpmovmskb + popcnt counting.

## Skip it when

- Any CSV that may contain quoted fields. Commas or newlines inside quotes split fields and rows, because quoted parsing is not implemented (see gotchas) even though the README documents a --quote flag.
- Piped or streamed input (stdin, S3 copies). Every command maps a named file, so the README's `aws s3 cp ... - | oxsv search --no-mmap` example cannot work.
- Numeric work on decimals or dates: stats has only Integer and Unicode types, sort -N and search --gt compare 64-bit integers, and the integer parser silently truncates (see gotchas). The sort is an unstable heapsort, unlike xsv's stable sort_by, so rows with equal keys can come out in a different order.
- Platforms other than Linux x86-64, since it calls raw Linux syscalls. On x86-64 the SSE2 fallback still runs popcnt unconditionally, and AVX2 is selected from CPUID leaf 7 without an OSXSAVE/XGETBV check.
- Production pipelines: 6 commits over two days (2026-02-28 to 2026-03-01), 0 stars, no issues, and a compat test of 14 cases on small fixtures that skips itself when xsv is not installed.

## How it is fast

Newline and delimiter scanning compares 32 bytes at a time with AVX2: vpcmpeqb, then vpmovmskb, then popcnt to count or bsf to find the first match, in a 128-byte unrolled counting loop. A CPUID check at startup chooses AVX2 or an SSE2 fallback. Files are mapped with MAP_POPULATE and MADV_SEQUENTIAL, or lazily for head and headers, so no read() copies or allocator are involved. The tool does far less than xsv: there is no RFC 4180 state machine and no UTF-8 validation, count is a single newline popcount over the whole file, and field extraction is a plain scalar byte loop.

## Compared with alternatives

No catalogued sibling is a CSV tool. The nearest analogues are chingrep (a CLI measured against ripgrep) and asmjson (an assembly parser measured against Rust crates). Pick oxsv over plain xsv only for count, head, select and exact-match search on local CSV known to be unquoted, where skipping a full RFC 4180 parse is acceptable.

## Gotchas

- Two documented flags do nothing. --quote/-q is in the README flag table, but main.c never parses it (unknown pre-command flags are skipped silently), and no assembly file reads oxsv_quoted, which oxsv_init sets to 0. main.c does parse --no-mmap and set oxsv_no_mmap, but no command reads it, and every command calls mmap_open on a path. The verifier's note that quoting is 'off unless --quote is given' is wrong: it is never available.
- num_parse_i64 (src/core/num.asm) accepts any leading-digit prefix as a valid integer, with no overflow check. '35.123456' parses as 35 and '2024-01-15' as 2024. stats therefore reports latitude, longitude and date columns as Integer with truncated min, max and mean, and sort -N and search --gt/--lt compare those truncated values.
- scan_count_byte accumulates its count in the 32-bit r15d register. count and index (the index loop also compares against r12d) therefore wrap or truncate past 4,294,967,295 newlines, which a narrow-row file of tens of GB can reach. count is a raw count of newline bytes, not of CSV records.
- oxsv index writes its own 'OXSV' header, offset and footer format to &lt;file&gt;.csv.idx. xsv's util::idx_path uses the same name, and config.rs opens that file automatically whenever it is newer than the CSV. Running xsv on a file after oxsv index makes xsv read oxsv's index as its own.

## Known shortcomings

- BENCHMARKS.md (gcc -O2, CPU only 'Intel Core' under WSL2): the xsv baseline looks crippled (xsv count ran about 82 MB/s vs 413.76 MB/s in xsv's own BENCHMARKS.md, derived); the default parse ignores quotes and count only counts newlines; the C baseline is a naive loop, not memchr; the shipped bench.sh times 500 MB, not the published 1 GB.
- Record correction: --quote/-q and --no-mmap are no-ops (main.c never parses --quote and no assembly reads oxsv_quoted or oxsv_no_mmap), so quoted-field parsing is never available and there is no stdin or pipe path. num_parse_i64 accepts any leading-digit prefix ('35.12' becomes 35, '2024-01-15' becomes 2024), so stats, sort -N and search --gt are wrong on decimals and dates; scan_count_byte's 32-bit accumulator wraps past 4,294,967,295 newlines; oxsv index writes its own format to &lt;file&gt;.idx, a path xsv auto-loads; the heapsort is unstable while xsv's sort is stable. bench.sh times wc -l but the table omits it; the parse_get_field microbench is scalar asm vs scalar C.

## Caveats and trade-offs

No CPU model (only 'Intel Core' under WSL2), no gcc version, no xsv version or build, no run-to-run spread. The xsv baseline ran far below xsv's own published throughput: 1 GiB in 13.14 s for count is about 82 MB/s and index about 75 MB/s, versus 413.76 MB/s and 379.28 MB/s in xsv's BENCHMARKS.md on an i7-6900K (derived from page data), which points at a slow WSL2 file path or build rather than parsing cost, so the 5.7-76x ratios are likely inflated. oxsv does less work by default: count only counts newline bytes, and quoted-field parsing is off unless --quote is given, whereas xsv always runs a full RFC 4180 parser; the generated test data has no quoted fields, so outputs agree here but would differ on CSV with quoted commas or newlines. search is exact match versus xsv's regex. oxsv memory-maps the file (an I/O strategy difference).

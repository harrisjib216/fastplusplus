## Verdict

No measurement exists: the README states that minias's performance is 'often better than gnu as and much better than the clang assembler', with no input files, timings, versions, build flags or hardware, and the repository contains no benchmark script; an independent search found no third-party numbers either.

## Use it when

- Bootstrapping or teaching a small C toolchain (cproc/QBE, chibicc) where a readable, hackable assembler matters more than full GNU as compatibility.
- Assembling plain C compiler output (-S without -g) for x86-64 Linux ELF objects, piped as 'cc -S -O2 file.c -o - | minias -o file.o -'.
- As a reference implementation of x86-64 instruction encoding and ELF relocatable output that fits in a few files under the ISC licence.
- When you want to measure for yourself whether a minimal assembler shortens build time on very large generated .s files; no published numbers exist to rely on.

## Skip it when

- C++ compiler output: the grammar has no COMDAT group sections ('axG',...,comdat) and no TLS relocation suffixes (@tpoff, @gottpoff, @tlsgd), so inline functions, templates and thread_local fail to assemble.
- Code that needs unwinding or debug info: .cfi_\* directives are silently discarded (no .eh_frame is produced), and -g output fails because .loc and .uleb128 are not in the grammar.
- AVX, AVX2 or AVX-512 code: the grammar has SSE (xmm) forms but no ymm/zmm or VEX/EVEX instructions, so -mavx2 or -march=native output fails; the roadmap item to test every opcode variant is still open.
- As a drop-in 'as' behind gcc or clang: any '--' option such as gcc's '--64' prints usage and exits, so a wrapper script is needed.
- Anywhere a speed claim must be backed: the only evidence is one README sentence with no workload, versions or machine.

## How it is fast

It does little work: the parser is generated by the vendored Minipeg (derived from Ian Piumarta's peg/leg), the whole file is parsed once into a linked list of interned statement values (a 4,096-entry direct-mapped cache built on murmurhash64a), and it then encodes instructions directly with REX/ModRM/SIB helpers and writes the ELF file. It never frees memory, keeps state in globals, and runs a fixed number of jump-relaxation passes (one by default) using worst-case label offsets instead of iterating to a fixed point. The author says the parser is the bottleneck; no profile or timing is published.

## Compared with alternatives

Pick minias over aron (Mach-O, macOS as baseline) when you need Linux ELF objects, and over Asmc, JWasm or UASM when your input is AT&T-syntax compiler output rather than MASM source; unlike Keystone it is a standalone program, not an embeddable library.

## Gotchas

- Silently ignored directives: .cfi_\*, .file, .ident, .type and .size parse to no-ops, so objects have no .eh_frame unwind tables and symbols are emitted without a function/object type or size (only .comm symbols get STT_OBJECT). Exceptions or backtraces through these frames, and tools that rely on symbol sizes, are affected without any error.
- Unsupported syntax fails loudly ('syntax error' at a line number) rather than misassembling, so trial builds show quickly whether a codebase fits the supported subset.
- Jump relaxation runs one extra pass by default using worst-case offsets; output is correct but may keep long jumps that more passes would shorten (raise with -r iter). '-r' given as the last argument with no value passes NULL to atoi and crashes.
- The speed sentence ('often better than gnu as and much better than the clang assembler') dates from the 2021 README, when the parser was generated by peg/leg; it was carried unchanged through the May 2026 switches to PackCC and then Minipeg, so it describes neither the current parser nor current GNU as/clang versions. test/test.sh only compares .text bytes against clang's encoding and times nothing.

## Known shortcomings

- One qualitative README sentence only ("often better than gnu as, much better than clang assembler"), no numbers or benchmark code (test/test.sh checks encodings against clang); hobby project with unfinished opcode coverage, 231 stars.
- Enricher: the speed sentence was written in 2021 under the peg/leg parser and carried unchanged through the 2026 PackCC and Minipeg swaps with no numbers anywhere; the grammar lacks COMDAT, TLS relocations, AVX/ymm/zmm, .loc and .uleb128, so most C++ and -g output fails; .cfi_\*, .type and .size are silently dropped (no .eh_frame); rejects gcc's --64; -r with no value crashes (atoi(NULL)).

## Caveats and trade-offs

Only evidence is one README sentence with no numbers, versions, machine or workload; the repo has no benchmark script (test/test.sh is an encoding-correctness test that uses clang as the reference). The author ranks speed third among goals (simple, tiny, fast) and says performance is limited by the generated parser; the parser generator was swapped (PackCC, then vendored Minipeg) in May 2026 and the speed sentence was last edited in that commit, so any measurement behind it is unpublished. Roadmap items still open: simple immediate expressions, self-hosting with chibicc, and testing every opcode with all variants. Hobby project ('written for fun and learning'), 231 stars, not widely referenced.

Supports a practical subset of AT&T x86-64 only; ELF relocatable output; not a library; deliberately omits many GNU as extensions and does not free memory (OS reclaims). Parser is generated by Minipeg from a PEG grammar and is the stated speed limiter.

## Maintenance

Active hobby project (last commit 2026-06-24, 231 stars, 16 forks, ISC licence, no issues filed) and small enough to vendor, but its speed claim is directional only and it covers C compiler output rather than general C++ or SIMD-heavy code.

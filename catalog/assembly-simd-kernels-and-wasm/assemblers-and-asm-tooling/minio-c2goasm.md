## Verdict

README benchcmp output (Go 1.7.5 and 1.8.1, GOMAXPROCS 12 per the -12 suffix, CPU unstated): calling one AVX2 fused multiply-add over 8 floats through cgo took 382 ns (Go 1.7.5) and 236 ns (Go 1.8.1) per call, against 10.9 ns through the c2goasm-converted assembly, about 35x and 22x (derived from page data). This measures per-call overhead, including probable per-call allocation on the cgo side, not the quality of the generated code.

## Use it when

- Go amd64 code that calls a small C/C++ SIMD kernel many times with little work per call, where a cgo call (236-382 ns in the README's Go 1.7/1.8 runs) would dominate.
- You want the package to build as pure Go (no C toolchain, easy cross-compilation for users) while keeping clang-optimized intrinsics or template code; the generated .s is committed.
- Leaf functions compiled by clang with at most 14 arguments, each a 64-bit value or pointer, that call nothing except memset or memcpy.
- Maintaining existing code generated by c2goasm, such as fwessels/go-cv-simd.

## Skip it when

- New projects: the repository was archived on 2021-12-01 (last commit 2019-08-12); gocc (kelindar/gocc) and GoAT (gorse-io/goat) credit c2goasm and are the maintained successors, and GoAT's page lists amd64, arm64, riscv64, loong64, s390x and ppc64le.
- Anything other than amd64 (README: ARM64 'should work' but support is lacking) or assembly from GCC ('will not work out of the box'); a Gorse write-up seen as a search snippet says c2goasm cannot handle AVX-512.
- Functions with calls to other functions, non-64-bit arguments, more than 14 arguments, or heavy per-call work where cgo's fixed cost is already amortised: the only benchmark measures call overhead on a single FMA.
- Code that needs 32-byte-aligned Go memory for aligned AVX loads: Go gives no such guarantee (issue #4).

## How it is fast

The speed comes from bypassing cgo: a Go-to-assembly call is an ordinary function call, while a cgo call switches to the system stack and goes through the runtime's cgocall machinery. c2goasm generates a prologue that loads Go stack arguments into the System V registers, reserves and (if needed) aligns stack space for the C code, moves arguments beyond the sixth onto that stack, and relocates RIP-relative constant references into a generated constants table; the body is clang's own optimized code, so SIMD intrinsics and templates keep their codegen.

## Compared with alternatives

No catalogued sibling turns compiler output into Go assembly: the siblings are x86 decoders (Zydis, iced, Intel XED, bddisasm), MASM-compatible assemblers (JWasm, UASM, Asmc) and Keystone, which solve different problems. For new Go work, prefer the maintained successors gocc or GoAT (not catalogued) over this archived tool.

## Integration

| | |
|---|---|
| **Form** | command-line tool (Go program) that emits committed Go assembly files; no runtime library |
| **Dependencies** | clang to produce the input assembly; asm2plan9s (run with -a) to encode instructions; optional asmfmt (-f) for formatting |
| **Minimum toolchain** | clang (Apple LLVM on macOS or clang on Linux) with -masm=intel -mno-red-zone -mstackrealign -fno-asynchronous-unwind-tables -fno-exceptions -fno-rtti; benchmarks used Go 1.7.5 and 1.8.1; later Go versions not tested in the repo |
| **Platforms** | amd64 only |
| **Thread safety** | not documented (the output is a plain leaf routine; reentrancy depends on the C code) |
| **Drop-in for the baseline** | partial — replaces a cgo call only for clang-compiled leaf functions, and each function needs a hand-written Go declaration and wrapper; C++ functions need extern "C" or the mangled names do not match |

## Gotchas

- Harness asymmetry (inference from the benchmark code, not measured): the cgo wrapper (cgocmp/CgoMultiplyAndAdd.go) passes &_f4 to C, which under Go's escape analysis of cgo arguments probably moves the 32-byte result array to the heap on every call, while the c2goasm wrapper declares //go:noescape and keeps it on the stack; neither benchmark calls b.ReportAllocs. The 236 and 382 ns cgo figures therefore likely include an allocation and cgo pointer checks, not only the cgo transition; for scale, a search snippet of David Crawshaw's 'Less cgo overhead in Go 1.8' post gives 56 ns for an empty cgo call in Go 1.8 (snippet only), against 236 ns here.
- The example C source (test/cpp/MultiplyAndAdd.cpp and cgocmp/cpp/MultiplyAndAdd.h) uses the aligned _mm256_load_ps on Go [8]float32 arrays, for which Go guarantees only 4-byte alignment; the checked-in converted assembly happens to use vmovups, but in issue #4 a regenerated version emitted vmovaps (which needs 32-byte alignment), and the maintainer replied that 'explicit alignment is a bit of a problem in Golang'. Use unaligned intrinsics.
- Open translation bugs were never fixed: #24 a clang 7 -O3 vectorized loop crashes at run time, #23 output fails with 'expected identifier, found "."', #10 'panic: Unknown line for table: push rbp', #11 GCC 8 function names, #30 very slow generation.
- The benchmark's assembly in test/ is a fixed checked-in file, and neither the clang version nor its -O level is recorded; the numbers are from 2017 Go releases on an unstated CPU and were never re-measured.

## Known shortcomings

- Tiny call-overhead microbenchmark (cgo 382/236 ns/op vs 10.9 ns/op) on Go 1.7.5/1.8.1 with no CPU model; archived 2021-12-01.
- Harness asymmetry (inferred from code, not measured): the cgo wrapper passes &_f4 to C, which probably forces one heap allocation per call, while the c2goasm side declares //go:noescape and neither benchmark calls ReportAllocs, so the 236/382 ns cgo figures likely include more than the cgo transition (an empty cgo call cost about 56 ns in Go 1.8 per a Crawshaw snippet). The example C uses aligned _mm256_load_ps on Go arrays with only a 4-byte alignment guarantee (issue #4); open crash issue #24 was never fixed; archived 2021-12-01.

## Caveats and trade-offs

Measures call overhead on one trivially small AVX2 fused multiply-add over 8 floats (BenchmarkMultiplyAndAdd), not the quality of generated assembly, and says nothing against pure-Go code. Numbers come from Go 1.7.5 and 1.8.1 (2017); cgo call overhead has dropped further in later Go releases and was not re-measured. CPU model not stated (the -12 suffix suggests GOMAXPROCS 12). Only the C side's compile flags are visible in source; the clang version used to produce the converted .s is not stated. Supports amd64 only and clang output only (GCC output does not work out of the box). Repository archived by the owner on 2021-12-01. Go-ecosystem assembly tooling, not an assembler measured against the category's GNU as, NASM or MASM baselines.

Converts C or C++ compiler assembly into Go (Plan 9) assembly, per function, amd64 only, with hand-written Go wrappers and an amd64.go declaration file; used with asm2plan9s. Not intended to port a whole project. Archived and read-only.

## Maintenance

Archived by the owner on 2021-12-01 (last commit 2019-08-12) with several crash and parse issues left open; Apache-2.0 and small enough to vendor, but gocc and GoAT, which credit it, are the maintained route.

## Verdict

First-party run on Node.js 16.14 and an unnamed Intel Kaby Lake desktop CPU computing 8000 digits of pi with the same series in every row: low-level MPZ calls 53 ms vs JS BigInt 129 ms (2.43x), high-level Integer wrapper 88 ms (1.47x), raw MPFR float series 118 ms (1.09x), high-level Float wrapper slower at 175 ms (0.74x). The identical table was already in the README at tag v1.0.0 (April 2022), so it measured the pre-tuning 1.0.0 build, not the current GMP 6.3.0 / Emscripten 3.1.58 package; the 215x atan row is a cached-constant read and the 1.65x 'delayed deallocation' row leaves cleanup outside the timer.

## Use it when

- JavaScript or TypeScript code that needs integer arithmetic on numbers of thousands of digits in tight loops and can write the hot loop with the low-level mpz_\* calls (2.43x over BigInt in the author's pi series).
- Arbitrary-precision floats with a chosen precision and rounding mode, or exact rationals, which BigInt does not offer; in the same pi benchmark decimal.js took 785 ms against 175 ms (Float wrapper) and 118 ms (raw MPFR).
- Transcendental functions (exp, log, sin, atan, asin, constants such as Pi, Euler, Catalan) at hundreds or thousands of digits with MPFR's correct rounding.
- Number theory helpers (probable-prime tests, GCD, powers) in browser or Deno code where a native GMP addon such as mpzjs cannot be installed.

## Skip it when

- Small or moderate integers (machine-sized up to a few hundred bits): the JS-to-wasm call and object allocation per operation are not amortised; the only published numbers are for 8000-digit operands.
- Code that wants BigInt's operators and garbage collection: the high-level wrapper keeps every intermediate alive until calculate() returns or destroy() runs, and there is no FinalizationRegistry support (issue #5, open since 2022).
- Floating-point work through the high-level Float() wrapper if the goal is speed: it was 0.74x of BigInt (175 vs 129 ms) in the author's own table; only the raw MPFR calls (118 ms) beat BigInt.
- Values whose binary exponent exceeds about 2^30: MPFR's exponent type is a 32-bit long on wasm32, so results silently overflow to Infinity (issue #11, open).
- Node.js-only projects that can load a native addon (mpzjs wraps native libgmp) or projects that cannot accept LGPL-3.0.

## How it is fast

The arithmetic runs in GMP's generic C mpn layer built with 64-bit limbs on wasm32 (ABI=longlong, MPN_PATH=generic, no assembly) and a tuned gmp-mparam.h generated by GMP's tuneup on wasm (for example USE_PREINV_DIVREM_1, which divides by a single limb with a precomputed inverse). Floats use MPFR's correctly rounded algorithms. The low-level path wins most because it reuses four mpz_t buffers in place, while the high-level wrapper allocates a new mpz_t for every operation and frees it only when the context ends.

## Compared with alternatives

No arbitrary-precision sibling is catalogued: hash-wasm, tiny-secp256k1 and bls-eth-wasm are fixed-function kernels, while gmp-wasm is a general bignum and multiprecision-float toolkit, so pick it when you need GMP/MPFR operations, rationals or correctly rounded floats in JavaScript rather than a single algorithm.

## Gotchas

- Harness flaw behind the headline 215x row: MPFR's mpfr_atan special-cases |x| = 1 and returns mpfr_const_pi/4, and mpfr_const_pi is served from MPFR's global precision-keyed cache (__gmpfr_cache_const_pi; gmp-wasm never calls mpfr_free_cache). After the first warm-up call each timed Float(1).atan().mul(4) only copies the cached pi and prints 8000 digits, so the 0.6 ms row measures a cache hit and string conversion, not a pi computation. The 7.59x asin(0.5) row does compute (atan of 1/sqrt(3)), but it is a different algorithm from the BigInt series.
- Harness asymmetry in the 'delayed memory deallocation' rows: calcpi.js pushes ctx.destroy() into GCCallbacks and runs them after `end` is taken, so the 78 ms and 169 ms rows simply exclude the freeing cost that the calculate() rows (88 ms, 175 ms) include; the extra 1.65x over 1.47x is untimed cleanup, not a faster technique.
- Inside calculate() every intermediate Integer stays allocated until the callback returns (mpz_t_arr is cleared only in destroy()), so a long loop grows the wasm heap; wasm memory never shrinks, and the README's remedy is binding.reset(), which re-instantiates the module and invalidates every live pointer.
- Float() defaults to 53-bit precision (changed from 52 in 1.2.0); pass precisionBits to the context or constructor. JS number arguments must be int32/uint32 (the \*_ui and \*_si GMP functions take a 32-bit long on wasm32) or the wrapper throws.

## Known shortcomings

- README numbers match but the 215x and 7.59x rows compare MPFR atan/asin with a BigInt series (different algorithm, derived ratios); the Float wrapper is slower (0.74x); the table predates the current calcpi.js and the 1.3.0 build (emsdk 3.1.58, -O3 -Oz, generic mpn); no CPU model.
- Enricher: the '215x' Float(1).atan().mul(4) row is a cache hit (MPFR's mpfr_atan special-cases |x|=1 as mpfr_const_pi/4 and const_pi is served from the global __gmpfr_cache_const_pi that gmp-wasm never frees, so after warm-up the timed run only copies pi and prints 8000 digits; wazero precedent, row struck); the 'delayed deallocation' rows (78 ms, 169 ms) run ctx.destroy() after the timer stops, so the 1.65x over 1.47x is untimed cleanup; the table is unchanged since v1.0.0 (April 2022, pre-tuning build, not GMP 6.3.0); the current harness also runs the native mpzjs addon with results unpublished; valid rows: MPZ low-level 2.43x, Integer wrapper 1.47x, MPFR low-level 1.09x.

## Caveats and trade-offs

First-party; CPU model not given (only 'Intel Kaby Lake desktop CPU'). The README table appears older than the current benchmark/calcpi.js, which also runs mpzjs, ExactNumber and 'stepwise' solvers absent from the table, and CHANGELOG 1.3.0 updated GMP to 6.3.0, MPFR to 4.2.1 and Emscripten after the Node 16 era. The 215x and 7.59x rows compare MPFR's atan/asin against the BigInt series (different algorithms). The high-level Float wrapper is slower than BigInt (0.74x); only the integer paths and MPFR low-level calls win. Harness is sound otherwise: 5 warm-ups, 4 timed rounds averaged, every result checked against 8000 reference pi digits (the sleep() between rounds is not awaited, so there is no pause). GMP is built size-optimized (-Oz) with generic C limbs and no assembly. Node 16 is old; last commit 2024-07-07. [retier] 215x atan row invalid (cache hit); delayed-deallocation rows untimed cleanup; pre-tuning build, not GMP 6.3.0; native mpzjs results unpublished

Manual memory management and deallocation concerns (README suggests reinitializing the bindings); LGPL-3.0; bundled wasm binary; offers Rational and Float types and many more operations than BigInt.

## Maintenance

Stale since 1.3.2 (2024-07-07, 32 stars, 3 open issues including the 32-bit exponent limit and a Kotlin/JS crash); LGPL-3.0 with a transparent Docker build, usable from npm, but the README benchmark has not been re-run since 2022 and the current harness also runs a native GMP addon (mpzjs) whose results are not published.

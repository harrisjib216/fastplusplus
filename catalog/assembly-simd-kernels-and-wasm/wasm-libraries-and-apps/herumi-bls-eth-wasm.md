## Verdict

ChainSafe/bls's README table comes from a December 2020 GitHub Actions run (ubuntu-latest, Node 12.x per the workflow at commit f4f1739; CPU not stated; run page now 404). It times bls-eth-wasm ^0.4.4 through the ChainSafe wrapper against noble-bls12-381 0.7.2 in pure JS: verify 47.67 vs 17.91 ops/s, fastAggregateVerify(30) 51.15 vs 18.37, verifyMultiple(30) 3.52 vs 2.03, aggregating 30 pubkeys 2898.9 vs 1875.0, aggregating 30 sigs 1033.0 vs 526.25, sign 108.81 vs 10.25 (1.5-10.6x, derived from page data). blst native ran 5-10x faster than herumi. Each figure is a plain mean of 100 herumi runs or 10 noble runs.

## Use it when

- Eth2-style BLS12-381 signing and verification in a browser, a bundler build or any JS runtime with WebAssembly where native blst bindings cannot load.
- As the fallback when the @chainsafe/blst native addon fails to install or load on Node; ChainSafe/bls already does this automatically.
- Signing-heavy JS code. In ChainSafe's 2020 run, sign was 108.81 vs 10.25 ops/s against noble-bls12-381 0.7, although only herumi's timing included hash-to-curve and a subgroup check.
- Aggregate checks: fastAggregateVerify over many public keys for one message (51.2 vs 18.4 ops/s at 30 keys), and multiVerify batch verification of independent (pk, msg, sig) triples.
- Threshold BLS in JS: SecretKey/PublicKey/Signature share and recover with Id values are exposed in index.d.ts.

## Skip it when

- Node services that can load native bindings. In the same run blst native was 5-10x faster (verify 326.38 vs 47.67 ops/s), and ChainSafe's blst backend also verifies asynchronously on the libuv pool. herumi's async variants just call the sync code.
- When your real alternative is today's pure JS. The table's baseline, noble-bls12-381 0.7, is deprecated. The @noble/curves README reports 77 verify/s and 112 sign/s for BLS12-381 G2 signatures, but on an Apple M4. That is a different machine, run and library version from the 2020 CI table and not comparable, so re-measure before assuming the 2-10x gap still holds.
- Multi-core verification inside one process. Each module load is one single-threaded wasm instance: multiVerify passes threadNum 0 and the build has no wasm threads or SIMD. Use one instance per worker.
- Messages that are not 32 bytes, or a non-Ethereum key/signature layout. The package is built with BLS_ETH, the README says 'The size of message must be 32 byte', and multiVerify returns false for other sizes. Hash longer messages first.
- Versions before v1.6.0. The README lists 'security fix: deserialize rejects an oversized input' for v1.6.0.

## How it is fast

It runs herumi's mcl optimal-ate pairing library and the bls layer as compiled C++. The build uses clang --target=wasm32 -O3 -flto, wasm-ld --lto-O3 and wasm-opt -O3, with 32-bit limbs (MCL_SIZEOF_UNIT=4), and inlines the wasm as base64 in src/bls_c.js. In ETH mode, verify checks e(P, sig) == e(pk, H(m)) as one two-pair Miller loop (millerLoopVec) followed by a single final exponentiation. multiVerify uses random 64-bit coefficients, G2 multi-scalar multiplication (mulVec) and blocks of 16 Miller loops, so a whole batch shares one final exponentiation. On the JS side, values live in Uint32Arrays that are copied onto the wasm stack for each call, so the hot path makes no wasm heap allocations.

## Compared with alternatives

Pick it when you need BLS12-381 Ethereum signatures and aggregation in JS. tiny-secp256k1 (WASM) covers secp256k1 ECDSA, starknet-rs covers StarkNet Pedersen hashing, and awasm-noble's catalogued evidence is BLAKE3 hashing only, so none of them does BLS pairings.

## Integration

|---|---|
| **Form** | module |
| **Dependencies** | none at run time (wasm embedded in src/bls_c.js; uses crypto.getRandomValues, which can be replaced with setRandFunc); rebuilding needs the herumi/bls and herumi/mcl submodules, clang and wasm-ld (the CI uses LLVM 21), wasm-opt (binaryen) and python3 |
| **Minimum toolchain** | Any JS engine with WebAssembly and crypto.getRandomValues; no minimum Node version documented (CI tests on Node 24; ChainSafe/bls requires Node &gt;=18) |
| **Platforms** | any WebAssembly host: Node.js, browsers (browser/bls.js), React via 'bls-eth-wasm/browser'; wasm32 with 32-bit limbs, no SIMD, no threads |
| **Thread safety** | Not documented. There is one wasm instance per module load, with a shared 1 MiB stack and global init state. Calls are synchronous JS, so use a separate instance in each worker. |
| **Drop-in for the baseline** | partial — not API-compatible with noble-bls12-381 (class-based objects, mandatory async init, 32-byte messages); through ChainSafe/bls the same IBls interface switches between herumi and blst-native |

## Gotchas

- Call `await bls.init(bls.BLS12_381)` before anything else. Arguments are copied onto a fixed 1 MiB wasm stack (STACK_SIZE=1048576), and glue.js throws 'stackAlloc: bad size' when a request does not fit. Split very large aggregate or batch calls.
- blsInit turns on subgroup (order) checks for deserialization in G1 and G2 by default. verifySignatureOrder(false) and verifyPublicKeyOrder(false) turn them off for speed and must not be used on untrusted input. aggregateVerifyNoCheck does not check that messages are distinct; for the basic (non proof-of-possession) scheme, call areAllMsgDifferent yourself.
- Harness flaw in the published numbers, which mostly favours the baseline. At ChainSafe/bls commit f4f1739 (the 2020-12-07 table), CI ran Node 12.x on ubuntu-latest with bls-eth-wasm ^0.4.4 (an Emscripten build), @chainsafe/blst ^0.1.3 and noble-bls12-381 ^0.7.2. noble's verify, verifyAggregate, verifyMultiple and sign rows were given messages already hashed to G2. The ChainSafe Signature constructor calls isValidOrder(), so herumi's sign and aggregate-signatures timings also include a G2 subgroup check that noble skips. The herumi ratios are therefore conservative on those rows. Only warm-up cuts the other way: noble ran 10 runs and herumi 100, each a plain mean. runForAllImplementations also does not await its async callback, so the blst and herumi loops stay sequential only through event-loop timing.
- src/bls_c.js and browser/bls.js are generated and committed by the build.yml GitHub Action on the dev branch. That job installs LLVM by piping apt.llvm.org/llvm.sh into sudo bash, and the repo has no LICENSE file (the BSD-3-Clause terms are only stated in the README and package.json).

## Known shortcomings

- Third-party ChainSafe/bls numbers come from a 2020 CI run whose page is gone; CPU and Node unstated; the noble-bls12-381 baseline is deprecated, ran 10 iterations against 100 and was timed without hash-to-curve; no LICENSE file (BSD-3-Clause per README and package.json).
- Harness flaw that mostly favours the baseline: at ChainSafe/bls commit f4f1739 (2020-12-07 table; Node 12.x on ubuntu-latest, bls-eth-wasm ^0.4.4 Emscripten build, @chainsafe/blst ^0.1.3, noble-bls12-381 ^0.7.2) noble's verify, verifyAggregate, verifyMultiple and sign rows received messages already hashed to G2, and ChainSafe's Signature constructor adds a G2 isValidOrder check to herumi's sign and aggregate-signatures rows, so herumi's ratios are understated; only warm-up cuts the other way (noble 10 runs, herumi 100, plain means). runForAllImplementations does not await its async callback. wasm is single-threaded with a 1 MiB stack; messages must be 32 bytes; no LICENSE file in the repo.

## Caveats and trade-offs

Third-party numbers from a ChainSafe CI run around late 2020 (run 1513710175; the run page now returns 404), so CPU, Node version and library versions are not recoverable; herumi has since reported about 1.1x (2022), 10% and 4% (2024) speedups and switched from Emscripten to clang in v1.5.0, and noble-bls12-381 (^0.7.2 in benchmark/package.json) is deprecated in favour of the much faster @noble/curves, so both sides are stale. Harness asymmetries: noble's verify, verifyAggregate and sign inputs are pre-hashed to G2 in prepareTest (hash-to-curve excluded from noble's timing, included in herumi's), which favours noble; noble ran 10 runs and herumi/blst 100, each a plain mean with no warm-up, which can penalise the JIT-compiled pure-JS noble. Not compared with herumi's own library compiled natively (blst native is a different library). No LICENSE file in the repo: the README says 'modified new BSD License' with a BSD-3-Clause link and package.json declares BSD-3-Clause. Harness asymmetries mostly favour the baseline: noble's verify, verifyAggregate, verifyMultiple and sign rows received messages already hashed to G2 (hash-to-curve excluded from noble's timing, included in herumi's), and ChainSafe's Signature constructor calls isValidOrder(), so herumi's sign and aggregate-signatures rows include a G2 subgroup check noble skips; only warm-up cuts the other way (noble 10 runs, herumi and blst 100, plain means, no warm-up). runForAllImplementations does not await its async callback. herumi has since reported about 1.1x (2022), 10% and 4% (2024) speedups and switched from Emscripten to clang in v1.5.0; noble-bls12-381 is deprecated in favour of @noble/curves, so both sides are stale. Not compared with herumi's own library compiled natively (blst native, 5-10x faster, is a different library). wasm is single-threaded with a fixed 1 MiB stack; messages must be 32 bytes. No LICENSE file: README says 'modified new BSD License', package.json BSD-3-Clause.

The wasm backend is 5-10x slower than blst native bindings (Node.js only); its advantage is running in browsers where native bindings are unavailable.

## Maintenance

Active (v1.7.0, last commit 2026-09-17 'bump mcl to v4.10'); BSD-3-Clause per README and package.json, but no LICENSE file in the repo. The 2020 numbers predate herumi's 2021 isValidOrder speedup, the 2022 1.1x and 2024 10% and 4% gains, and the v1.5.0 switch from Emscripten to clang, so the herumi side is likely faster now while the baseline is a deprecated library. Harness flaw found: noble's inputs were pre-hashed while herumi's sign and aggregate-signatures rows include a wrapper subgroup check, so the gaps are understated except for warm-up.

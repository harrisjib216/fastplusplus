## Verdict

First-party README text only. The root README says pure GROQ rules run via Rust/WASM '\~5-10x faster', and packages/groq-wasm/README.md says '\~5-10x faster than TypeScript for complex queries'. No benchmark code, query corpus, Node.js or browser version, hardware or sample count exists in the repo. In the default lint() path the TypeScript groq-js parse still runs, so the end-to-end gain must be smaller than any ratio for the WASM call alone.

## Use it when

- You already lint GROQ with the Sanity ESLint plugin, CLI or LSP; the WASM path comes with @sanity-labs/groq-lint and costs nothing to adopt
- Linting large batches of GROQ queries in CI or an editor, where the Rust rule passes may beat the TypeScript walks (unmeasured)
- Browser or edge use where you want GROQ formatting (groq-format) without a Rust toolchain
- Node.js 22.3.0 or newer with ESM, which both packages require

## Skip it when

- If you need a proven speedup: the '\~5-10x faster' line has no benchmark, corpus, runtime version or hardware behind it, and the repo has no bench script
- When findings must be identical across paths: WASM findings keep the Rust severities and rule semantics, which differ from the TypeScript rules they replace
- Schema-aware linting: invalid-type-filter and unknown-field always run in TypeScript on a groq-js parse, so a WASM run parses each query twice
- Older Node.js or CommonJS-only toolchains: 1.0.0 dropped CJS builds and requires Node.js 22.3.0 or newer
- Stability-sensitive production use: Sanity Labs calls it 'pre-v1' and maintained on a 'best-effort basis'; 7 stars, and upstream rule logic is regenerated by an LLM from rules.yaml

## How it is fast

The pure-GROQ rules move from TypeScript AST walks over groq-js to a Rust pipeline: the groq-parser-rs parser lowers the AST to an IR, and 14 rule passes check it in one call. Findings cross the boundary once, as a JSON string. The WASM module is built by wasm-pack with opt-level 's' (size) and LTO, and loaded synchronously at import. Nothing in the repo measures the effect.

## Compared with alternatives

No sibling lints GROQ, so this is the only choice for that job. Unlike sh-syntax, es-module-lexer or hash-wasm, which publish measured WASM-versus-JS numbers, this entry's speedup is an unbenchmarked README ratio; treat it as a convenience of the Sanity lint toolchain, not as a proven fast path.

## Gotchas

- The default lint() call still parses every query with groq-js. deep-pagination-param is not in WASM_RULES and needs no schema, so it always runs in TypeScript, even though its own source comment says groq-js 'does not support parameters in slice expressions', so it can never fire. A default call therefore pays the groq-js parse plus a Rust parse, IR lowering and a JSON round trip. The claimed 5-10x can apply at most to the WASM call measured on its own, never to the end-to-end lint(). Disabling deep-pagination-param (with no schema) is the only way to skip the groq-js parse.
- Severities differ between paths. computed-value-in-filter is 'warning' in the TypeScript rule but 'high' in upstream rules.yaml, which mapSeverity turns into 'error'. Setting forceTs, or the per-query fallback that runs when the Rust parser throws, therefore changes what CI fails on. The Rust linter also runs deep_pagination_param, whose findings are filtered out.
- Wrong source positions after non-ASCII text. byteOffsetToLocation in packages/groq-wasm/src/lint.ts advances its counter by one per code point, while the WASM returns UTF-8 byte offsets. Line and column numbers therefore drift for any finding that follows a non-ASCII character, and the 'offset' field it returns is a byte offset, not a JS string index.
- The docs are stale. packages/groq-wasm/README.md still documents initWasm, isInitialized, lintAsync and formatAsync, and packages/groq-lint/README.md still documents initLinter(); CHANGELOG 1.0.0 removed all of them. Since 1.0.0 the WASM loads at import time and a load failure throws WasmError. The root README's 'automatic fallback to TypeScript if WASM unavailable' therefore no longer covers load failures, only queries the Rust parser rejects.

## Known shortcomings

- Only a README ratio ("about 5-10x faster than TypeScript") with no benchmark anywhere; the speed comes from wrapping atombender/groq-lint (third-party Rust).
- Design flaw: the default lint() still parses every query with groq-js, because the TypeScript-only deep-pagination-param rule always runs (its own comment says it can never fire under groq-js), so the 5-10x cannot hold end to end and no benchmark exists. WASM severities differ from TypeScript (computed-value-in-filter error vs warning); byte offsets are counted as code points, so line and column drift after non-ASCII text; the 'fallback if WASM unavailable' is obsolete since 1.0.0 (an import-time load failure throws WasmError); the READMEs document removed APIs.

## Caveats and trade-offs

Ratio-only claim with no benchmark, workload, corpus, hardware, Node/browser version or sample count anywhere in the repo; neither packages/groq-wasm nor packages/groq-lint has a bench script. The WASM side wraps the third-party Rust crates atombender/groq-lint and groq-format (packages/groq-wasm/rust/src/lib.rs calls groq_lint::lint), so the speed belongs to that crate; only the 'pure GROQ' rules run in WASM, while schema-aware rules stay in TypeScript, and the two rule implementations are not shown to produce identical findings. The 5-10x range is qualified as 'for complex queries'.

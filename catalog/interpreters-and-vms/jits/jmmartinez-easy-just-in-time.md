# Easy::jit

## Verdict

First-party Quarkslab blog (EuroLLVM/FOSDEM 2018 era, read only as a search snippet): the specialised convolution kernel ran about 4.5x and the comparator-inlined quicksort about 2x faster than the same functions compiled ahead of time, sizes 16 to 1024, compile time excluded; no CPU, compiler flags or build type are given, and the repo harness behind these numbers has the out-of-bounds write, non-sorting comparator test and unset -O level described under gotchas.

## Use it when

- A hot generic kernel whose parameters (filter mask, sizes, strides, channel count, a callback pointer) are fixed for a long run but only known at run time, e.g. per video stream or per loaded config.
- Callback-heavy C-style code (qsort-like comparators, function-pointer tables) where inlining the callback is the main win.
- Research or prototyping of runtime specialisation on an LLVM 6 toolchain you can pin, where writing templates for every parameter combination is impractical.
- Long-running loops that amortise compile cost: the blog cites break-even after about 2 convolution calls and 29 quicksort calls at size 1024.

## Skip it when

- Any toolchain newer than LLVM/Clang 6.0: CMake requires find_package(LLVM 6.0), issue #42 (move to LLVM 7) and #51 (link errors on LLVM 14.0.6, port only in a third-party fork) are open, and the project is abandoned since 2021-05-15.
- GCC or MSVC builds: the method needs the Clang plugin at compile time and the LLVM JIT libraries at run time.
- Short-lived or latency-sensitive calls: every new argument combination pays a full LLVM -O2 plus codegen compile (the pipeline is populated twice in Optimize()), and that cost is excluded from the quoted speedups.
- When the parameter set is small and known at build time: templates or constexpr specialisation give the same code without a JIT or a large LLVM runtime dependency.
- Production use: open issues report every example failing with an InlineParameters assertion (#43) and 'Pass registered multiple times' crashes (#45), all unanswered.

## How it is fast

Runtime partial evaluation (value specialisation): known arguments are inlined as constants (InlineParameters pass), constant function pointers are devirtualised (DevirtualizeConstant pass), then the standard LLVM -O2 pipeline runs, so loop bounds become constants, small loops fully unroll and indirect calls such as a qsort comparator get inlined. Code is generated by the legacy LLVM ExecutionEngine (MCJIT, CodeGenOpt::Aggressive) with -mcpu set to the host CPU, so it can also use ISA extensions the AOT binary was not built for.

## Compared with alternatives

Pick it over AsmJit or sljit when you want to specialise existing C++ source rather than emit machine code by hand, and over RapidUDF when the code to speed up is a C++ function, not an expression string; TPDE solves compile latency of LLVM back-ends and is complementary, not an alternative.

## Integration

| | |
|---|---|
| **Form** | Clang pass plugin (EasyJitPass.so) plus a shared runtime library (EasyJitRuntime) and headers |
| **Dependencies** | LLVM 6.0 and clang 6.0 (development packages), Python lit for tests; optional OpenCV for examples and Google Benchmark for the benchmark |
| **Minimum toolchain** | Clang/LLVM 6.0 exactly (CMake find_package(LLVM 6.0 REQUIRED)), C++14 |
| **Platforms** | Linux x86-64 and aarch64 detected in CMake; other hosts not documented |
| **Thread safety** | Not documented; easy::Cache is an unsynchronised std::unordered_map and the BitcodeTracker is a global static without locks, so concurrent jit or cache calls need external locking. |
| **Drop-in for the baseline** | partial: the function body stays unchanged, but call sites must go through easy::jit or easy::Cache and the whole project must be built with clang plus the plugin |

## Gotchas

- Harness flaw: benchmark/CMakeLists.txt adds only '-Xclang -disable-O0-optnone' and the plugin to CMAKE_CXX_FLAGS and sets no optimisation level, and the README build line passes no CMAKE_BUILD_TYPE, so a build that follows the README compiles the AOT baseline (kernel, Qsort) at -O0 for generic x86-64 while the JIT side always runs the LLVM -O2 pipeline with CodeGenOpt::Aggressive and -mcpu=host; the blog's 4.5x and 2x do not state which build was timed, and a WebSearch summary cites about 8x against an -O2 static build (source not identified).
- Harness flaws in benchmark/benchmark.cpp: BM_convolve allocates (n-3)^2 ints but writes index i\*(n-2)+j up to (n-4)(n-1), out of bounds for every n of 5 or more; the image is all zeros; Qsort tests 'if (cmp(...))' instead of '&lt; 0', so with distinct keys every element moves left, recursion depth is n and the timed work is an O(n^2) chain of comparator calls that does not sort; JIT compile time is excluded from the timed loop.
- The catalogue record says LLVM ORC; the runtime (runtime/Function.cpp) actually uses the legacy llvm::ExecutionEngine (EngineBuilder, EngineKind::JIT), not ORC.
- Functions not deduced automatically must be exported with EASY_JIT_EXPOSE or -mllvm -easy-export, otherwise easy::jit throws BitcodeNotRegistered at run time.

## Known shortcomings

- The 4.5x and 2x figures exist only in a snippet of the first-party Quarkslab blog (blocked); benchmark/benchmark.cpp has harness bugs (the convolution output buffer is written out of bounds and the qsort comparator lacks '&lt; 0', so it does not sort), so both sides of the comparison run a workload other than the one claimed. Abandoned since 2021-05-15.
- Enricher: benchmark/CMakeLists.txt sets no -O level and the README's cmake line passes no CMAKE_BUILD_TYPE, so following the README builds the AOT baseline (kernel, Qsort) at -O0 for a generic ISA while the JIT side always runs LLVM -O2 with CodeGenOpt::Aggressive and -mcpu=host; the blog's build type is unknown. The runtime uses the legacy llvm::ExecutionEngine (MCJIT), pinned to LLVM 6.0; issues #43 and #45 (crashes) unanswered.

## Caveats and trade-offs

Snippet only: numbers come from the first-party Quarkslab blog (EuroLLVM'18 / FOSDEM'18 era), which could not be opened; no CPU or flags. Harness flaws in benchmark/benchmark.cpp: Qsort tests 'if (cmp(v[i], v[left]))' where the K&R original tests '&lt; 0', so with int_cmp returning -1/0/1 it is not a correct sort, and it re-sorts the same vector in place every iteration; BM_convolve allocates out with (n-3)^2 ints but the kernel writes index i\*(n-m+1)+j up to (n-4)(n-1), out of bounds for every tested n (both the JIT and AOT paths run the same code, so the ratio is not fabricated, but the harness has undefined behaviour); the image is all zeros; JIT compile time is excluded from the timed loop. Baseline is AOT code of the same generic function, not PyPy, LuaJIT, V8 or HotSpot. Last commit 2021-05-15; needs an LLVM 6-era toolchain. [retier] The 4.5x and 2x figures exist only in a snippet of the first-party Quarkslab blog (blocked), with the build type unknown; following the README builds the AOT baseline (kernel, Qsort) at -O0 for a generic ISA (benchmark/CMakeLists.txt sets no -O level, the cmake line passes no CMAKE_BUILD_TYPE) while the JIT side always runs LLVM -O2 with CodeGenOpt::Aggressive and -mcpu=host, so the comparison is not like for like. benchmark/benchmark.cpp writes the convolution output buffer out of bounds and the qsort comparator lacks '&lt; 0' (an O(n^2) comparator chain, not a sort). Runtime is the legacy MCJIT ExecutionEngine pinned to LLVM 6.0; abandoned since 2021-05-15; crash issues #43 and #45 unanswered.

Compiler-assisted: needs a Clang/LLVM pass plugin and an LLVM runtime library; functions must be annotated; compile cost paid at run time, with a cache to avoid recompiling.

## Maintenance

Abandoned since 2021-05-15 and pinned to LLVM/Clang 6.0 with crash reports unanswered; BSD-3-Clause, so usable as a reference design for runtime specialisation, but porting to a current LLVM (a third-party llvm-14.0.6 branch exists with link errors) is the price of using it.

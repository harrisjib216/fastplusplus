## Verdict

A first-party chart (README, generated by tests/benchmark.py on a Ryzen 5 3400G against NumPy 2.3.5) shows 30,000 evaluations of sum((v1 + i) @ v2 for i in range(10)) taking about 0.079 s for Copapy versus 0.308 s for NumPy at 10 elements (3.9x) down to 0.321 s versus 0.555 s at 500 elements (1.7x), values read from the SVG markers (derived from page data). The constant gap of about 7.7 microseconds per iteration is NumPy's three-call overhead; GCC version, Python version and whether the PyPI wheel or a local build was used are not stated.

## Use it when

- Small fixed-structure numeric kernels (tens to a few hundred scalars) evaluated at high rate from Python, where NumPy's per-call overhead (about 7.7 microseconds per iteration in the README benchmark) dominates.
- Embedded or realtime targets that need deterministic machine code with no syscalls, no libc and memory needs known at compile time: x86_64, x86, AArch64, ARMv6/7 including Thumb and Cortex-M, RISC-V RV32/RV64 with hardware floating point.
- Realtime optimisation loops that need reverse-mode autodiff inside the compiled code, such as the README's Madgwick IMU fusion and two-joint inverse kinematics examples.
- Graphs with many compile-time constants or sparse (zero) coefficients, which the tracer folds away before code generation.

## Skip it when

- Bulk array math: there are no SIMD stencils yet, the lead drops from about 3.9x at 10 elements to 1.7x at 500, and nothing beyond 500 elements was measured.
- Code with data-dependent control flow: branches must be decidable at trace time (cp.iif is the workaround), so general Python programs do not compile.
- Workloads that move much data between Python and compiled code: write_value and read_value make one runner call per scalar, and the README benchmark measures no data transfer at all.
- Production systems that need stability or hardware I/O: the project is at version 0.0.x, hardware I/O is not yet available, and divide-by-zero is still possible at runtime (README footnote).

## How it is fast

Copy-and-patch compilation: every graph operation maps to a stencil precompiled by GCC (machine code with relocation holes), the compiler concatenates stencils, strips each stencil's trailing tail-call jmp (an add becomes one addss instruction) and keeps operands in two virtual registers mapped to hardware registers; the runner mmaps code and data, applies architecture-neutral patch records and jumps to the entry point. The whole traced graph runs as one native call, so Python pays one call per evaluation where the NumPy version pays three calls plus temporaries. Tracing also folds compile-time constants and removes multiplications by 1, additions of 0 and branches multiplied by 0.

## Compared with alternatives

CPython's copy-and-patch JIT, PochiVM and WasmNow use the same technique for whole languages, C++ metaprograms or Wasm, and Numba or Hana Jit speed up ordinary Python/NumPy on desktops. Pick Copapy only when the output must be deterministic, libc-free machine code for embedded or realtime targets authored from Python, ideally with autodiff; for general numeric speedups Numba covers far more of Python and NumPy.

## Gotchas

- Side effects inside assert statements: Target.compile, run and write_value call the runner only inside 'assert coparun(...) &gt; 0' (src/copapy/_target.py), so under 'python -O' or PYTHONOPTIMIZE nothing is compiled or executed and a timing loop like tests/benchmark.py would time a no-op; runner error codes (-4 code and data more than 2 GB apart, -5 bad patch) are also silently dropped then.
- @cp.jit caches by function object only: later calls with a different argument count, vector length or type reuse the first trace (zip silently truncates mismatched inputs), and any Python control flow is frozen at the first trace.
- README benchmark harness: the Copapy loop never reads its result back while NumPy returns a scalar each iteration; the NumPy case adds an int32 [10,1] array to float32 vectors, which NumPy promotes to float64, so the baseline allocates and computes a 10 x v_size float64 temporary per call while Copapy uses C float; the results JSON is not committed and the unplotted pure-Python row runs 300 iterations but records 3000. The ratio measures call overhead, not code quality.
- Early-stage code: wrong-result bugs were closed only in September 2026 (#29 runner built on Windows x64 with /O2, #28 cp.sin on 32-bit x86), after the last non-dev PyPI release (0.0.7.post0, 2026-04-05); the C runner does no bounds checks on COPY_DATA, COPY_CODE or PATCH offsets, so it trusts whatever command stream it receives.

## Known shortcomings

- Numbers exist only as an SVG chart; ratios read from it (derived from page data): about 3.9x over NumPy 2.3.5 at vector size 10 and 1.7x at 500, a constant gap of about 7.7 us per iteration that is NumPy call overhead. No GCC or Python version stated, results JSON not committed, and the Python row miscounts iterations. NumPy is not a listed baseline.
- Enricher: Target.compile, run and write_value invoke the runner only inside 'assert coparun(...) &gt; 0' (src/copapy/_target.py), so under python -O nothing compiles or runs and a benchmark would time a no-op; the README run is not shown with -O, so the chart stands. The NumPy case promotes float32+int32 to float64 with a 10 x v_size temporary while Copapy uses C float; the result is never read back, so the ratio is call overhead. @cp.jit caches by function object only. Wrong-result bugs #29 (Windows x64 /O2 runner) and #28 (cp.sin on x86-32) were closed 2026-09, after the last stable PyPI release 0.0.7.post0; the runner does no bounds checks on COPY_DATA, COPY_CODE or PATCH offsets.

## Caveats and trade-offs

Baseline is NumPy 2.3.5 (float32 arrays), not PyPy, V8, LuaJIT or HotSpot; the win is small-vector call overhead: the gap is a constant \~7.7 microseconds per iteration from v_size 10 to 500 (derived from the chart), so the ratio shrinks from about 3.9x to 1.7x as vectors grow. Numbers exist only as a chart image; the results JSON the script writes is not in the repo. The Copapy case calls tg.run() (which still builds a small command buffer in Python and calls the in-process coparun runner) and never reads the result back, while the NumPy case returns a scalar each iteration; the README discloses that no data moves between Python and compiled code. The work is real, not a no-op: cp.value inputs are non-anonymous constants that the compiler keeps as runtime data. Harness nits: the pure-Python row runs iter_size//100 iterations but records iter_size//10 (that row is not plotted), and the unused cp_vs_python_sparse function contains an 'assert False'. A @cp.jit decorator exists for ordinary Python functions, but the README benchmark does not cover it and says cp.jit is not optimized for data transfer.

Not a general-purpose JIT: a tracing copy-and-patch compiler for statically typed numeric computation graphs aimed at deterministic realtime use (x86_64, ARM32, AArch64 and RISC-V); generated code makes no syscalls and needs no libc; the C runner builds with GCC (tail-call optimisation required). Hardware I/O is not yet available per the README.

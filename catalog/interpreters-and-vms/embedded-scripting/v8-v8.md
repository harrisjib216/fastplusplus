## Verdict

In ahaoboy/js-engine-benchmark (an Octane v8-v7 subset forked from Mozilla's arewefastyet, one run per engine on GitHub-hosted runners with unstated CPUs, results dated 10/5/2026), the d8 shell scored 48107 vs QuickJS 2026-06-04 1217 on Ubuntu (V8 main 15.7.0, component build), 64220 vs 1761 on macOS arm64 and 46932 vs 1067 on Windows (official canary 15.7.35 binaries). plb2 on an Apple M1 MacBook Pro (hyperfine wall-clock, start-up included) shows Node 21.5.0 at 3.73 s vs QuickJS 59.04 s for nqueen and 2.88 s vs 135.66 s for matmul.

## Use it when

- Long-running, compute-heavy JavaScript inside a C++ host where warmed-up throughput matters: 48107 vs QuickJS 1217 on Ubuntu, 64220 vs 1761 on macOS arm64, 46932 vs 1067 on Windows.
- Object- and call-heavy code (DeltaBlue 106708 vs 757, RayTrace 116474 vs 1594 on Ubuntu) where speculative optimization pays off most.
- Hosts that also need fast WebAssembly through the same embedding API (the repo's hello-world sample compiles and runs a Wasm module next to a script).
- x64 or arm64 desktop and server hosts that can afford tens of MB, a C++20 toolchain and the gn/depot_tools build, and want the same engine semantics as Chrome and Node.js.
- Multi-tenant hosts that run several Isolates in parallel on separate threads.

## Skip it when

- Platforms that forbid runtime-allocated executable memory: with --jitless only the interpreter remains, and plb2's Node-nojit row (Apple M1) is no faster than QuickJS (nqueen 55.48 s vs 59.04 s, matmul 162.84 s vs 135.66 s, sudoku 63.91 s vs 67.55 s).
- Small or embedded hosts: the shootout's V8 builds are 28.8 MB (macOS d8) to 66 MB (Ubuntu shell plus shared libraries) versus about 1 MB for QuickJS, and Score/MB on Ubuntu is 729 vs QuickJS 1190.
- Short scripts and cold starts: the suite throws away a one-second warm-up per benchmark, so start-up and JIT warm-up cost are not in these numbers; plb2 notes JIT runtimes need up to about 0.3 s to compile and warm up.
- Regex-heavy workloads or macOS arm64 hosts where JavaScriptCore is an option: JSC beats V8 on RegExp on all three OSes (14308 vs 11558 Ubuntu, 31307 vs 16440 macOS, 19236 vs 10455 Windows) and on the macOS arm64 total (67664 vs 64220).
- Projects that cannot adopt the gn/depot_tools build, C++20, or keep up with frequent V8 releases and security fixes.

## How it is fast

Tiered execution driven by type feedback and inline caches: the Ignition bytecode interpreter collects feedback, hot functions tier up to Sparkplug (baseline compiler), Maglev (mid-tier optimizing compiler, also the on-stack-replacement target) and TurboFan with Turboshaft phases (top-tier speculative optimizer), with deoptimization when speculation fails; an experimental Turbolev tier (Maglev plus Turboshaft) exists behind a flag. Compilation runs concurrently on background threads, regular expressions are compiled to native code with tier-up, and the GC uses parallel scavenges and concurrent marking. The gap over QuickJS in this suite is the warmed-up JIT versus interpreter gap.

## Compared with alternatives

Pick V8 over SpiderMonkey (19137) and ChakraCore (19392) when you want about 2.5x their Ubuntu score and an engine under daily development; pick it over QuickJS, Escargot, PrimJS or Hermes only when peak throughput on long-running code justifies 28-66 MB, C++20 and a gn build. On locked-down no-JIT platforms QuickJS gives the same speed as jitless V8 at a fraction of the size.

## Gotchas

- The embedder must be compiled with the same build configuration as the V8 library: V8::Initialize() checks pointer compression, 31-bit Smis, the sandbox, Android target and checks flags against the binary and refuses to start on a mismatch.
- Harness: the three V8 columns are different builds. Ubuntu runs ahaoboy/v8-build's tip-of-tree main (15.7.0; the 'git checkout \$VERSION' line is commented out) built with is_component_build = true (934.6 KB d8 plus 65.1 MB of shared libraries), while Windows and macOS arm64 run Google's official canary binaries (v8-win64-rel / v8-mac-arm64-rel 15.7.35) downloaded from storage.googleapis.com. That build script also calls ninja v8_monolith, a target V8's BUILD.gn only defines for non-component builds.
- Harness: each benchmark gets a thrown-away warm-up of at least 1 s, then at least 1 s and 32 iterations of measurement; the score is reference time over the geometric mean, and each engine runs once per OS on a shared GitHub-hosted runner with no repetitions or variance, so the numbers are warmed-up peak throughput only.
- JIT engines carry a large attack surface: WebSearch snippets (pages not opened) report CVE-2026-85046, a V8 type confusion exploited in the wild and fixed in Chrome 152.0.7977.82 on 2026-09-04. Embedders running untrusted code must track V8's security releases or use --jitless.

## Known shortcomings

- ahaoboy CI shootout numbers (48107/64220/46932 vs QuickJS 1217/1761/1067) come from CI runners with no CPU model and prebuilt binaries with unknown flags; V8 is second to JavaScriptCore on macos-arm64 and has a large footprint for an embedded-scripting use. V8 is itself a spec baseline for jits and bytecode-vms-and-wasm.
- Enricher: the ahaoboy V8 columns differ by OS (ubuntu: ahaoboy/v8-build tip-of-tree main 15.7.0 with is_component_build=true, 934.6 KB d8 plus 65.1 MB shared libraries, the git checkout of the version commented out; Windows and macOS: Google's official canary 15.7.35), one run per engine with the warm-up thrown away; JavaScriptCore beats V8 on RegExp on all OSes, and plb2's jitless Node is about QuickJS speed (nqueen 55.48 vs 59.04 s, matmul 162.84 vs 135.66 s).

## Caveats and trade-offs

Third-party shootout run by CI on GitHub-hosted runners; CPU model, compiler and flags are not stated and the engine binaries come from prebuilt per-engine build repos (ahaoboy/v8-build, ahaoboy/quickjs-build), so this is tier B rather than A. Versions on the page: v8 15.7.0 (ubuntu) and 15.7.35 (macos-arm64, windows), QuickJS 2026.06.04. The suite is an Octane/v8-v7 subset (Richards, DeltaBlue, Crypto, RayTrace, EarleyBoyer, RegExp, Splay, NavierStokes, forked from mozilla/arewefastyet) scored over a fixed time budget. V8 is top on ubuntu and windows but second to JavaScriptCore (67664) on macos-arm64. JIT engine vs interpreter-only baseline: V8 costs 28.8-66 MB on disk vs about 1 MB for QuickJS (Score/MB on ubuntu 729 vs 1190), so the comparison trades footprint for peak speed. The benchmark repo is small (59 stars). GitHub repo is a mirror of chromium.googlesource.com. plb2 numbers are from https://raw.githubusercontent.com/attractivechaos/plb2/HEAD/README.md (Node and Bun, not a bare V8 shell).

Embeddable C++ API, but large (shell build listed at 66M total, score per MB 729 vs QuickJS 1190), complex build system (gn/depot_tools), JIT requires writable-executable memory so it is not usable on locked-down platforms; much higher memory and startup cost than QuickJS or Duktape.

## Maintenance

Very active (several commits on 2026-10-06; main is version 15.7), BSD-3-Clause and copyable, but the GitHub repo is a read-only mirror of chromium.googlesource.com with issues disabled, and embedding means owning a heavy toolchain and a steady security-update cadence.

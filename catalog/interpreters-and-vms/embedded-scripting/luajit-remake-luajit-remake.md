## Verdict

Across 44 Lua benchmarks on an Intel i7-12700H laptop, pinned to one core, with GC off in all VMs, LJR's generated interpreter ran about 1.31x faster than LuaJIT 2.1's interpreter (JIT off) and 2.79x faster than PUC Lua 5.1 by geometric mean (paper abstract via search snippet; the 2022 README says 1.346x and 2.85x). Baseline versions and build flags are not given in the repo, and the bench script times only luajitr, which now tiers up to the baseline JIT by default.

## Use it when

- Research or teaching on interpreter and JIT construction: seeing how a generated interpreter (Deegen) can beat LuaJIT's hand-written assembler interpreter.
- Benchmark studies of dispatch techniques (GHC-convention tail calls, inline caching, hidden classes) on x86-64 Linux, using the 44 scripts in luabench/.
- Running self-contained, short-lived Lua 5.1 batch scripts on x86-64 Linux where memory growth without GC is acceptable and the scripts do not need require/module.

## Skip it when

- Anything long-running or allocation-heavy: there is no garbage collector, so memory only grows.
- Embedding in a C/C++ application: only the standalone luajitr binary exists; there is no documented Lua C API, FFI or REPL, and the package library (require, module) is missing.
- Platforms other than x86-64 Linux, or CPUs without BMI, SSE4 and FSGSBASE (the release build uses -mbmi -msse4 -mfsgsbase).
- Peak throughput: per the paper abstract, LJR's baseline JIT is on average 33% slower than LuaJIT's optimizing tracing JIT (faster on 13 of 44 benchmarks), and the optimizing (DFG) tier is unfinished.
- Production use: the README calls it a work in progress far from production-ready, and the last commit is 2025-02-18.

## How it is fast

Each bytecode handler is compiled through LLVM IR as a function using LLVM's GHC calling convention, which has no callee-saved registers and is patched here to pass more arguments. Handlers end in guaranteed tail calls, so dispatch is continuation passing with the VM state pinned in registers. Deegen also generates inline caches for table and call sites, type-speculation fast paths, and slow paths split out of the hot code (deegen_ast_inline_cache, deegen_call_inline_cache, deegen_ast_slow_path). Tables use hidden-class 'structures' with butterfly storage (runtime/structure.h, butterfly.h), so property access can be served from an inline cache.

## Compared with alternatives

For production embedding, pick a maintained sibling such as Luau (which also beats PUC Lua 5.x with its interpreter) or Daslang, because LJR has no GC, no C API and no commits since 2025-02-18; pick yklua for a JIT on current PUC Lua 5.5 semantics. Pick LJR only to study or reuse the Deegen approach, or to compare interpreter designs on Lua 5.1 code.

## Gotchas

- Harness and reproduction flaw: the README's 34.6% / 185% numbers were last updated 2022-11-26, when only the interpreter existed. At HEAD, deegen/deegen_options.h sets x_allow_interpreter_tier_up_to_baseline_jit = true and VM::Create defaults to EngineMaxTier::Unrestricted, and standalone/main.cpp exposes no switch. A HEAD build of luajitr therefore moves each function to the baseline JIT after it has executed 20x its bytecode length, so `bash run_bench.sh` measures interpreter plus baseline JIT rather than the interpreter the README compares. To reproduce the claim you must edit that constant or build a 2022 commit.
- run_bench.sh times only luajitr; the PUC Lua 5.1 and LuaJIT baselines are not scripted, and how their GC was disabled is not documented. It sends stdout and stderr to /dev/null and checks only the exit code, so output correctness is not verified. bench_pretty_format.py reports the mean of the middle 5 of 7 runs (fastest and slowest dropped), while the README footnote says 5 repetitions.
- There are three different headline figures: the 2022-11-22 blog says 28% faster than LuaJIT's interpreter and 171% faster than PUC Lua; the README says 34.6% and 185%; the peer-reviewed paper abstract (search snippet only) says 31% and 179% over 44 benchmarks. Cite the paper's figure.
- GC was turned off in every implementation, so the comparison leaves out collector cost entirely, and a real LJR deployment would run out of memory where PUC Lua or LuaJIT would not.

## Known shortcomings

- Beats the LuaJIT interpreter, not LuaJIT's JIT (the paper's own baseline JIT is about 33% faster); OOPSLA 2026 Deegen paper numbers are snippet only (arXiv blocked). run_bench.sh runs only luajitr, baseline builds are not scripted; no garbage collector; last commit 2025-02-18 (stale).
- Enricher: the README 34.6%/185% numbers date from 2022-11-26 and are interpreter-only, but at HEAD deegen_options.h sets x_allow_interpreter_tier_up_to_baseline_jit = true with the VM's default max tier Unrestricted and luajitr has no switch, so run_bench.sh now measures interpreter plus baseline JIT; it also discards output and checks only the exit code, and the baselines and their GC-off method are not scripted. Three headline figures circulate: blog 28%/171%, README 34.6%/185%, paper 31%/179% (the paper confirms the baseline is the LuaJIT 2.1 interpreter).

## Caveats and trade-offs

Work in progress and not production-ready per the README. Garbage collection was turned off for every implementation in the comparison, which hides the collector cost of PUC Lua and LuaJIT. README names no PUC Lua or LuaJIT versions or their build flags. Single laptop; run_bench.sh notes thermal fluctuation of about 10 percent. The JIT tiers are not finished in the repo (README says ongoing; last commit is 2025-02-18), so the JIT numbers exist only in the paper. The paper (Deegen: A JIT-Capable VM Generator for Dynamic Languages, OOPSLA 2026 per the search result) could not be opened because arXiv is blocked. ## Maintenance

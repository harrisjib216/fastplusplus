## Verdict

Author-run benchmark (2017) comparing MD4C's md2html CLI against the cmark CLI of that era, 10 runs each on tmpfs, on a 64-bit Slackware 14.2 Linux box with unstated CPU and compiler flags: MD4C ran 1.4x-7.7x faster depending on input shape and used \~1.8x less peak heap on a \~105MB Pro-Git Markdown compilation, with far fewer realloc() calls (36 vs 1,304,578) reflecting its no-AST design.

## Use it when

- You only need HTML (or another flat format) output and don't need to inspect/mutate a parsed document tree
- You're parsing large or many documents and cmark's AST allocation overhead (memory, realloc churn) is the bottleneck
- You want a single-header/single-source C library to vendor with zero dependencies beyond libc
- Input may be adversarial or untrusted and you want protection against quadratic-time pathological Markdown
- You're fine writing your own callback-based renderer instead of consuming a ready-made tree

## Skip it when

- You need a DOM/AST to transform, query, or re-serialize the document (MD4C has no tree; you'd build and maintain your own)
- You need GFM tables/strikethrough/tasklists out of the box without opting into extension flags — CommonMark-only by default
- Input isn't already validated UTF-8/ASCII-compatible and you care about malformed-input handling: MD4C does no input validation by design (GIGO) and will propagate ill-formed byte sequences verbatim
- You're relying on the 2017 author benchmark as a rigorous head-to-head: CPU model and compiler flags are unstated, and it compares a SAX renderer against an AST-building parser, which the author himself calls an unfair memory comparison
- You need runtime allocator customization or documented thread-safety guarantees — neither is documented in the public header

## How it is fast

No AST allocation: nodes/spans are never materialized as heap objects, they're reported directly as callback events with pointers into the original input buffer plus a length (strings aren't even zero-terminated, avoiding a copy). This is why realloc() calls on the Pro-Git benchmark are 36 for MD4C vs 1,304,578 for cmark, and heap peak is \~1.8x lower. The parser is also written for linear/near-linear time on adversarial input, with a pathological-input test suite (test/pathological-tests.py) guarding against the quadratic blowups some Markdown parsers hit.

## Compared with alternatives

No siblings catalogued yet for Markdown specifically — the other markup-html-markdown entries (lexbor, html5-parser, MarkupEver, MyHTML, pugixml, roxmltree, selectolax, stb_xml) are HTML/XML parsers, not Markdown. Pick MD4C whenever the workload is Markdown-to-HTML (or Markdown-to-anything via callbacks) and you don't need a DOM.

## Gotchas

- Callback strings are not zero-terminated; you must use the supplied MD_SIZE length, not strlen()
- No input validation: malformed UTF-8 is passed through to callbacks unchanged (GIGO philosophy), so validate upstream if that matters
- Multiple heap-buffer-overflow CVEs were reported and fixed in 2018 (issues #36–#39); no similar reports found in more recent history via search
- GFM-style tables, strikethrough, footnotes, tasklists, highlight/insert/spoiler spans etc. are all opt-in via MD_FLAG_\* bits, not defaults

## Caveats and trade-offs

Author-run benchmark (MD4C author, July 2017) against the cmark master of that time (\~0.28), never independently reproduced. The script is public in a gist, but the CPU model and compiler flags are not stated. It compares a SAX-style renderer with AST-building cmark: in the author's own follow-up (post #14), an experimental MD4C path that builds a cmark AST narrows the gap to \~1.4-1.5x (0.32s vs 0.46-0.48s on many-atx-headers/many-paragraphs). The \~105MB size belongs to cmark-benchinput.md alone, not to the synthetic files.

SAX-like push parser only (no DOM), CommonMark-compliant but no built-in GFM table/strikethrough support unless the caller implements it, does no input validation by design (GIGO philosophy), assumes UTF-8 by default.

## Maintenance

Actively maintained (last commit 2026-09-17), MIT licensed, single C source/header pair small enough to vendor directly — low risk to adopt even without upstream support.

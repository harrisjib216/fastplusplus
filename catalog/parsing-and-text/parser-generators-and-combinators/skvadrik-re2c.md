## Verdict

On 35 Google Benchmark CPU-time lexer benchmarks (HTTP, URI, Apache log, datetime, email, IPv4, plus synthetic alt/cat/rep patterns), built with GCC-14.2.0 and Clang-19.1.4 at -O3 on an Intel Core i7-8750H, re2c --tags lexers ran roughly 1.0-1.44x faster than Ragel 7.0.4's -G2 simple variant on the real-world formats, but 1.5-4.1x slower on synthetic repetition-heavy patterns — I confirmed the raw cpu_time values (e.g. http-rfc7230-gcc_re2c-simple = 21.17) directly in results_20250131.json.

## Use it when

- Target is C, C++, Go, Rust, D, Java, JS, OCaml, Python, Swift, V, or Zig and you need only a lexer, integrated by hand, not a full parser toolkit
- Real-world text formats close to the benchmarked ones (HTTP headers, URIs, log lines, datetimes, email addresses), where re2c ran \~1.0-1.44x faster than Ragel
- You're willing to write buffer/driver code yourself in exchange for not depending on Ragel's runtime conventions
- Submatch/capture extraction is needed alongside tokenizing (--tags)
- Public-domain licensing (no attribution or patent clause) is acceptable or preferred

## Skip it when

- Grammar is dominated by fixed-length repetition/counting patterns (the rep-\*/rep-alt-\* benchmarks) — Ragel was 1.5-4.1x faster there
- You want one tool for both lexing and parsing; re2c only generates the lexer, so you still need a separate parser
- You need re2c benchmarked against Flex, Bison, ANTLR, or Boost.Spirit before deciding — its own suite only compares to Ragel
- Grammar is large/complex enough that inline-jump code generation risks a much bigger generated file than a table-driven approach (see issue #427, "Generated file too large")
- Betting specifically on the Go backend (re2go) for throughput — issue #487 reports a real-world case where generated Go code was reportedly an order of magnitude slower than Go's standard regexp

## How it is fast

Instead of Ragel's/Flex's table-driven DFA interpretation, re2c encodes the automaton directly as conditional jumps and character-range comparisons in the target language, letting the downstream compiler apply ordinary branch and jump-table optimizations to the lexer body. It runs its own passes (state merging, jump threading, range-comparison compression) before emitting code, and for --tags submatch extraction tracks minimal per-tag position updates rather than replaying full match history.

## Compared with alternatives

Pick re2c over the catalogued siblings when you need a lexer only (not a full parser) and want one grammar to retarget across many languages (C/C++/Go/Rust/Java/etc.); the siblings (flap, PAPAGENO, Pika Parser, winnow, chumsky, lexy, MPL/FastParse) are single-language parser or parsing-combinator libraries benchmarked against Bison/Flex, ANTLR4, or nom, and none of them compare to Ragel the way re2c does.

## Gotchas

- Nothing runs out of the box: you must define the API primitives (buffer cursor, limit, refill callback, etc.) yourself before generated code compiles or runs correctly — re2c does not validate these definitions
- Inline-jump codegen can make generated files much larger than table-driven output for big/complex grammars (issue #427)
- The Go backend (re2go) has at least one reported case of being far slower than Go's stdlib regexp on real-world input (issue #487) — don't assume the C/C++ numbers here transfer to other backends
- License is a bespoke public-domain dedication with no explicit patent grant; GitHub's license detector reports it as NOASSERTION, which some legal reviews flag despite it being effectively public domain

## Caveats and trade-offs

The baseline is Ragel, not Flex/Bison/ANTLR/Boost.Spirit; none of those appear in re2c's benchmark suite. Results are mixed: real-world grammars mostly favor re2c (\~1.0-1.44x simple-vs-simple, smaller against Ragel's buffered variant), but synthetic repetition-heavy patterns favor Ragel by 1.5-4.1x, so 'faster' does not hold universally. Ragel has no results for 4 of the 35 benchmarks (rep-cat-\*, rep-23-rep-19-rep-17), and the cpu_time unit is not stated in the JSON. GitHub reports the license as NOASSERTION because the LICENSE is a bespoke public-domain dedication ('re2c is in the public domain... may be distributed freely'), with no patent grant; usability=copyable per the public-domain rule.

re2c emits inline conditional-jump state machines instead of table-driven code, which can grow generated code size for large grammars; it requires hand-writing the driver/interface code around the generated lexer; results are workload-dependent rather than a uniform win.

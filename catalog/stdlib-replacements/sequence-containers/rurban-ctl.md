## Verdict

First-party log-scale plots from the repo's tests/perf programs compare CTL (gcc -std=c11) against libstdc++ (g++ 10.2.1, -std=c++17) at -O3 -march=native on int elements up to about 25k, one run per size, on an unstated CPU; the result is parity for most push, insert, erase and iterate operations, wins for str push_back (about 3-4x), priority_queue top (an O(1) read loop) and unordered_set erase (about 1.3x), and losses for deque pops (3-4x) and all sorts (1.2-35x). The plots date from early 2021 and do not cover the 2026 swisstable.h and hashmap.h.

## Use it when

- Pure C99/C11 code bases that want STL-like containers with type safety and no C++ runtime, at roughly libstdc++ speed for push, insert, erase and iteration on int-sized elements.
- Byte-string building with push_back in C, where its str measured about 3-4x faster than std::string push_back at about 25k chars.
- Projects that value hardening over raw speed: a 2^32-byte default max_size, compile-time hash-collision policies (sleep, abort, sorted vector or tree fallback) and cbmc/satabs-verified core functions.
- Code that wants C versions of the C++23/26 containers (flat_map, inplace_vector, hive) with the same names as the standard.

## Skip it when

- Sorting: vec/deq/str sort is a recursive Lomuto quicksort with no insertion-sort cutoff and no introsort fallback; it measured 1.5-2x slower than std::sort on random ints and about 35x slower on a string of 25k chars from 23 values, and inputs with many equal keys degrade toward O(n^2).
- Deque-heavy queues: deque pop_back and pop_front measured about 3-4x slower than std::deque, and each page holds 512 elements, so a deque of 3 doubles costs about 4 KB (issue #26, a FreeRTOS board ran out of heap).
- Hash tables on a fast path: unordered_set is chained like std::unordered_set (the docs say it is 'not much better'), and the newer swisstable.h/hashmap.h use scalar linear probing, rehash the whole table on every erase, and have no published benchmarks.
- Latency-critical services with the default security policy, which can call sleep(1) inside a lookup (see gotchas).
- Multithreaded sharing: nothing is thread-safe; thread-safe 'pctl' variants are only planned.

## How it is fast

There is no special algorithm: every function is a static inline specialization generated by the preprocessor, so the compiler inlines the whole container into the caller, while several libstdc++ members (for example std::string's growth path) are called from the shared library, which the README credits for part of the results. Data structures are conventional: realloc'd vector and string, deque of 512-element pages, red-black tree set/map, chained hash buckets for unordered_set with prime or power-of-two growth, and scalar linear probing for swisstable.h/hashmap.h. Sorting is a plain recursive Lomuto quicksort, which is why its sorts lose.

## Compared with alternatives

Pick CTL when the code must stay in C: the catalogued sequence-container siblings (ankerl::svector, plf::colony, plf::list, EASTL, veque, fast_vector) are C++ and show real speedups over std containers, while CTL only reaches parity. libcdada is the other C option in the category and also reports parity with libstdc++; CTL covers far more container types and is header-only.

## Gotchas

- Default hash collision policy CTL_USET_SECURITY_COLLCOUNTING 2 runs `if (++count & 128) sleep(1)` in unordered_set, swisstable.h and hashmap.h find, insert and erase; the bit test is true for every probe from the 128th to the 255th (and again from 384th), so one walk through a 200-entry chain or probe run sleeps about 72 s. With swisstable's linear probing at its 0.75 maximum load, or with the identity int hash used in the docs' example and dense keys, such runs are reachable without an attacker (from code reading, not measured); define CTL_USET_SECURITY_COLLCOUNTING 0 or 3, or use CTL_USET_CACHED_HASH, if latency matters.
- swisstable.h is not a SIMD Swiss table despite the name: it is scalar linear probing over entries with a used flag, POD keys and values only, and erase calls a full same-capacity rehash (O(capacity) per erase); pointers from find are invalidated by growth and by erase.
- Errors are silent: size beyond max_size (2^32 bytes by default) or allocation failure returns without action unless assert.h is included without NDEBUG; containers above 2 GB need max_size raised explicitly.
- Harness limits behind the plots: one gettimeofday-timed run per size (microsecond resolution, sizes up to 99 x 256 = 25,344 ints); the 7x priority_queue top 'win' times 25k reads of the same O(1) element into a volatile, so it measures loop code generation, not the container; the compile chart warms up only the C compile before timing it.

## Known shortcomings

- Tier C, no CPU model: plots (March 2021, vs libstdc++ 10.2.1) show parity overall; wins are str push_back 3-4x, pqu top about 7x and uset erase 1.3x; losses are deque pop_back/pop_front 3-4x slower and every sort slower (string sort about 35x). Fork of glouw/ctl.
- Enricher: plots are mostly parity with 2021 numbers from one gettimeofday run per size (max 25,344 ints); the pqu top '7x win' is an O(1) read loop into a volatile and measures codegen; the compile chart warms up only the C compile; sort is a naive recursive Lomuto quicksort with no cutoff or introsort (explains the 35x string-sort loss; duplicate-heavy input goes O(n^2)). Gotcha: default CTL_USET_SECURITY_COLLCOUNTING 2 does 'if (++count & 128) sleep(1)' in unordered_set, swisstable.h and hashmap.h, firing on every probe 128-255, so one long chain sleeps up to 128 s; swisstable.h is scalar linear probing, not SIMD, and fully rehashes on every erase; deque page is 512 elements (issue #26); no benchmarks for 2026 hash maps.

## Caveats and trade-offs

This is a weak claim: the project's stated goal is STL-compatible C containers with security and verification features, and the plots show parity rather than wins, with sorts and deque pops clearly slower. The README says only 'C is roughly comparable to C++'; the unordered_set doc says 'Overall the STL unordered_set performance is bad, and our is also not much better.' The compile chart shows equal compile time (about 1.7 s each) and a larger stripped CTL binary (60.12 KB vs 43.944 KB), with only compiler memory lower. No ratio appears in text; all figures were read off embedded PNG plots, so they are approximate. The plots were last regenerated in February-March 2021 (last docs/images commit 2021-03-26, GCC 10.2.1), so they predate about five years of changes (new hashmap policies, swisstable work in 2026); the str and set graphs are not in gen_images.sh's default list. Hardware is not stated; each point is a single wall-clock run per size; results are first-party. Only int (and char for str) elements are measured. As the README notes, the C++ functions are partly dynamically loaded from libstdc++.so.6 while the C versions are compiled into the binary. GitHub shows the repo as forked from glouw/ctl; the README lists a renamed API and 254 methods as improvements over the original. [retier] 2021 plots vs libstdc++ 10.2.1 (no CPU model), one gettimeofday run per size (at most 25,344 ints): parity overall; str push_back 3-4x and uset erase 1.3x wins; pqu top 7x is an O(1) read into a volatile (codegen, not work); deque pop 3-4x slower; every sort slower (naive Lomuto quicksort, string sort 35x). Default CTL_USET_SECURITY_COLLCOUNTING sleeps 1 s per probe in the 128-255 range; swisstable.h is scalar and rehashes fully on erase. Fork of glouw/ctl.

Header-only macro-templated containers for C99/C11 (one include per element type), 24 container types, fat bounds-checked iterators, default max_size of 2^32 bytes and anti-DoS hash policies; the unordered_set uses a security-oriented collision policy that trades speed for safety. Only the lower-than comparator is officially supported with algorithms.

## Maintenance

Actively developed (973 commits, last commit 2026-09-25, with heavy 2026 work on hash maps and C++23/26 containers) and MIT-licensed, but the published performance evidence is five years old, first-party and mostly shows parity; the default hash-collision policy can sleep inside lookups and the quicksort degrades on duplicate-heavy input.

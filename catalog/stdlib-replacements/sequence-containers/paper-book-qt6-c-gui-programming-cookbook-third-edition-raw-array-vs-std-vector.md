## Verdict

The book (relayed via the seed lead; no numbers on any repo page) reports one run: new int[] about 650 ms, std::vector&lt;int&gt; about 3,830 ms and QVector&lt;int&gt; about 5,400 ms for filling and summing 100,000,000 ints, about 5.9x and 8.3x slower than the array (derived). Compiler, build configuration and CPU are not stated; the .pro file sets no optimisation flags or CONFIG += release, so Qt Creator's selected configuration decided, and the vector sides grow without reserve and read with at().

## Use it when

- A hot path that fills a large buffer whose final element count is known up front, where profiling shows reallocation from a growing vector.
- Large buffers of trivial types that will be overwritten anyway, where you want to skip the zero-fill that std::vector&lt;int&gt;(n) or resize(n) performs (new int[n] leaves ints uninitialised).
- Interop with C APIs that take a pointer and a length and own nothing, keeping ownership in std::unique_ptr&lt;int[]&gt; rather than a bare pointer.
- Debug or unoptimised builds where std::vector and QList layers are not inlined and their per-element overhead dominates (for example a tool that has to run fast in Debug).

## Skip it when

- Any case where std::vector with reserve(n) (or a sized buffer read with operator[]) is acceptable: that closes most of the measured gap and keeps RAII, size tracking and iterator support.
- Sizes that are not known before filling: the raw array cannot grow, and hand-rolled growth just re-implements std::vector.
- Code that relies on bounds checks for safety, or on exception safety: a bare new[] leaks if anything between new[] and delete[] throws, and mismatched delete is undefined behaviour.
- Qt API boundaries that expect QList/QVector: converting from a raw buffer copies the data, losing the gain.
- Expecting the book's 5.9x or 8.3x in an optimised build: the comparison was one run of an unstated build configuration and its baseline idioms (no reserve, at()) carry most of the difference.

## How it is fast

The array side does one allocation of the final size and then plain indexed stores and loads, while both container sides grow geometrically from empty, so they reallocate and relocate everything stored so far many times (about 27 times to reach 100M if capacity doubles; the growth factor is implementation-defined), touch more fresh pages, and pay a bounds check on every std::vector::at() read. The speedup therefore comes from preallocation plus unchecked access, not from a faster container: std::vector with reserve(count) and operator[] performs the same memory operations as the array. The relayed 650 ms for the array is about 6.5 ns per element for one store, one load and the page faults (derived), slow for an optimised build, which points to an unoptimised one (inference; the build is not stated).

## Compared with alternatives

Try the Data Structures and Algorithms with the C++ STL reserve() sibling first: reserve plus operator[] gets most of this gain while keeping std::vector. Pick a raw or unique_ptr-owned array only when you also need to skip value-initialisation of a large trivial buffer; for many small vectors ankerl::svector or sfl::small_vector avoid the heap, and fast_vector reports about 2x over std::vector even with reserve.

## Gotchas

- The int sum of 0..99,999,999 overflows a signed int (undefined behaviour) and result, result2 and result3 are never used, so an optimising compiler may remove the array test entirely (new/delete pairs may be elided since C++14) and report a near-zero time for it.
- Each timed region includes allocation, first-touch page faults and the free at function exit; the tests run once in a fixed order (array, std::vector, QVector) with no warm-up, timed by QElapsedTimer in whole milliseconds. With doubling growth the vector briefly holds both the old and new buffers at its last reallocation, about 0.8 GB for 400 MB of ints (derived).
- In Qt 6, QVector&lt;T&gt; is an alias of QList&lt;T&gt;, and QList::at() is noexcept with only a Q_ASSERT_X bounds check that release builds compile out; that QVector is still the slowest of the three in the book's run fits a Debug build better than a release one (inference).
- Matching the array with the standard library needs care: std::vector&lt;int&gt;(n) and resize(n) zero the buffer before you write it, so use reserve(n) plus push_back, or std::make_unique_for_overwrite&lt;int[]&gt;(n) (C++20), to avoid writing the memory twice.

## Known shortcomings

- Book numbers only. Optimizing.pro sets no optimisation flags, so a Debug build is likely; the int sum overflows (undefined behaviour) and results are unused, so -O2 may delete the array test. The gap is mostly push_back without reserve plus at() bounds checks, not std::vector itself. Stale (last commit 2024-04-22).
- Enricher: gap is mostly the idiom (no reserve, bounds-checked at(), zero-fill); QVector result fits a Debug build; signed overflow and unused results let the optimiser elide the array test.

## Caveats and trade-offs

The timing numbers are the book's own (quoted in the seed lead); the repository carries the benchmark program but no results file, so the numbers do not appear on the benchmark_url page and the ratios could not be checked against it. Idiom difference more than a container difference: the array is allocated once at full size and indexed with operator[], while the vector grows by push_back with no reserve() (repeated reallocation and copying of up to 400 MB) and is read through bounds-checked at(); a reserved vector read with operator[] would close most of the gap. Compiler, flags and CPU are not stated; the .pro file sets no optimisation flags and Qt Creator's default build configuration for a new project is usually Debug, in which case std::vector and QVector overhead (no inlining) is exaggerated. Each test runs once, in a fixed order (array first), and the returned sums are unused. The code sits in an application main() beside a GUI start-up, not a standalone benchmark. [verifier] The int sum of 0..99,999,999 overflows a signed int (undefined behaviour), and because the results are unused an optimised build may delete the array test entirely (new/delete pairs may be elided since C++14), so a 650 ms array time with a several-second push_back vector fits an unoptimised build better than a release one. In Qt 6, QVector&lt;int&gt; is an alias of QList&lt;int&gt;. [retier] Enricher: most of the gap is the idiom (no reserve plus std::vector::at bounds checks); std::vector&lt;int&gt;(n) zero-fills, so use reserve or make_unique_for_overwrite to match new[]. Qt 6 QList::at() is noexcept and checks bounds only through Q_ASSERT_X (qtbase 6.5 qlist.h), so QVector being slowest fits a Debug build (inference). Vector growth peaks near 0.8 GB (derived). The signed int sum overflows (undefined behaviour) and unused results let the optimiser elide the array test.

A plain new[] array has a fixed, known size, no growth, no bounds checking and no RAII (a leak or double delete is the caller's problem); std::vector or std::unique_ptr&lt;int[]&gt; keeps the safety. The win only applies when the element count is known up front.

## Verdict

The only number is a Julia-binding README line, written in 2018 by a Julia maintainer after issue #37 disproved the earlier '7x faster than openlibm' line: Yeppp.log! is '3x faster' than Julia's own Base log on 10^7 random Float64. It comes from a single cold @elapsed run of each (JIT and allocation included) with no CPU, Julia version or flags stated. Independent runs on Skylake-era machines found Yeppp slower (0.66x in #37; 0.027 s vs 0.015 s for a plain loop in #32), which the dispatch table explains: those CPUs never reach the assembly kernels.

## Use it when

- Legacy code that already uses its array API and runs on the x86-64 cores it was tuned for (Nehalem to Haswell, AMD K10, Bobcat, Bulldozer to Steamroller), where the assembly kernels actually run
- Studying how per-microarchitecture assembly is generated (PeachPy) and how a high-degree Horner polynomial is interleaved across many SIMD registers to hide FMA latency
- Projects that need one vendored BSD-3 array-math API callable from C, C#, Java and Fortran, and that accept a scalar fallback on everything else

## Skip it when

- Any x86-64 CPU newer than Haswell (Intel) or Steamroller and Jaguar (AMD): the dispatch table has no entry for Broadwell, Skylake or later Intel models, nor for any Zen, so log, exp, sin, cos and tan fall back to a scalar C loop. Users report it slower than plain Julia: i7-6820HQ Yeppp 0.027 s vs loop 0.015 s (Yeppp.jl #32); Yeppp.log! at 0.66x of Base on Julia 0.6.2 (#37)
- ARM, PowerPC, MIPS or 32-bit x86: codegen/math.py registers only x64 assembly for the transcendental functions, so those platforms always run the scalar C fallback
- Code that can see NaN or +Inf in its input (see gotchas)
- Anything needing maintenance, AVX-512 or SVE, a float32 transcendental API, or a buildable source tree. The official Bitbucket repo and its release binaries are gone, and the GitHub mirror lacks the generated yepCore/yepMath sources and headers

## How it is fast

The kernels are x86-64 assembly generated by the author's PeachPy Python assembler, with one hand-scheduled version per microarchitecture (Bobcat, K10, Nehalem, Sandy Bridge, Bulldozer, Haswell). Log reduces the input to a mantissa in [sqrt(2)/2, sqrt(2)) and evaluates a degree-20 Horner polynomial with a double-double ln2. The Haswell fast path interleaves 10 AVX2/FMA3 vectors (40 doubles) to hide FMA latency and branches to a slower full path only when a batch holds subnormal, zero, negative or infinite values. At yepLibrary_Init() a dispatcher picks the kernel by matching the CPU model it detected against a hard-coded list of microarchitectures.

## Compared with alternatives

Rarely. SLEEF covers the same vector log/exp/sin with documented ulp bounds, is maintained, and supports AVX-512, NEON and SVE. VDT is header-only and inlines into auto-vectorized loops. herumi/fmath is faster for float32 logf/expf. Pick Yeppp! only for legacy code bound to its array API on Haswell-era or older x86-64.

| **Thread safety** | Not documented. yepLibrary_Init() must run once before any call because it fills global dispatch pointers that start as NULL. The array kernels keep no other state |
| **Drop-in for the baseline** | no |

## Gotchas

- Correctness bug in the scalar C fallback (yepBuiltin_Log_64f_64f in library/headers/yepBuiltin.h). The final '+inf and NaN' fixup tests x after x has been overwritten by the reduced mantissa (always in [0.707, 1.414)), so it never fires. log(NaN) returns 1025\*ln2 + ln(0.75) = 710.188 and log(+Inf) returns about 709.78. This matches Yeppp.jl issue #31 exactly ('Yeppp.log([NaN]) = 710.188', open since 2016). That fallback is the path modern CPUs take
- The Sandy Bridge and Haswell AVX log fast paths screen inputs with ordered VCMPLTPD/VCMPGTPD against min_normal/max_normal. Those compares are false for NaN, so NaN appears to stay on the fast path and come out near 710. This is from reading the code, not from running it. The Nehalem path uses an unsigned integer range check and does catch NaN
- Dispatch matches exact CPU models: the x64 switch in Dispatch.cpp has no case for Broadwell or SkyLake, even though CpuX86.cpp detects them, and CpuX86.cpp does not know Skylake-S/H (model 0x5E), any later Intel core, AMD Excavator or Zen. All of these get the 'Unknown' list and the naive C++ implementation, with no warning
- Pointers must be naturally aligned (8 bytes for double) or calls return YepStatusMisalignedPointer. Calling any function before yepLibrary_Init() calls through a NULL dispatch pointer. Tan has assembly only for AMD Bulldozer (FMA4), so on Intel it is always scalar

## Known shortcomings

- Only a 3x-over-Julia-Base-log claim from the Yeppp.jl README (confidence low); the original Bitbucket repo is gone, so the record points at an unofficial GitHub mirror. Filed under stdlib-replacements/math-simd-linear-algebra (elementwise SIMD math), not big-integer-arbitrary-precision.
- The only number is the Yeppp.jl README's '3x vs Base log' (baseline Julia log, not &lt;cmath&gt;); the mirror has a libm harness (examples/c/sources/Entropy.c, -O3) with no published numbers, and a Julia Discourse snippet reports Yeppp.log 2x slower on some CPUs. Bitbucket original 404; mirror 39 stars, abandoned 2015.
- Dispatch flaw that holds on any current CPU: Dispatch.cpp matches exact CPU models only, so Broadwell, Skylake and later Intel plus Excavator and Zen fall back to scalar C for log/exp/sin/cos/tan; this explains Yeppp.jl #37 (0.66x of Base on Julia 0.6.2) and #32 (i7-6820HQ: Yeppp 0.027 s vs loop 0.015 s). Correctness bug: yepBuiltin_Log_64f_64f tests x after mantissa reduction so its NaN/+Inf fixup never fires (log(NaN) = 710.188, matching open issue #31; log(+Inf) = 709.78); the Sandy Bridge and Haswell AVX paths appear to pass NaN through too (code reading). The README 3x line was written in 2018 by the Julia maintainer after #37 disproved the old 7x line, from a single cold @elapsed run with no CPU stated. The mirror lacks the generated yepCore/yepMath sources (needs Python 2.7 plus old PeachPy), Bitbucket binaries are gone, tan has assembly only for AMD FMA4.

## Caveats and trade-offs

The only number reachable is a one-line claim in the Yeppp.jl (Julia binding) README ('Yeppp's vectorized log is 3x faster than the one in Base, which is written in Julia') with a five-line @elapsed example: one cold run each, no warm-up, no hardware, Julia version, compiler or flags. The baseline is Julia's own scalar log, not &lt;cmath&gt;/libm, the baseline of the math-simd-linear-algebra category this record is now filed under. The mirror ships a libm-baseline harness, examples/c/sources/Entropy.c (naive p\*log(p) loop with libm log versus yepMath_Log_V64f_V64f plus yepCore_DotProduct on 16M doubles, built with -O3 by examples/c/Makefile), but no published output. Independent reports contradict the 3x on newer machines (WebSearch snippets only, discourse.julialang.org EGRESS_BLOCKED): in the 2019 Julia Discourse thread 'Performance of log.(x)' Yeppp.log was about twice as slow as Base log on one machine, and posters note its speed is inconsistent across architectures, sometimes slower than an unvectorized loop, because the precompiled 2014-2015 binary dispatches on CPU models it recognizes. The official Bitbucket repository (bitbucket.org/MDukhan/yeppp) returns 404, so repo_url is the unofficial GitHub mirror (last commit 2015-08-24 'Build: new build system based on Ninja + Python'; its README is a FAQ with no benchmarks). The project's own comparisons against MKL/libm on yeppp.info and docs.yeppp.info, the PPAM 2013 paper (Dukhan and Vuduc) and the Hot Chips 25 poster were EGRESS_BLOCKED and are not recorded. Abandoned since 2015. [retier] Vectorized paths dispatch on exact CPU model (Dispatch.cpp): Broadwell/Skylake and later, Excavator and Zen fall back to scalar C, so Yeppp.jl #37 (0.66x of Base) and #32 (i7-6820HQ slower than a loop) contradict the README's 3x line (single cold run, 2018). yepBuiltin_Log_64f_64f returns 710.188 for NaN (issue #31) and 709.78 for +Inf. Mirror lacks generated yepCore/yepMath sources; binaries gone.

Array-oriented SIMD library (vector add, multiply, dot, sum, log, exp, sin, cos, tan, polynomial evaluation) for 15 platforms across x86, ARM, PowerPC and MIPS, callable from C, C++, C#, Java and FORTRAN, with runtime dispatch to the best instruction set. Operates on whole arrays, not a drop-in scalar libm replacement.

## Maintenance

Abandoned since 2015 (mirror's last commit 2015-08-24; Yeppp.jl archived 2020-04-09), and the official Bitbucket repo and binaries are gone. BSD-3 lets you vendor it, but on current CPUs it runs a slow scalar fallback with a NaN/+Inf bug, so treat it as historical reference rather than something to copy.

## Verdict

The only number is first-party: discussion #567 (2025-04-24) reports 510,308 vs 34,721 animated 4-14 px anti-aliased rects held at 60 FPS (about 14.7x) for TGFX vs Skia chrome/m136 Ganesh, from the online WebGL benchmark built from libpag/tgfx-benchmark (TGFX main commit a56652e) and libpag/skia-benchmark. Device, GPU and browser are not stated. Reading the April 2025 harness code shows the two sides were not timed alike: Skia's frame time includes flushAndSubmit with GrSyncCpu::kYes (a blocking wait for the GPU), TGFX's flushAndSubmit() used syncCpu=false, and the ramp-and-stop rule keys on that frame time, so the 14.7x is inflated by an unknown amount.

## Use it when

- Animated 2D scenes with very many small, simple primitives (rects, rounded rects, sprites, atlas text) drawn on a GPU, where per-draw CPU overhead is the bottleneck.
- Mobile or web apps that want a Skia-like API with a much smaller binary, especially on WebGL 2 or WebGPU via WebAssembly.
- Projects already in the PAG/libpag ecosystem, or ones that need the same renderer on iOS, Android, HarmonyOS, desktop and the browser.
- Layer-tree UIs with partial or tiled redraw (the V2.1 notes claim support for canvases of up to 200,000 layers).

## Skip it when

- Anything that needs a CPU or software rasterizer (headless servers, printing pipelines): TGFX is GPU-only, and Linux without a GPU needs SwiftShader. Blend2D, ThorVG's CPU backend or Skia's raster backend fit better there.
- Workloads dominated by complex anti-aliased paths, strokes, gradients or blend modes: the only published comparison is the rectangle test, and the announcement says the platform runs only basic rectangle rendering.
- When you need Skia's full feature set (SkSL runtime effects, Graphite, PDF/SVG fidelity, mature text shaping) or a drop-in Skia replacement.
- When you need stable APIs: the latest tag is v2.1.1 (2025-09-26) while main has kept moving, and the benchmark repo itself needed a fix in August 2026 to adapt to the current TGFX window API.
- Apple-only Metal deployments: the README still lists the Metal backend as in progress.

## How it is fast

OpsCompositor defers draws into pending lists and merges consecutive drawRect calls that share clip and brush (colour may differ and goes per vertex) into one RectDrawOp of up to RectDrawOp::MaxNumRects = 2048 rects, drawn with a cached shared index buffer (30 indices per coverage-AA quad). That turns the benchmark's 500k drawRect calls into a few hundred draw calls. With TGFX_USE_THREADS, which is on by default for native builds and the wasm-mt web build, vertex data is generated by async tasks on worker threads (RenderFlags::DisableAsyncTask turns this off for single-rect ops) into a shared, block-allocated vertex buffer. The rest of the speed is a small code base built for batching rather than Skia's general Ganesh op pipeline; V2.1 also added SIMD math (Highway is a dependency).

## Compared with alternatives

Pick TGFX over vkvg, vger or the Rive Renderer when you want a broad Skia-like GPU API that ships on mobile, desktop and the web (WebGL 2 and WebGPU) from one code base. Pick Blend2D, ThorVG (CPU) or Vello CPU when no GPU can be assumed or when you need independently measured numbers.

## Gotchas

- Batching is the speed source: a change of draw type, clip or brush (shader, filters, blend) flushes the pending batch, and a batch holds at most 2048 rects, so interleaved heterogeneous draws lose most of the advantage the rectangle benchmark shows.
- The default web build is multithreaded wasm (pthreads with a worker pool of navigator.hardwareConcurrency); the README warns that renaming the generated .js breaks the worker bootstrap, and a single-threaded build (build:st) turns off async vertex generation.
- Open correctness issue #1172 (January 2026): thin polygon strips render incorrectly. Earlier anti-aliasing seam (#1068) and Src/SrcIn path blend (#544) bugs are closed.
- An independent user test in issue #381 (TGFX 1.2.1, Windows 11, December 2024) got about 30 FPS with 500 moving rects in TGFX versus about 100 FPS with 8,000+ in Skia. That predates the 2.0 rect batching and had no recorded maintainer resolution, but it is the only third-party data point found.

## Known shortcomings

- GPU-vs-GPU comparison (TGFX GPU backend vs Skia Ganesh, WebGL/WASM or native) from discussion #567: 510,308 vs 34,721 rectangles at 60 FPS (14.7x derived) with public bench code (libpag/tgfx-benchmark and libpag/skia-benchmark, src/benchmark/ParticleBench.cpp) but the device, GPU and browser for the posted numbers are never stated, so C. Skia benchmark moved to m136 on 2025-04-08 and m142 on 2025-10-15; screenshots sit behind private-user-images tokens. tgfx.org/benchmark blocked here.
- Retiered C to D (retier-22): the April 2025 harnesses time Skia with flushAndSubmit(GrSyncCpu::kYes), waiting for the GPU, and TGFX with flushAndSubmit() without a CPU sync (one-frame deferred submit since November 2025), and the ramp-and-stop rule keys on that draw time, so the 510,308 versus 34,721 rectangle counts (14.7x) are inflated by an unknown amount; only Skia is linked with -sASSERTIONS=2; the wasm-mt build runs TGFX vertex generation on worker threads while Skia records on one thread; a user test in issue #381 (TGFX 1.2.1) found Skia far faster; open bug #1172 (thin polygon strips).

## Caveats and trade-offs

First-party announcement (release notes of V2.1 dated 2025-04-24) with no GPU model, driver, OS, browser, resolution or backend for the quoted numbers; the result screenshots in the discussion sit behind private-user-images tokens and tgfx.org/benchmark is blocked from this environment (EGRESS_BLOCKED), so only the numbers quoted in the discussion text were seen. Benchmark code is public and the workload is identical on both sides (libpag/tgfx-benchmark and libpag/skia-benchmark, src/benchmark/ParticleBench.cpp; Skia built with is_official_build=true is_debug=false, Ganesh), so the comparison is GPU renderer vs GPU renderer, not a CPU rasterizer test. It is a single synthetic test of many small anti-aliased filled rectangles, which the discussion itself says covers only basic rectangle rendering; the result depends on draw-call batching more than rasterization. skia-benchmark moved to chrome/m136 on 2025-04-08 and to m142 on 2025-10-15, so today's online page compares against m142, not the m136 build behind the quoted numbers. [retier] Harness asymmetry invalidates the headline (GPU sync on the Skia side only; one-frame deferred submit on the TGFX side since November 2025; Skia alone built with -sASSERTIONS=2; TGFX vertex generation on worker threads in the wasm-mt build). First-party with no GPU model, driver, OS, browser or resolution; tgfx.org/benchmark is blocked here. A user test in issue #381 (TGFX 1.2.1) found Skia far faster before TGFX's batching work; open bug #1172 (thin polygon strips).

GPU-only (OpenGL 3.2+/ES 3.0+, WebGL 2, Vulkan 1.1+, WebGPU; Metal in progress); no CPU/software rasterizer; much smaller feature set than Skia (README: 'a compelling alternative to the Skia graphics library while maintaining a much smaller binary size'); runs on iOS, Android, HarmonyOS, macOS, Windows, Linux and the Web.

## Maintenance

Very active (last commit 2026-09-24, 1.6k stars, BSD-3-Clause, copyable), but the latest tagged release, v2.1.1, is a year behind main, and the only performance evidence is a first-party rectangle test whose harness favours TGFX.
